# 异步任务与完成语义分层（六对象权威 + 五层完成 + 九状态机）

## R（原文摘引）
> Task 是异步执行的最小业务单元，具有独立、持久的标识和自己的业务 State。Task 可以跨越等待、恢复、人工审批等多个阶段持续存在，也可以跨多个 Session 续跑。（第 10 章 10.1.1）
> 执行状态……它回答"这次执行有没有跑完"，不回答"业务目标是否达成"。（第 10 章 10.1.2）
> Checkpoint 保存的是按恢复契约保存的状态……它不等同于外部副作用幂等：若外部写入已提交而 Checkpoint 尚未落盘，重跑仍会产生重复副作用。（第 10 章 10.1.3）
> 任务队列承担排序与缓冲，调度器负责将 Task 投递给合适的 Worker 并维护租约，任务执行状态机维护生命周期与转换合法性。（第 10 章 10.2.3）
> run_latest 只补跑错过窗口内最新一次，其余忽略……prompt 不自动决策，挂起并通知运维或业务方人工选择。（第 10 章 10.3.3）
> OR Join 的关键是显式取消未选分支，否则它们会继续消耗资源、产生副作用，与下游已基于"先到结果"做出的决策冲突。（第 10 章 10.4.3）

## I（解释）
1. **先分对象权威，再写代码**：Task（业务应用定义，跨 Session 跨等待跨恢复）、业务 State（与 Task 同寿）、Session Context（按会话）、Checkpoint（按恢复契约）、Runtime State（一次执行租约内：心跳/租约/当前步骤）、外部副作用（与外部系统同寿）。跨 Session 续跑要显式装载授权的 Task State，不是默认共享上下文。
2. **完成语义五层防"进程结束当任务完成"**：执行状态（跑没跑完）→ 节点运维状态（基础设施健康，影响调度不等于任务结论）→ 候选证据（日志/Trace/快照/Artifact）→ Evidence（被成功标准明确引用并核验过的证据）→ Outcome（业务应用或获授权 Verifier 依成功标准做的最终判定）。LLM-as-a-Judge 只是 Evaluation 实现，不是 Outcome 权威。
3. **恢复与幂等是两份责任**：调度器管触发/并发/failover，但重复投递仍会发生，执行端按业务操作标识核对结果；Checkpoint 用于复用计算避免重算，不保证副作用幂等——外部写入已提交而 Checkpoint 未落盘时，重跑仍会重复。幂等机制按交付语义与外部能力组合选择（唯一键/幂等键/去重账本/outbox-inbox/租约 fencing/对账补偿），无通用必选项。
4. **三组件与九状态**：队列（优先级+FIFO+积压降级）、调度器（负载均衡+租约+背压：并发配额/水位线/速率自适应/租约超时/动态容量）、状态机 waiting→queued→running→终态，加 hold（等审批/输入/外部条件）、skipped、mark_succeeded；失败/终止任务只能由用户手动重跑回 queued。监听用回调为主、轮询/租约兜底、共享存储做权威，信号缺失以权威 Task State 重新对账。
5. **HITL 与触发**：人工介入使任务进 hold（分钟到数天）——内置调度门槛低，外置调度等待期可释放 Worker 但需对接调度 API 与恢复接口；审批回传载荷含 Task ID/审批版本号/授权主体/决策结论并验证未过期未重复。时间触发与事件触发在执行层统一为向队列投递 Task；错过窗口四策略（run_latest/run_all/skip/prompt）按业务语义选，外置 failover 期间业务代码必须幂等。
6. **编排谱系与 DAG 纪律**：自主决策/预定义工作流/Multi-Agent/组合按动态决策需求、路径稳定性、风险、维护成本选；DAG 节点分业务节点与逻辑节点，循环语义靠运行时有界展开（ForEach/Loop+最大迭代），图保持无环；需要带环状态流转（审批驳回回起草）就改用状态机/流程图模型，不把环塞进 DAG。三种边（普通依赖/AND Join/OR Join）里 OR Join 必须显式取消未选分支。引擎三能力：步骤级 Checkpoint 持久恢复、区分计算复用与副作用幂等的局部重跑、可视化运维（重跑/跳过/强制成功留审计）。

## A1（原书案例 + 合成演练）
- 原书实践篇案例（第一手转述）：PatchPilot Agents 内核补丁交付——"先建立工作流，再引入 Agent。没有状态、上下文和回检的 Agent，难以在生产工程中稳定运行……以'是否完成交付'而非'是否完成一次执行'衡量效果"；持久化任务状态管理执行与恢复，交付回检自动创建检测轮次（c-24，效果数字未说明）——完成语义分层与状态持久化的真实落地。PolarDB-X Loop 从报警到自动修复——以"稳定复现"作为修复交付门禁：复现过程固化为测试用例（修复前必触发、修复后必通过+完整回归），研发先审复现证据再审代码；借此修复五年未明根因的 MDL 锁泄漏，Heap Dump 平台累计两千多份处理任务（c-25）——Evidence 判定 Outcome 的门禁实践。
- 合成演练（纸面推演）：财务对账 Agent：每晚 2 点跑、失败需补跑、含人工审核节点、审核驳回回到起草步。推演产出：Task 定义含成功标准引用 Evidence/Verifier（对账差异清零的 Evidence=对账报告）；执行状态 succeeded≠对账差异清零（五层完成语义）；审核等待数小时→外置调度释放 Worker，审批载荷含 Task ID/审批版本号/授权主体/决策结论；审核中进 hold，满足后回 waiting（九状态表）；调度器 failover 重复投递→执行端按业务操作标识核对，Checkpoint 只管复用计算；错过窗口按业务选 run_latest 且 failover 期间业务代码幂等；"驳回回起草"是带环流转→判定改用状态机/流程图模型而非把环塞进 DAG（可核验的分枝决策）。全部输出对照状态转换表与策略清单核验。

## A2（情境应用）
场景：任务要跑几分钟到几天、不能靠一个 HTTP 请求扛住时；判断"任务完成"的标准含糊（进程退出 vs 业务验收）时；定时任务错过窗口要不要补跑时；人工审批期间 Worker 空转烧钱时；选 Agent 自主循环、预定义工作流还是多 Agent 编排时；工作流引擎选型或恢复能力验收时。
语言信号：「任务要跑几小时怎么设计」「进程结束就算完成吗」「定时任务错过了怎么补」「审批期间 Worker 一直占着？」「这个流程有驳回循环，DAG 画不了」「async task / completion semantics / workflow / DAG / scheduler / idempotency」。
区分：ai-gateway 只记账不判完成（网关请求成功≠任务完成的另一半）；state-storage 管 Checkpoint 存储与 Durable Execution 存储侧机制，本卡管任务侧责任划分与状态机；multi-agent-org 管多 Agent 委派与聚合判定，本卡是单任务异步模型（其结论被 U12 复用）；agent-comm 管任务句柄与续传点的交互语义判别，本卡用其结论定义任务模型。

## E（执行步骤）
输入契约：任务定义要素（目标、成功标准与 Evidence 来源、优先级、Agent/池、关联 Session、重试策略、超时、计划时间与业务时间）、人工介入点清单、外部副作用清单（能否幂等）、通知方式约束。缺"成功标准与 Evidence"时不进入实现，先回业务定义。
1. 建六对象权威表：每类信息标注权威所有者与生命周期。完成标准：表覆盖 Task/业务 State/Session/Checkpoint/Runtime State/外部副作用六行，无双重权威。
2. 定完成语义五层：为该 Task 写执行状态口径、运维状态口径、候选证据清单、Evidence（被成功标准引用）、Outcome 判定者与规则。完成标准：Task 定义中成功标准显式引用 Evidence 与 Verifier。
3. 搭三组件与九状态机：队列属性（优先级/FIFO/积压降级）、调度器策略（含背压组合五项）、状态机合法转换（失败/终止只能手动重跑回 queued；hold 满足后回 waiting 或转 skipped）。完成标准：状态转换表无非法边，队列深度入观测。
4. 定恢复与幂等责任：调度器 failover 场景下执行端的核对方式（业务操作标识）；外部副作用按能力组合选幂等机制；新实例重新取得执行权。完成标准：每个副作用动作有幂等手段或人工核对路径。
5. 定触发与错过策略：时间/事件统一投递 Task；定时属性（并发数/阻塞策略/错过策略/时区/发生标识）逐项声明；failover 期间幂等前提写入设计。完成标准：四策略选择记录及理由。
6. 选编排形态并画图：按谱系判断（动态决策需求/路径稳定性/风险/维护成本）；带环流转→状态机/流程图；DAG 则定义节点类型、三种边语义、循环用有界展开。完成标准：图谱+边语义表，OR Join 配取消动作。
7. 验收引擎三能力：步骤级 Checkpoint 恢复演练、局部重跑（计算复用 vs 副作用核对分开验证）、可视化运维操作留审计。完成标准：三项各有一次演练记录。
输出契约：对象权威表、Task 定义模板（含成功标准字段）、状态转换表、幂等责任清单、策略选择记录、编排图。判停：成功标准无法引用任何可核验 Evidence 时，回到业务方澄清，不以模型自述充当 Outcome。

## B（边界）
- 反例（第 2 章，ce-03）：以模型自行宣布完成或进程结束作为任务完成，高风险动作无人监督——完成语义必须由环境证据判定，本卡五层就是防这个。
- 反例（第 22 章，ce-142）：把 API 受理成功当作题目完成——受理与完成是两个语义节点，同步方式调异步 Agent 会评"已受理"而非"已交付"。
- Checkpoint 不是幂等保证（10.1.3）：外部写入已提交而快照未落盘时重跑仍重复；"强制标记成功"只改执行状态并留审计，不能跨层改 Outcome。
- OR Join 不显式取消未选分支会持续消耗资源并产生与下游决策冲突的副作用；默认调度规则与显式汇聚规则要在同一张图里说清，否则"全部完成"与"任一完成即继续"互相矛盾。
- 预定义工作流不消除节点内模型错误、工具开销与失败重试（10.4.1）；工作流节点内部仍可以是完整 Agent 自主循环——不要把"上工作流"当成质量保证。
- 通知方式（Webhook/推送/轮询）、重试参数、轮询频率书中明确按业务定——本卡给结构与选择规则，不给可照抄数值。
- 平台必要性假设（适用边界）：三组件+九状态面向生产级多 Worker 场景。轻量场景（单进程、秒级任务）用数据库状态表+简单轮询即可成立，不必引入完整调度系统；判据是等待时长与恢复要求，不是架构时尚。
- 阿里云产品视角：两个实践篇案例均为阿里内部/客户系统转述（PatchPilot、PolarDB-X），落地机制（交付定义、复现门禁）通用，具体工具链不可平移。
