# 上线前 Agent Simulation（约束不可靠内核 + Scenario Spec + Manifest/Run Result + 证据分层）

## R（原文摘引）
> 它们全部在做同一件事：约束一个不可靠的内核，让错误难以穿过系统抵达病人。（第 16 章 16.1）
> 真正的边界只有两条：不触达未授权的生产账户、数据与网络；不产生不可控的真实业务副作用。（第 16 章 16.2）
> 每个对象替换前问一句：这个对象的行为，是这次要考察的内容，还是这次要设定的条件？是内容则不能替换；是条件则必须替换，并写清楚替换成了什么。（第 16 章 16.2）
> 这条边界让"复现"有了精确含义：用 Manifest 重建条件，用 Run Result 核对事实。（第 16 章 16.3）
> 运行完成、任务成功、允许发布，是三个互相独立的结论，不能相互推导。（第 16 章 16.6.1）
> n 次独立运行零违规，违规率的单侧 95% 置信上界是 1 − 0.05^(1/n)，大样本下近似 3/n。（第 16 章 16.6.2）

## I（解释）
1. **为什么仿真**：医疗系统的可靠不靠保证每个医生每次都对，而靠资质、规程、复盘、模拟器约束不可靠内核；大模型天然就是那个不可靠内核。Agent 还比人类少三样制度前提——角色无外部标准、失败无自然代价、身份不连续——补齐以年计，而"把 Agent 放进可控环境安全地失败一次并留下证据"是当下就能做的那一件。
2. **边界看授权与后果，不看实现方式**：只要不触达未授权的生产账户/数据/网络、不产生不可控真实副作用，连接隔离的真实后端仍是仿真；反之全是软件替身却路由到了生产账户，那是事故不是仿真。执行模式按真实成分分三档（全替身/混合/隔离真实依赖），模式选择取决于验证目标，结论不可跨档混用。
3. **替换的判断准绳**：SUT（推理、工具选择、参数构造、异常处理）是被测内容绝不能替换；其余对象是实验条件，必须替换并记录替换物。把工具调用顺序脚本化是最隐蔽的失效——Run 看起来正常，被测的却是那段脚本，且无任何告警。
4. **数据契约保证复现**：Scenario Spec（声明式场景规格）→ 启动时生成不可变 Manifest（锁定全部资产版本）→ Run → Task/Session → Event（已落地的事实）；Run Result 收拢五类产出，其中 records（原始记录）→ observations（事实观测）→ evidence（面向评价项的证据引用）三层分离——同一份原始材料供评估、合规、回归各自消费，互不污染。计划（triggers/event_specs）与事实（Event）不共享名字。
5. **四维状态防归因纠缠**：执行状态、仿真有效性、证据完整性、任务质量独立记录——一次完整、有效、材料齐备的 Run 完全可能产生错误的业务结果，压成一个"成功/失败"就说不清是环境坏了还是 Agent 错了。
6. **模拟器本身要治理**：用户模拟器三层（Persona/认知状态/行为策略），记错金额的场景里真实状态与用户认知两份都保存；质控五维（角色一致性/反应规则/信息可见性/目标终止/行为分布）——过度配合的模拟器高估 Agent，始终拒绝的产生无意义失败。环境要事实一致（API 返回与数据库同源），超时按请求生命周期分三位置注入各验不同能力；故障注入四步记录（计划→生效→命中→恢复），缺一不可信。
7. **职责与统计纪律**：Harness 五做五不做（不做遥测/评分/发布决策）；运行完成、任务成功、允许发布三个结论互相独立；证据不足输出"不可判定"。零违规结论用置信上界表述（n 次零违规≈违规率不超过 3/n），不是零。仿真假设会过期——仿真成功率上升而生产人工接管增加就是信号，按事件（接口变更/故障复盘/用户结构变化）触发校准而非固定周期。

## A1（原书案例 + 合成演练）
- 原书案例（第 29 章与实践篇转述）：①GOAI 大赛 Agent Infra 赛道 15 项决赛作品全部选择高风险流程（安全处置/生产变更/资金结算等），未规定之处多队一致收敛出五条工程选择，其中两条直接对应本卡：执行者不为自己的结果签字；一次运行留下可回放的完整证据（多数作品尚未进入日常生产，价值在验证工程前提，作者已注明）。②Agentic SOC（亲历）：SOCBench 版本化基线（211 任务/16 场景/9 维度/5 阶段，含 12 道安全测试与噪声题）支撑定位弱项/验证改进/持续回归三职责，发布前缺陷复测 + 独立测试集 + 生产重放 + 灰度。
- 合成演练（按原书规则推演）：退款 Agent 上线前需覆盖"用户记错金额、首次查询超时、提交前撤回"三类情形。写 Scenario Spec 十字段组（sut/user/environment/interaction/events/execution/evaluation_ref/provenance 等）；对每个对象做"内容还是条件"判定（Agent 决策链是内容不可替换；订单查询 API 在全替身模式下是条件，记录替换物）；建用户模拟器（Persona + 认知与真实状态两份 + 反应规则）并定质控五维指标；超时选"已发送未提交"位置注入（检验等待与查询确认）；生成不可变 Manifest 与 Run Result，四维状态独立记录；三道证据检查后交 Evaluation 判定。可核验输出：Spec 十字段齐备且 user.private_facts 与 environment 初始数据为同一订单实体（联合建模）；Run Result 三层分离；执行/有效性/完整性/质量四状态独立呈现；若 300 次零违规，结论表述为"违规率 95% 置信上界≈1%"而非"零"。

## A2（情境应用）
场景：Agent 要接管高风险流程（资金/安全处置/生产变更），上线前需验证行为又不能拿生产试错；模型或 Prompt 升级后要做回归比较证明行为没退化；出过生产事故，要把该情形固化成可重跑的回归场景；要检验 Agent 对超时、撤回、异常输入的应对。
语言信号：「上线前怎么验证 Agent 行为」「不能在生产上试错，怎么办」「怎么搭一个能安全失败的测试环境」「用户模拟器怎么建才像真人」「故障注入注在哪、怎么确认生效」「回归跑 300 次全过能说明什么」；英文 trigger：agent simulation / user simulator / fault injection / reproducibility / regression gate / sandbox testing。
区分（初稿）：observability 是生产侧的遥测与 Trace 语义，本卡是上线前受控环境的行为验证——Run 的遥测采集复用 U15 的语义，Simulation Harness 自己不做遥测；质量评估器选择（规则→Judge→人工）归 U15 与调优篇，本卡只交付证据与仿真有效性检查，判定交给独立 Evaluation；场景提取产出的候选场景要固化进回归集/黄金集需重新验证（衔接调优篇）；环境的会话隔离与网络管控机制归 agent-security 与运行环境设计，本卡只定义仿真对其的依赖。

## E（执行步骤）
输入契约：SUT 边界定义（哪些决策链是被测对象）、上线风险清单（用户行为异常/环境故障/边界操作类型）、可用的隔离环境与脱敏数据、成功标准与独立评价方。缺"SUT 边界"或"隔离环境"时先补——无法隔离生产影响即不具备仿真前提。
1. 判边界与选模式：用两条判据（不触达未授权生产账户/数据/网络；不产生不可控真实副作用）确认仿真成立；按验证目标选执行模式（回归与快速迭代用全替身；端到端集成用混合；服务栈验证与故障实验用隔离真实依赖）。完成标准：每个场景标注模式且注明该模式能支持的结论范围。
2. 场景设计：用户与环境联合建模五维约束（实体绑定/信息可见性/动作入口/事件时序/目标演化——用户嘴里的订单与数据库里的必须是同一张单子）；写 Scenario Spec 十字段组；逐对象做"内容还是条件"判定。完成标准：Spec 十字段齐备；SUT 决策链零替换；每个被替换对象记录替换物。
3. 建模拟器：用户侧三层模型（Persona/认知状态/行为策略，真实状态与认知两份都存）+ 质控五维指标（各定义适用条件与统计单位）；环境侧事实一致（API 与数据库同源）+ 超时按三位置（未发送/已发送未提交/已提交响应丢失）选择注入点；故障注入按四步记录。完成标准：质控指标可核对（拒绝"模拟器准确率 95%"式表述）；故障四步证据齐备。
4. 执行与记录：启动生成不可变 Manifest（锁定场景与全部资产版本组合）；Run 产出按 records/observations/evidence 三层分离；执行/有效性/完整性/质量四维状态独立记录；两张账协调（事件联动账 + 业务日历/仿真逻辑/单调时钟/墙钟四种时间分离）。完成标准：复现语义成立——用 Manifest 重建条件、用 Run Result 核对事实。
5. 证据交付：Simulation 侧完成有效性检查（场景配置正确/用户行为守规/故障生效并命中/必需证据可访问）；评估侧做三道证据可用性检查（记录完整性/运行有效性/证据充分性），不足项输出"不可判定"。完成标准：结论按统计纪律表述——n 次零违规写作"违规率 95% 置信上界≈3/n"，不写"零"。
输出契约：Scenario Spec 集 + Manifest + Run Result（三层分离 + 四维状态）+ 证据包（支撑评估/归因/回归/回放等用途）+ 结论报告。判停：场景材料只有事故表象未经事实核实时不直接固化（"未确诊的病历不能直接开成处方"）；仿真成功率上升而生产人工接管增加时停下校准假设。

## B（边界）
- 全替身模式下的回归通过不构成对真实依赖栈的任何结论（16.2）：模式结论不可混用；"未产生副作用"不等于完成了端到端验证（调优篇 ce-124 同向警告）。
- 把工具调用脚本化是最隐蔽的失效（16.2）：被测对象被移出回路且无告警——这道"内容还是条件"判断属于场景设计，没有工具能代劳。
- 复现纪律反例：把场景里的未来计划叫 Event 是最易犯的命名错（计划在等待、事实已落地）；把生产事故表象直接抄成场景等于未确诊病历直接开处方——先核实事实与责任归属再固化进回归集。
- 统计误读（16.6.2）：置信上界不是"真实违规率有 95% 概率低于该值"（混淆频率学派置信区间与后验概率）；前提是固定样本量、独立同分布、无非选择性排除。
- 模拟器质量反例（16.4.2）：过度配合的模拟器高估 Agent 能力，始终拒绝的产生无意义失败；生成与评分用同一模型会引入共同偏差。
- 假设过期与替代幻觉（16.6.3）：仿真用户不是真实用户、场景来自已知失败模式（覆盖不了未知风险）；Simulation 与生产可观测、安全框架、资产治理互补而非替代——仿真成功率不能替代真实业务指标。
- 职责边界：Harness 不做任务生命周期管理、鉴权、遥测采集、质量评分、发布决策——把任何一项收进来就从执行引擎膨胀为总控制器；Testing Gate 汇总证据但不是发布决定者；回放不保证模型逐字复现，只能重建输入条件。
