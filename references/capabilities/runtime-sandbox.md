# 沙箱与 Agent Runtime（环境契约 + 隔离分级 + 等待分档 + 接管围栏）

## R（原文摘引）
> Agent use sandbox 表示 Agent 的编排逻辑位于沙箱外，通过接口调用其中的代码、浏览器或其他工具；Agent in sandbox 表示 Agent 进程和主要工具链共同运行在沙箱内。（第 7 章 7.1.2）
> Harness 编排层持有任务目标、上下文和下一步决策……Agent Runtime 负责把任务组织成可启动、可等待、可取消和可恢复的运行过程……Sandbox 提供具体的计算与工具环境。（第 7 章 7.6.1）
> 后端选择取决于运行代码的可信程度、租户边界、操作系统能力、设备需求和运维成本。对外提供 SDK 或 Kubernetes 接口，并不能单独说明底层隔离强度。（第 7 章 7.6.2）
> 唤醒入口位于休眠沙箱之外。定时器、消息入口或请求路由组件先接收事件，再恢复环境并交付任务；休眠中的 Agent 自身不继续执行任务循环。（第 7 章 7.3.3）
> 平台可以用执行代次区分接管前后两次执行，并由受保护的存储或写入入口拒绝旧代次，这类机制通常称为围栏。（第 7 章 7.3.4）
> 试点阶段应明确任务的环境契约：使用哪个模板、挂载哪些数据、保留哪些状态、依据什么验收产物，以及何时释放资源。（第 7 章 7.7.3）
> 沙箱的首次可用时延应从环境申请开始计算，直到命令通道、依赖、工作区和所需服务全部就绪。……CPU 使用率较低不能单独作为回收依据。（第 7 章 7.5.1/7.5.3）

## I（解释）
1. **先分负载，再谈选型**：按 Agent 与沙箱的部署关系分三类典型负载——编排在外（use）、进程在内（in）、训练评测（RL-Eval），分别对应工具执行的时延与隔离、长任务的连续性与恢复、评测的吞吐与可复现。环境类型按任务产物选：Code / Browser / Computer / AIO 共享工作区 / MCP-Skill 环境；跨工具任务用共享工作区衔接，共享范围与任务/租户边界匹配。
2. **三层职责是边界不是三个服务**：Harness 掌任务语义（何时调工具、何时结束），Runtime 管可启动/可等待/可取消/可恢复的运行过程，Sandbox 供计算与工具环境。无论怎么部署，编排层都应掌握任务语义，平台不得凭进程存活猜任务完成。
3. **环境契约是第一交付物**：模板、挂载、保留、验收、释放五要素写清，短任务从"按需创建+明确清理"起步，每新增机制（会话亲和、休眠、预热、快照分叉）都必须对应一个已观察到的运行问题。
4. **等待期按保留内容分四档**：持续运行 / 浅暂停留内存 / 深休眠持久化释放 / 只留文件重建进程。按完整任务周期评估：长保留短执行的任务从降等待占用获益，频繁短等待反而被保存/恢复开销拖慢。判断能否休眠不能只看"没有新请求"，还要查在运行工作与未完成操作；唤醒入口必须在休眠体之外。
5. **隔离看判断变量，不看接口形式**：容器/用户态内核/MicroVM 按代码可信度、租户边界、OS 能力、设备需求、运维成本选；SDK 与 K8s 双入口可指同一底座，同名参数在不同实现中支持范围可能不同，迁移前用代表性任务过完整生命周期。开放范围靠出口代理、短期凭证、资源限额与独立工作区收敛。
6. **接管与验收有硬机制**：实例故障先分类（环境故障 vs 依赖故障），接管前用执行代次围栏拒绝旧实例写入，外部操作按原标识核对后才能续行；恢复完成以"任务能从已有成果继续推进"为准。首次可用时延从申请计到通道/依赖/工作区/服务全就绪，冷启动与预热分开记；上线前过五类故障场景验证。

## A1（原书案例 + 合成演练）
- 原书实践篇案例（转述）：信永中和会计师事务所引入 AgentCore 多智能体平台与 AI 网关，一周完成联调上线，形成统一入口与四类办公 Agent（第 25-28 章实践篇，c-35）——佐证"Runtime 平台化托管 + 统一入口"的接入路径，案例未说明沙箱隔离后端与时延数据。Agentic SOC 以 211 个安全调查任务构成版本化基线驱动 Agent 研发（c-27）——佐证"运行环境支撑可复现的任务循环"，沙箱机制本身未展开。
- 原书机制示例（转述）：第 7 章在 7.3-7.7 给出的休眠唤醒、执行代次围栏、Template/Snapshot/Fork/Reset、单位成功任务成本等均为机制叙述与构造情境，书中声明具体阈值"需按自身负载设定"，未给实测数值。
- 合成演练（纸面推演，非实测）：编码 Agent 日均 300 次任务、单任务 6 分钟（含 2 分钟等用户确认）、执行模型生成的不可信代码、团队有 K8s 运维能力。推演产出：负载=Agent use sandbox（编排在外）；环境=Code+AIO（下载-计算-生成-预览连续任务共享工作区）；等待期四档评估→长保留短执行选深休眠，唤醒入口放沙箱外路由层；隔离后端按五判断变量逐项打分→不可信代码+租户边界→MicroVM 或用户态内核；入口=K8s（但模板/超时/暂停恢复/网络/持久化/错误处理逐项验证同名参数）；时延口径=申请→命令通道/依赖/工作区/服务全就绪，冷启动与预热分记；上线前跑五类故障场景（实例退出/挂载失败/旧实例失联重现/等待期取消/新版本恢复旧任务），通过标准由企业定义。每项可对照候选清单核验。

## A2（情境应用）
场景：给会执行生成代码或不可信内容的 Agent 选运行环境时；长任务在等用户/等外部事件期间资源成本过高时；执行实例挂掉后要保证任务不断、旧实例不双写时；沙箱/平台上线前做验收时；评估"该用 SDK 还是 K8s、容器还是 MicroVM"时。
语言信号：「Agent 要跑生成的代码，怎么隔离」「沙箱怎么选，容器够不够」「任务等确认的时候环境还一直计费吗」「实例挂了任务怎么接管、会不会两个实例同时写」「sandbox / runtime / isolation / cold start / hibernation / fencing」。
区分：state-storage 管"状态放哪里"（Event Log/Checkpoint/工作区存储）；本卡管"执行环境怎么供给、隔离、等待、接管与回收"。async-completion 管任务模型与完成语义，本卡只提供其执行底座（等待期策略与唤醒入口）。ai-gateway 管流量准入，不管环境生命周期。

## E（执行步骤）
输入契约：任务负载画像（编排位置、单任务时长、等待占比、产物类型）、执行代码可信度、租户边界要求、团队运维能力（有无 K8s/平台团队）、成本与时延约束。缺"代码可信度"或"租户边界"时应先询问，不能静默假设为可信。
1. 分类负载与选环境类型：按 use/in/RL-Eval 归类，按任务产物选 Code/Browser/Computer/AIO/MCP-Skill。完成标准：负载-环境映射表，每行注明首要价值（时延/连续性/吞吐复现）。
2. 交付环境契约：每类任务写五要素——模板、挂载、保留、验收、释放。完成标准：五要素无空项，验收产物可指认（文件/测试/报告）。
3. 选隔离后端与入口：按可信度/租户边界/OS 能力/设备需求/运维成本逐项打分选容器/用户态内核/MicroVM；入口按团队形态选 SDK 或 K8s，同名参数列差异清单。完成标准：决策记录含五变量结论 + 待验证参数清单。
4. 设计等待期与连续性：按四档评估等待策略（用完整任务周期算账），配置会话亲和+动态挂载双映射，唤醒入口外置，休眠前保存继续点与等待条件。完成标准：等待策略表 + 恢复后重检清单（文件/连接/凭证/端口）。
5. 定故障接管流程：环境故障 vs 依赖故障分诊→确认旧实例停止或失效其写权→执行代次围栏→外部操作按原标识核对→从已有成果续行。完成标准：接管 runbook，含"恢复成功"判据（任务可续推，非接口成功）。
6. 定基线与上线验证：首次可用时延（申请→全就绪，冷启动/预热分记）+ 单位成功任务成本 = 窗口内归属费用 ÷ 成功任务数（失败与重试计入）；上线前执行五类故障场景验证。完成标准：基线报告 + 五场景验证结论（通过标准由企业预定义）。
输出契约：负载映射表、环境契约、选型决策记录、等待策略表、接管 runbook、基线与验证报告。判停：无法定义验收产物或无代表任务可测时，先回任务定义，不做选型。

## B（边界）
- 反例（第 14 章 14.6.3/14.6.4，ce-69/70/71）：Agent 运行环境不按不可信负载做会话级隔离——多任务共享同一沙箱与凭据、空闲环境不回收、出站默认允许、未封禁云元数据端点，残留凭据与横向跳板是真实失效模式。
- 反例（第 2 章，ce-08）：编排层直接依赖 Runtime 的内存结构/函数调用细节，导致 Runtime 无法替换、任务无法跨实例恢复——接口必须是任务与状态。
- 接口形式不说明隔离强度（7.6.2）：提供 SDK 或 K8s 接口≠底层隔离达标；同名参数在不同实现中支持范围不同，须逐项验证后才能宣称可迁移。
- CPU 使用率低不能单独作为回收依据（7.5.3）；回收与扩容共同决定容量，缩容先停新工作再等在途任务到可恢复点。
- 快照边界：沙箱快照不自动回退外部数据库、已发消息或已完成的业务操作——外部副作用的补偿归业务规则与幂等，不归沙箱（工作区/产物存储的快照语义见 state-storage）。
- 平台必要性假设（适用边界）：原书以多租户平台视角叙述（三平面、预热池、配额）。单团队小规模场景"平台"可退化为容器+脚本+明确清理，按需加机制；不要为照搬架构引入无人观测的复杂度。
- 阿里云产品视角：实践篇案例与部分示例隐含阿里云产品语境（托管沙箱、AgentCore），吸收的是机制与验收方法；具体产品能力、参数支持范围需自行验证，不因案例成功等同选型结论。
- 休眠阈值、保留期限、时延目标书中均未给数值，声明"需按自身负载设定"——本卡输出的是口径与检查表，不是可照抄的参数。
