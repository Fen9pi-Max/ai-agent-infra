# 多 Agent 团队与编排（收益成本判据 + 三拓扑 + 三层聚合 + 权限交集）

## R（原文摘引）
> 只有当专业分工、并行执行、故障隔离和过程治理带来的收益，能够覆盖沟通与协调成本时，Agent 团队才真正具有价值。（第 11 章 11.1.4）
> 主管—执行、对等协作和分层编排，是对决策、委派和汇报关系的不同安排。它们不是从低级到高级的演进阶段，而应根据实际工作特点选择。（第 11 章 11.3.2-11.3.4）
> 团队级停止条件需要在根 Task 开始前约定，包括总体时间或成本预算、最大委派深度、派生任务数量、单项任务的重试次数、结果返工轮次……（第 11 章 11.4.3）
> 执行者提交结果，表示候选成果已经产生；Leader 或指定审核成员接受子任务结果，表示它具备继续用于下游工作的条件；根 Task 达到完成条件……三者相关，但不能互相替代。（第 11 章 11.4.4）
> 团队共享的是上下文来源，而不是完全相同的 Context。……这种选择应遵循"最小充分"原则。（第 11 章 11.5.1）
> "主体"回答谁在行动，"委托授权"回答主体为什么可以代表他人行动，"凭证"只是主体向目标系统证明身份或权限的载体。（第 11 章 11.7.1）

## I（解释）
1. **组队先过账**：单 Agent 上下文集中、链路简单，适合范围明确、强串行任务。团队要算收益（专业分工、并行、故障隔离、过程治理）是否盖过成本（拆分、信息传递、共享状态一致性、更多调用与开销）。多个 Agent 能互调不等于团队——团队需要共同目标、明确分工、可持续追踪的过程与可验证的结果。
2. **编排层管边界不管细节**：把目标转成可验收任务、建依赖、汇集状态与产物；若所有信息都汇到一个主管再逐步决策，系统退回单点，主管成为新的上下文与执行瓶颈。成员在能力范围内自选执行方式，协作过程显式记录，连续性不依赖某个 Agent 常在线。
3. **接入按可控范围三选，并做五项检查**：能改代码→协作 SDK/任务接口；能装插件→插件+适配；只能调 API→外部适配并记录远端任务编号。个人工作区 Agent 接入的是运行实例而非用户会话，团队任务用个人工具须用户明确选择。接入后用一次小任务过五项：到达/连续交互/状态反馈/成果交付/控制恢复——"能互调"与"是团队"由此区分。
4. **拓扑三选非升级**：主管—执行（交付物/负责人/依赖清楚时放行执行者）、对等协作（须预约定分歧解决与最终交付责任）、分层编排（小组能承担完整交付责任时加层才有意义）。能力与角色分离：擅长≠负责，同一 Agent 可在不同团队承担不同角色。
5. **过程四阶段 + 双保险**：任务定义（Task/Subtask/Task Run 分层，只有独立交付/不同责任/明确依赖才拆）→计划制定（保留有效进展而非覆盖重建）→调度执行（按 Task State 调度，通知只是提醒）→结果聚合。双保险：根 Task 前约定团队级停止条件（总预算/最大委派深度/派生任务数/重试次数/返工轮次），聚合按提交→接受→根完成三层判定，"已完成"非终态、内部接受≠业务验收。
6. **信息与安全底座**：共享上下文来源而非相同 Context，按最小充分裁剪，Handoff 交接四类（目标/已知事实/待办/引用），完整搜索过程与未验证推理不传；团队记忆验证后才沉淀并带来源边界；消息说"发生了什么"、Task State 与 Artifact 记"当前事实是什么"。身份三分离（主体/委托/凭证），有效权限取人员权限∩团队边界∩Agent 策略∩资源策略∩委托范围，入站出站分开；长程任务跨多条 Trace，用 Span Links 保留真实因果。

## A1（原书案例 + 合成演练）
- 原书调研与实践案例（转述）：2026 调研（1906 份问卷）——多 Agent 协作最大痛点为状态与上下文衰减（60%），其次死锁雪崩与成本失控；最盼端侧与开源运行底座（73%）、研发-测试闭环（65%）（c-08）——团队级风险与信息模型的实证。多 Agent 研发小队：15 个面向工序的 Agent 组成能力池，AgentCore 作 Leader 按任务状态调度；Coding Loop 两层回环（内层"代码能不能跑"、外层"方案是不是对"），Produce/Verify 分离（作者与 Judge 独立会话），分级验证连续不收敛转 Human Gate；24 道基线题中 19 道新题盲测：10 等价/5 接近/4 部分完成/0 方向错误，在线交付约一周（作者自注样本量小）（c-28）——拓扑、聚合判定与验证分工的真实运行。
- 合成演练（纸面推演）：季度竞品报告团队：调研 Agent（本地个人工作区）+数据分析 Agent（平台托管）+撰写 Agent+主管。推演产出：先用收益成本判据列量化对照表（专业分工+并行收益 vs 拆分/传递/一致性成本）→判定组队；调研 Agent 按可控范围选外部适配接入且不自动继承个人目录权限；接入后一次小任务过五项检查；拓扑选主管—执行并在交付物负责人依赖清楚时放行；停止条件参数（总预算/最大委派深度 2/返工 2 轮）写进根 Task；聚合按提交→接受→根完成三层判定，"已完成"非终态；共享上下文按最小充分+Handoff 四类裁剪；权限=角色∩团队边界∩Agent 策略∩资源∩委托；跨 Trace 用 Span Links 关联。各输出对照检查项核验。

## A2（情境应用）
场景：纠结一个 Agent 还是拆成多个时；要接入异构/他人开发的 Agent 协作时；设计团队分工与主管/对等/分层结构时；多 Agent 委派或返工失控、成本雪崩时；团队级权限与审计责任设计时。
语言信号：「要不要拆成多个 Agent」「这几个 Agent 怎么分工」「主管 Agent 会不会成瓶颈」「委派越派越多怎么办」「Agent 之间交接要传什么」「multi-agent / team topology / orchestration / delegation / handoff」。
区分：async-completion 是单任务异步模型，本卡管"谁委派给谁、结果怎么聚合判定"；agent-comm 管协作双方的传输与交互语义选型（协议、通道），本卡管协作秩序（路由规则、消息/状态分工）；state-storage 管各对象存储承载，本卡的六对象信息模型消费其分层结论；ai-gateway 管单点流量治理，本卡权限模型与它互补但不重复。

## E（执行步骤）
输入契约：根任务目标与范围、候选成员能力清单（含可控范围：代码/插件/仅 API）、风险与预算约束、可参与的人（角色）、验收标准。缺"验收标准"或"预算约束"时不进入分工设计。
1. 判定单/多：列收益侧（分工/并行/隔离/治理）与成本侧（拆分/传递/一致性/调用开销）对照表。完成标准：判定结论附量化或半量化对照，不凭直觉。
2. 接入成员：每个成员按可控范围三选定接入方式，写适配层与能力边界（能反馈什么、接受哪些控制）；个人工作区成员明确资源使用范围。完成标准：成员清单含接入方式与边界声明。
3. 五项接入检查：用一次小范围任务验证到达/连续交互/状态反馈/成果交付/控制恢复。完成标准：五项各有结论，未过项有整改动作。
4. 选拓扑与角色：按决策/委派/汇报关系三选拓扑，角色与能力分离记录（可自主决定什么/交付什么/何时寻求协调）。完成标准：团队结构图+角色表，注明选择理由。
5. 定协作过程：Task/Subtask/Task Run 分层与拆分判据、计划节点与执行顺序分离、失败关联子任务并核对版本。完成标准：任务层次模板+拆分判据清单。
6. 定停止条件与聚合：停止条件参数写进根 Task（触顶后暂停新委派与自动返工、保留结果与阻塞、标记等待人工）；聚合三层判定规则与最终交付说明。完成标准：参数表+三层判定规则成文。
7. 定信息与安全底座：共享上下文最小充分清单、Handoff 四类模板、团队记忆沉淀门槛（验证后+来源边界）；身份三分离与权限交集规则、入站/出站分离；观测用 Span Links 关联 teamId/taskId/taskRunId。完成标准：信息分工表+权限模型+观测关联方案。
输出契约：判定对照表、成员接入清单、五项检查结论、团队结构与角色表、停止条件参数、聚合判定规则、信息与权限方案。判停：验收标准缺失或无人可承担最终交付责任时，回到任务定义，不组队。

## B（边界）
- 过度组队是反模式：收益成本判据是红线——范围明确、上下文关联紧密、步骤强串行的任务用单 Agent；拆分粒度只有定性判据（独立交付/不同责任/明确依赖），不满足任一条就不拆子任务。
- 主管瓶颈：所有信息汇总到一个主管再逐步决策等于回到单点模式；交付物、负责人、依赖清楚时即应放行执行者（11.3）。
- 反例（第 11 章，ce-45/47/49）：Agent 持有或复用用户长期凭证、入站可访问默认换取出站全部资源、交接时全量传递上下文与凭证导致权限扩大——有效权限取交集，交接只给双方均被允许的最小范围。
- 反例（第 11 章，ce-46/50）：权限只在入口检查一次（长任务中委托过期仍继续访问）；把动态执行图强简化成一棵调用树（因果失真，须用 Span Links）。
- 团队记忆≠共用向量库：未经验证的假设与临时判断直接入长期记忆会被当事实反复引用；沉淀须带来源、验证方式、适用边界与时效。
- 个人工作区边界：仅设目录参数挡不住访问其他文件，限制由权限控制或沙箱实施；本地执行不等于数据留本机。
- 平台必要性假设（适用边界）：第 11 章默认平台托管团队的治理设施（注册、审计、Span Links）。无平台时用共享任务表+约定通道降级实现，判据仍是五项检查与三层聚合，不是设施齐全度。
- 阿里云产品视角：实践篇案例（研发小队、AgentCore）为阿里系转述，机制（Leader 调度、Produce/Verify 分离、盲测基线）通用，平台名仅为出处语境；调研数据为 2026 时点自评，作方向证据不作精确基准。
