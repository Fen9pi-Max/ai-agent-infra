# Harness 构建入口选择（契约先行 + 四判据四入口 + 企业保留责任清单）

## R（原文摘引）
> 构建 Agent 不能从选择框架或打开工具开始，而应先固定任务契约（Agent Contract）。（第 3 章 3.1.2）
> 它们最显著的差异，不是模型能力，也不是应用形态，而是 Harness 的通用行为由谁实现，Runtime 与 Sandbox 由谁提供，以及企业应用需要补齐哪些控制和验收责任。（第 3 章 3.1.3）
> 四类构建入口不是成熟度高低关系，也不必互斥。企业应根据任务结构、定制深度、数据边界、环境影响、团队能力和交付方式选择最低充分方案。（第 3 章 3.7）
> 平台可以推进基础 Harness、执行工具并产生 Event，但不能替企业定义业务正确性。（第 3 章 3.4.3）
> 托管越多，企业越应把工具、数据、权限和成功标准定义清楚，否则只是把不明确的 Agent 行为转移到了云端。（第 3 章 3.4.4）

## I（解释）
1. **契约先行**：构建顺序是先固定任务契约再选实现——契约回答为谁工作、接受什么输入、交付什么结果、允许影响哪些系统、哪些动作必须拒绝或审批、什么证据证明完成。同一目标（修复高危漏洞）按契约不同可以是"只出报告""隔离环境修改+测试"或"创建合并请求"。
2. **四判据选四入口**：定制深度（是否须改 Loop/Context）、数据边界（环境可否托管）、运行责任（谁维护状态恢复与 Sandbox）、交付方式（个人工作区/嵌入式应用/异步任务服务/平台内 Agent），对四类入口打分——高代码框架（控制最大、自担生产六责任）/产品化 Harness/SDK（复用执行、自担多租户与验收）/Managed Agent（托管 Harness+Session+隔离）/云产品（预置资源、自担业务 Task 与权限边界）。
3. **入口非阶梯、可组合**：四类入口不是自建→半托管→全托管的成熟度阶梯，同一企业可混用多入口再由平台统一纳管（纳管三条件：版本归属可追溯、Event/Artifact/Trace 关联 Task/Identity/Tenant、远程 Agent 提供可验收证据而非自然语言结论）。
4. **责任不可托管**：平台推进执行与产生 Event，但发布权、验收权、知识可见性、记忆可写性始终在企业。各入口下的集成模式是稳定机制：SDK 预授权+审批回调、托管四对象五步、SSE 事件续接、云产品契约反推资源、发布状态≠业务完成。
5. **八对象责任人表**：Agent Contract/Execution/Context&State/Capability/Environment/Control/Interaction/Quality 八个构建对象，进入生产后每个都必须有明确责任人——最小 Agent 可只实现部分，问题不能没有责任人。

## A1（原书案例 + 合成演练）
- 原书·契约示例（3.1.2，转述）：同一"修复高危漏洞"目标，按契约不同构成"只出报告""隔离环境修改+测试""创建合并请求"三种 Agent；除非契约明确授予发布权限并规定审批条件，Agent 不应把修复完成解释为已发布。
- 原书·实践案例：PatchPilot 内核补丁交付——先建立工作流，再引入 Agent，"没有状态、上下文和回检的 Agent 难以在生产工程中稳定运行"（c-24）；Kitta 领域定制 Code Review 走高代码自建路径，7 万+补丁、门禁准确率 97%（c-23）；信永中和引入 AgentCore 多智能体平台 + AI 网关，一周联调上线——托管/平台路径的典型（c-35）。
- 合成演练（纸面推演，非原书案例）：客服 Agent，数据不出私域、6 人团队无平台团队、交付为嵌入现有工作台的异步任务。四判据打分：定制深度=中高（需改工单 Context 组装）→ 排除纯云产品；数据边界=私域 → 排除全托管执行面；运行责任=不自维护 Sandbox → 排除高代码全自担；交付=嵌入式异步任务 → 入口=产品化 Harness/SDK 嵌入 + Workflow 引擎承载 FAQ（入口可组合）；再按八对象逐一指定责任人，无空位。

## A2（情境应用）
场景：项目要开工、争论"用什么框架/平台搭"时；决定自建还是用托管/云产品时；接入 SDK 嵌入业务应用时；多来源 Agent 要统一纳管时。
语言信号：「LangGraph 还是 Claude Code SDK 还是直接用平台」「自建还是托管 build vs buy」「用云控制台拖一个行不行」「平台能帮我们兜底什么」「harness / framework / managed agent / SDK 集成」。
区分：arch-selection 先回答要不要 Agent、什么形态成熟度，本卡在其后回答"由谁实现、责任怎么分"；审批决策框架（ALLOW/DENY/ASK、HITL 层次）归 action-plane，本卡只管审批回调的入口集成模式（SDK 嵌入时审批责任留企业）；状态逻辑分层（Call/Session/Task 存储）归 state-layering，本卡只管各入口下状态外置的路径责任。

## E（执行步骤）
输入契约：任务契约（来自 arch-selection 的形态决策 + 目标/输入输出/允许禁止动作/完成证据）、数据边界与合规要求、团队规模与维护意愿、交付对象形态、候选入口清单。
1. 固定任务契约：写出为谁工作/输入输出/允许影响哪些系统/必须拒绝或审批的动作/完成证据。完成标准：六要素齐备且可被非本项目成员复述。
2. 四判据打分：定制深度、数据边界、运行责任、交付方式逐项判高中低。完成标准：每判据一句证据；判据冲突时按数据边界优先（不可托管则排除对应入口）。
3. 对照入口选型：按判据映射入口组合（可多入口组合，Workflow 引擎与 Agent 入口不互斥）。完成标准：入口→判据映射逐项可复核，无"按团队偏好"式理由。
4. 八对象责任人表：Agent Contract/Execution/Context&State/Capability/Environment/Control/Interaction/Quality 逐对象标注"入口提供/企业自建/共同"。完成标准：无空位对象。
5. 企业保留责任清单：按入口类型列必留项（多租户隔离、审批后端决策、Outcome 独立验收、task_id↔session_id 映射、四组概念区分 Task/Session、Event/Trace、Artifact/Outcome 与六类要素版本化承诺）。完成标准：每项有责任人与验收方式。
输出契约：入口决策 + 责任人矩阵 + 企业保留责任清单 + 集成模式要点（审批回调/事件续接/契约反推资源）。判停：任务契约未定（目标或完成证据缺失）时先回 arch-selection 补契约，不先选工具。

## B（边界）
- 反场景：纯个人脚本/一次性原型无需此决策流程，直接最轻入口即可；已选定入口且无新增任务类型时不重开选型。
- 最贵误判有二：把入口当成熟度阶梯（3.5.1 明确否定——云产品不是"低级"、高代码不是"高级"）；以为托管平台会替企业决定知识可见性与 Skill 授权（ce-27：托管转移的是 Session 与执行基础的运行责任，不是业务数据边界与资产授权）。
- 功能可用 ≠ 生产责任满足（3.3.3）：文档明示后台 Subagent 不可恢复、Sandbox 未启用约束时不自动隔离——接入产品化 Harness 须逐项确认并发/恢复/保留/审计语义；共享部署不构成强多租户边界。
- 云产品快速构建 ≠ 用可视化页面替代工程设计（3.5.1）：业务目标、任务状态、数据边界、工具授权和 Outcome 标准仍由企业定义。
- 具名时效（进 B 不进机制）：canUseTool/allowedTools/Last-Event-ID/stop_reason.requires_action 等 SDK API 名、Environment-Session-Event 托管对象模型、AgentScope/QwenPaw Hub 等产品名随版本演进，吸收时以机制对应（预授权+回调审批、事件幂等续接、idle≠完成），不按产品名照抄。
- 适用边界（原书视角）：手册由阿里云出品，Managed/云产品入口的例证与其产品线对齐，评估时以"平台不定义业务正确性"的机制校准，不预设某厂商产品的责任边界。
