# Agent 状态存储分层选型（四类状态 × 正确性边界 × 物理承载）

## R（原文摘引）
> 从数据形态看，Agent 的状态不是单一对象，而是一组生命周期、访问方式和一致性要求各不相同的数据集合。（第 8 章 8.1.2）
> 正确的起点不是先选择某一种引擎，而是先定义不同状态对象的正确性边界，再为其匹配相应的存储能力。（第 8 章 8.1.3）
> 一个有效的 Checkpoint 不应只是模型上下文的简单拷贝，而应包含恢复所需的关键状态：当前任务阶段、已完成步骤、未完成步骤、工具调用结果引用、工作区版本、子任务状态、等待条件以及状态版本。（第 8 章 8.2.3）
> 只有持有最新接力棒的实例才能提交下一次状态变化；旧实例即使仍在运行，也不能覆盖新的执行结果。（第 8 章 8.2.4）
> 语义检索若先跨租户召回、再过滤结果，可能已在候选生成阶段引入不必要的数据暴露风险。因此，平台应在索引空间、检索条件和重排序策略中前置租户与权限约束。（第 8 章 8.7.1）
> 关键状态能否原子提交，产物引用是否稳定，知识和记忆的权限撤回是否及时，各层能否独立备份与恢复，以及数据是否能够完整导出。（第 8 章 8.7.5）
> 参考架构以两个独立的正交维度组织长期记忆，避免把"来源"与"稳定性"混为同一分类轴。（第 8 章 8.4.2）

## I（解释）
1. **选型顺序倒过来**：不是先挑数据库，而是先把状态对象分四类——运行时状态（事件日志/检查点/租约/状态指针）、工作区与产物、记忆与知识、业务语义与治理状态——再逐对象定义正确性边界（顺序、原子、幂等、可回滚、可检索、可审计），最后匹配物理承载。误配的后果是具体的：任务事实当可检索文本会丢顺序与原子性，成果当无版本附件难回滚，记忆与权限混同让越权内容持续影响决策。
2. **运行时状态三件套**：Event Log 只追加记录有业务意义的动作，强一致边界收敛到任务/会话级（不是全局日志），事件与状态同事务或走 Outbox；Checkpoint 按七要素保存（上下文拷贝不算），在五个关键边界主动打（外部调用前后/长计算后/人工确认前后/工作区变更后/交接时）；Durable Execution = 读最新 Checkpoint + 回放其后事件 + 执行租约 + 状态指针——执行实例可替换，任务事实在外部持久化。
3. **工作区分层、产物不可变**：共享不变部分（只读基础层）、隔离变化部分（任务独占可写层）；CoW 快照支持试验/回滚/分支，但环境回滚不撤销外部副作用；多 Agent 不共写同一目录，各自写私有分支、经快照或 Artifact 引用读取；进 Artifact Store 的成果带八项元数据且不再原地修改。
4. **记忆与知识是两套治理**：记忆按来源（用户表达/Agent 归纳/业务事实）× 稳定性（人设/画像/事件偏好）双正交分层，写入以"对后续交互有预测价值"为门槛，三路召回+Rerank，遗忘分归档/降权/删除三级且删除要清派生链；知识库走受控边界检索（RAG 语义相似、GraphRAG 按验证过的路由规则、DataProbe 只读账号+授权 Schema），权限过滤覆盖检索到生成全链路、答案可溯源到文档段落版本。Persona 由治理方显式维护，不作经验性记忆。
5. **平台级横切**：多租户隔离三层组合（物理/逻辑/行级）且权限前置到索引空间；一致性分级——权威事实先可靠提交、派生视图最终一致但知道新鲜度；统一元数据+血缘让源变更可追踪；成本按数据价值冷热分层、保留期显式化、减少无效复制。
6. **验收与恢复是收口**：选型按五问验收（原子提交/引用稳定/权限撤回及时/独立备份恢复/完整导出），落到实际任务与故障场景而非产品名称；关键业务恢复走五步：定位最后已确认事件→加载检查点→校验租约与幂等→确认外部调用状态→决定继续/重试/补偿/转人工，并持续演练。

## A1（原书案例 + 合成演练）
- 原书实践篇案例（转述）：MiniMax 全系产品的记忆数据底座——星野日均新增数亿条、超百 TB，大字段使传统库在 10 亿行后性能急剧下降；以分布式多主+Serverless 弹性+冷热分层+大字段优化承载长期记忆，读写性能 +3 倍、存储成本 -75%（第 25-28 章实践篇，c-34）——佐证"记忆类状态单独选型承载 + 冷热分层收益"，属阿里云客户报告，数字为产品语境。B 站以 PolarDB for AI 节点在库内完成实体挂靠推理，"数据不出库"（c-36）——佐证结构化事实与知识的承载边界受控，ROI 未说明。
- 合成演练（纸面推演）：跨境电商客服 Agent，任务跨 3 天、含人工退货审批、需记用户偏好、查订单库与产品知识库。产出：四类状态地图（运行时/工作区产物/记忆知识/治理）→ 逐对象正确性边界表（误配后果对照）→ Event Log 边界=任务、事件与状态同事务（Outbox 兜底）→ Checkpoint 在"人工确认前后"边界保存七要素 → 恢复=最新快照+回放+租约围栏 → 退货报告=Artifact 带八项元数据不可变 → 偏好=记忆按来源×稳定性落层、写入先判预测价值、冲突保留待确认 → 订单事实=DataProbe 只读账号+授权 Schema → 本体引入判定：订单实体身份与多跳查询是持续需求→引入 → 多租户=逻辑隔离+语义检索前置权限 → 权威事实强一致/向量索引最终一致知新鲜度 → 选型五问逐项过 → 恢复五步演练。每项可对照清单核验。

## A2（情境应用）
场景：Agent 要外置状态（恢复、多实例、多 Agent 共享）却不知放哪里时；压缩/断线后任务事实丢失或被摘要改变时；记忆库和知识库混在一个向量库治理不动时；为 Checkpoint 存什么、多久打一次纠结时；多租户数据隔离与成本治理设计时；做"组件组合 vs 一体化 Agent 数据库"决策时。
语言信号：「Agent 的状态到底存哪里」「上下文一压缩任务就变了」「checkpoint 该存什么」「记忆和知识库能放一起吗」「租户数据怎么隔离」「state storage / event log / checkpoint / memory vs knowledge / multi-tenant」。
区分：runtime-sandbox 管执行环境的供给与接管（本卡的 Checkpoint 会被其恢复流程引用）；async-completion 管异步任务模型与完成语义——本卡的 Durable Execution 是存储侧机制，任务侧责任划分（调度器/执行端/幂等组合）在彼处；multi-agent-org 从团队视角消费六对象信息模型。上下文压缩的窗口管理本身另有专卡，本卡只管"权威状态必须在上下文之外"。

## E（执行步骤）
输入契约：状态对象清单（含产生者与消费者）、每对象的生命周期/一致性/访问方式要求、合规与保留要求、租户规模。缺"哪些事实影响任务正确性"时应先问清业务边界，不替业务猜。
1. 画四类状态地图：把每个对象归入运行时/工作区产物/记忆知识/治理状态。完成标准：地图无未归类对象，每对象有唯一属主类。
2. 逐对象定正确性边界：列顺序、原子、幂等、可回滚、可检索、可审计要求，写误配后果。完成标准：边界表覆盖全部对象。
3. 设计运行时状态三件套：Event Log（任务级强一致+Outbox+事件标识去重+重放条件）、Checkpoint（七要素+五个关键边界+频率与成本匹配）、Durable Execution（恢复公式+执行租约+围栏标识+状态指针；外部副作用另用幂等标识）。完成标准：三件套各有字段级清单。
4. 设计工作区与 Artifact：三层结构、CoW 快照（过可信五问）、围栏写入或私有分支、Artifact 八项元数据与不可变版本。完成标准：写入路径与合并/发布规则成文。
5. 设计记忆与知识：记忆双正交分层+写入门槛+冲突消解+三路召回+遗忘三级（删除清派生链防重建）；知识增量更新（版本水位+验证后切换）+权限前置过滤+答案溯源；本体仅在实体身份/关系约束/多跳查询成为持续需求时引入，实例数据与 Schema 变更分流程。完成标准：写入与读取策略表 + 本体引入判定记录。
6. 平台级横切：多租户三层组合+前置过滤、一致性分级（权威 vs 派生+新鲜度标注）、元数据与血缘、成本三原则（价值分层/显式保留期/减复制）。完成标准：横切策略表。
7. 选型验收与恢复演练：组件组合 vs 一体化按五问逐项验证（落到实际任务与故障场景）；恢复五步演练（含主区切换、索引重建、误删恢复、跨组件幂等）。完成标准：验收结论 + 演练记录。
输出契约：状态地图、正确性边界表、三件套字段清单、工作区/Artifact 规则、记忆知识策略表、验收结论、恢复演练记录。判停：业务无法回答"哪些状态影响任务正确性"时，先回任务契约梳理，不进入引擎选型。

## B（边界）
- 反例（第 2/5 章，ce-05/18）：把可恢复任务的真实状态放在模型上下文内——压缩、截断或模型误读改变任务事实，长任务与多 Agent 协作失去恢复基础；影响后续行动的事实必须先落权威状态再移出上下文。
- 反例（第 2 章 2.2.3，ce-06/23）：Memory 与 Knowledge 放进同一个向量库，同时失去"写入门槛+遗忘"与"权限过滤+时效管理"两类治理；错误推测、失败轨迹或恶意输入被写入记忆后当作经验反复引用。
- 反例（第 5 章 5.6，ce-24/22）：撤回数据只降检索分数不清派生切片/摘要/缓存/索引——数据事实上仍可被召回；先跨租户召回再"提醒模型不要泄漏"时隔离已经失败。
- Checkpoint 不是万能恢复：环境回滚不撤销已提交外部系统的操作（8.3.3）；Durable Execution ≠ 外部动作恰好一次，跨系统副作用必须另配幂等标识、结果确认与补偿（8.2.4）。
- 时间衰减与引用频率有边界：长期有效的约束不因少被调用而淡出，引用频率不等于正确性（8.4.4）；Persona 不作经验性记忆（8.4.2）。
- "统一"指数据模型与治理界面，不是单一底层引擎（8.7.5）；短会话轻量场景组件组合仍是合理起点，不必一体化。
- 平台必要性假设（适用边界）：第 8 章按多租户平台规模叙述（三层隔离、血缘、成本治理）。单 Agent 原型可裁剪为 Event Log+Checkpoint+文件产物三件起步，多租户/血缘等横切随真实租户需求引入。
- 阿里云产品视角：p2-34/p2-41 引文带 Lakebase 产品名、实践篇案例锚定 PolarDB——机制（切片粒度权衡、本体四要素、冷热分层）通用，吸收时去除产品绑定；选型验收落到任务与故障场景，绝不按产品名称选型。
