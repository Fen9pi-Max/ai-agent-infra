# 可观测性与审计（观测矩阵 + Span 层级 + 指标下钻 + 证据链闭环）

## R（原文摘引）
> AI 可观测性需要明确两个基本问题：一是"看什么"，即从哪些维度判断 Agent 的运行状态；二是"看哪里"，即需要覆盖哪些观测对象。（第 13 章 13.1.3）
> Agent 的问题还可能表现为错误规划、无效检索、工具误用，或者任务表面完成但结果不符合预期，因此"请求成功"并不等同于"任务成功"。（第 13 章 13.1.2）
> 以一次 Agent 任务为例，建议形成"ENTRY → AGENT/WORKFLOW → STEP → LLM/RETRIEVAL/TOOL"的基本层级。（第 13 章 13.2.2）
> 此类问题通常需要先通过聚合指标发现趋势或异常，再下钻到对应请求的 Trace，查看具体错误位置和步骤耗时。（第 13 章 13.3.3）
> Agent 的一次行为通常跨越"主体与授权 → 目标和指令 → 模型调用 → 检索或记忆 → 工具调用 → 系统副作用 → 结果传播"多个环节。（第 13 章 13.4.2）
> 最终闭环应是"观测事实 → 审计判断 → 调查处置 → 策略更新 → 执行验证"，而不是把所有可疑信号直接变成同步阻断。（第 13 章 13.4.5）

## I（解释）
1. **规划靠正交矩阵防遗漏**：先回答"看什么"（运行表现／稳定性与性能／成本与效率／行为审计四维度）×"看哪里"（任务与交互层／Agent 执行层／AI 基础设施层三层对象），每格落到具体指标、日志、Trace 或事件上，问题才能从任务结果逐层定位到执行步骤与基础设施。
2. **统一建模换可聚合性**：异构技术栈允许多种采集入口并存，但经统一网关归一语义后，用 Session–Trace–Span 三层组织（长会话不记成一条永不结束的 Trace；HITL 长等待切新 Trace 用 Session 标识关联），Span 按 ENTRY→AGENT/WORKFLOW→STEP→LLM/RETRIEVAL/TOOL 层级建父子关系，十二种执行语义统一命名——同类行为跨应用同名，才能做聚合分析。
3. **请求成功≠任务成功**：技术指标只能发现执行错误；任务效果要在 Trace 之上做三层评价（最终结果／关键步骤／执行轨迹），评估器按确定性递减选择（规则→LLM-as-a-Judge→人工），结果关联回 Session/Trace/Span。
4. **排障有固定路径**：先聚合指标发现趋势（错误率、超时率、延迟分位），再下钻 Trace 找错误首次出现步骤与传播路径；延迟分端到端与步骤耗时两层看。自托管推理引擎按"指标→Trace→并发→资源→优化验证"五步收敛。
5. **成本可归集重算**：Token 分输入/输出/缓存记录并关联到调用，汇总到 Trace/Agent/Session 层，保留模型、供应商、计价版本等依据。
6. **审计是证据链不是日志堆**：完整审计的最小证据链四要素——主体与范围、意图与授权、执行事实、结果与证据，缺一即不完整；检测走"原始事实→候选信号→上下文研判→已确认事件"分层链路，研判三状态（证据缺失≠安全），严重性与置信度分记；处置走五步闭环，交付物是可分派的风险队列而非告警列表。

## A1（原书案例 + 合成演练）
- 原书案例（实践篇转述）：①畅捷通智能运维——五层一体化监控（基础/中间件/应用性能/业务/用户体验）+ 应用-资源-租户三维拓扑治"看不见/管不住/动不了"，SLA 从 99.9% 提升至 99.995%，故障定位从平均 10 分钟以上压缩至 30 秒以内，MTTK 效率提升超 20 倍。②2026 开发者调研——人工抽查占 55%、基于轨迹自动评估仅 6%、28% 无系统性评估体系；使用评估手段的企业任务成功率 70%+ 约为无评估体系者的两倍（持续迭代企业达 84%）——观测与评估基建直接关联可靠性。
- 合成演练（原书第 13 章为方法论，此为按其规则推演）：客服 Agent（检索 + 2 个工具）上线后部分任务表面完成但结果不符预期，且 P95 延迟升高。按四维度×三层对象矩阵规划观测 → 建 Span 层级（业务主键入 Baggage 随上下文传播）→ 聚合指标发现错误率趋势后下钻 Trace，定位错误首次出现步骤与传播路径 → 对结果不符预期的 Trace 做三层评价 → 对一处疑似越权工具调用检查审计证据链四要素。预期可核验输出：Span 树各层级含模型/Token/工具名/参数摘要/完成原因；审计记录四要素逐项在场，缺任一项即判不完整；排障产出"错误首次出现步骤 + 传播路径"而非仅错误计数。

## A2（情境应用）
场景：Agent 已上线但排障无抓手（只知失败不知哪步失败）；要向安全/合规团队交付审计能力；Token 账单突增需归因到会话/任务；要建效果评估却不知从哪取数；接入无法修改内部实现的 CLI/IDE Agent 需要遥测。
语言信号：「Agent 上线了怎么知道它干得怎么样」「出了问题怎么定位是哪一步」「Trace 怎么建、埋点埋在哪」「审计要留什么证据才算完整」「成本怎么算到每个会话头上」；英文 trigger：observability / tracing / span / drill-down / audit trail / token attribution。
区分（初稿）：agent-security 管事前/事中拦截（Guardrail）与权限收敛，本卡管"发生了什么"的还原与事后审计；asset-governance 管资产版本台账，本卡管运行轨迹——两者的接口是"这次运行解析到了哪个资产版本"；效果评估器体系建设归调优篇，本卡只定"在 Trace 上做三层评价"的接入点与评估器选择顺序。

## E（执行步骤）
输入契约：Agent 技术栈与可改造程度清单、业务成功标准（判定任务成功的可观测条件）、合规要求（允许做什么/需审批什么/绝不能做什么）、现有基线数据。缺"业务成功标准"必须先向业务方询问，不得静默用技术指标替代。
1. 规划观测矩阵：四维度 × 三层对象逐格判定需要什么信号、从哪里采集。完成标准：矩阵无空格，每格标注采集方式或"明确不覆盖 + 原因"。
2. 建采集与 Span 层级：按语义需求选接入方式（需还原决策过程/区分阶段必须手动埋点；纯技术监控可用探针；不可改造的 Agent 用适配器 + Daemon 重建），多源按原生调用 ID/时间边界去重；建 ENTRY→AGENT/WORKFLOW→STEP→LLM/RETRIEVAL/TOOL 层级，跨步骤字段写 Baggage。完成标准：进程内唯一 TracerProvider，同一操作只计一次 Token。
3. 定切分与语义：Session-Trace-Span 三层边界（重试不结束 Trace、HITL 长等待切新 Trace 关联），十二执行语义统一命名。完成标准：同类操作跨应用同名可聚合。
4. 稳定性排障：聚合指标发现趋势 → 下钻 Trace → 错误分类（模型/检索/工具/参数/权限/超时/人工终止）+ 首次出现步骤 + 传播路径 → 端到端与步骤延迟分层定位。自托管推理再走五步闭环（指标→Trace→并发→资源→优化验证）。
5. 成本归集：Token 分输入/输出/缓存记录，多层汇总到 Trace/Agent/Session，保留计价依据可重算；与任务结果结合区分合理高成本与浪费。
6. 效果三层评价：最终结果/关键步骤/执行轨迹三层次定义评价问题，评估器按规则→Judge→人工选择，评价记录含评估器版本与判断理由，关联到 Session/Trace/Span。
7. 审计闭环：证据链四要素齐备；检测走分层链路（原始事实→候选信号→上下文研判→已确认事件），研判输出三状态之一，严重性与置信度分别记录；确认事件进带负责人的风险队列，关闭后验证处置生效并用误报/漏报/MTTA/MTTR/复发率评估审计质量。
输出契约：观测矩阵表、Span 层级与属性清单、排障 SOP（含判停条件）、成本归集表、审计记录格式（四要素齐备）、分优先级风险事件队列。判停：无基线与业务成功标准时先补齐再接入；托管 API 用户跳过推理引擎五步排障。

## B（边界）
- Trace 只记模型输入输出是最大反例（实践篇 ce-34）：Context 决策、工具结果、验证证据之间无因果关联时问题无法定位到环节；构建期不埋事件与关联 ID，事后任何平台都补不出可信 Trace（ce-35）——埋点是构建期义务不是平台期补丁。
- 观测本身是高敏资产：为诊断方便明文记录凭证、完整 Prompt 与敏感数据，观测建设会成为新的泄露渠道（ce-52）；最小采集、脱敏、分级授权必须与采集同步设计。模型评审结论与事实记录混存且无版本标注，会被下游当作权威证据扩散（ce-51）。
- 事后审计不能撤销已发生的副作用（文件修改/外发/泄露，13.4.1）：撤销与拦截是 Guardrail（U16）的职责；审计结论反哺拦截时检测与拦截须分开建模——只有确定、低延迟、可解释、可回放的策略才适合实时阻断。
- eBPF 等运行时证据缺用户目标与业务授权上下文，且对加密流量可见性有限，必须与埋点/网关日志互证，不能单独据此认定越权或攻击。
- 指标陷阱：底层指标正常不等于用户体验正常（畅捷通案例的起点），只看聚合不看 Trace 下钻会漏长尾；指标标签用低基数字段，高基数内容留在 Trace 里下钻。
- 适用边界：推理引擎五步排障仅适用于自托管推理；观测方案解决"看什么怎么看"，效果评估体系（代表性样本、基准答案、评估器校准）归调优篇，本卡只做接入点。
