# 任务契约（Agent Loop 五阶段状态机 + 十任务态 + 委派契约 + 五级完成验证）

## R（原文摘引）
> 允许模型根据当前目标和环境反馈，重复执行"判断—行动—观察—再判断"，直到任务被验证完成、进入等待、失败或取消。（第 4 章 4.1.1）
> 消息历史记录了模型和用户曾经交换的内容，却不应成为任务状态的唯一来源。（第 4 章 4.1.2）
> 预算耗尽时，则应产生明确终态与未完成清单，而不是悄然截断。（第 4 章 4.1.2）
> 主 Agent 负责全局目标、计划、预算、依赖和最终结果，不应把"任务完成"的责任一并交出去。（第 4 章 4.3.2）
> 模型只能提出完成申请，Harness 才能提交完成状态。（第 4 章 4.6.2）

## I（解释）
1. **Loop 即状态机**：最小完整循环 = Prepare（读权威状态、定本轮目标、请求 Context）→ Model（判断行动/委派/询问/等待/申请完成）→ Act（交行动平面完成校验与执行）→ Observe（标准化结果更新任务事实）→ Verify（用环境事实验收）。Verify 不过则回 Prepare 产生新缺口——循环的出口是被验证的终态，不是模型停笔。
2. **权威状态 ≠ 消息历史**：目标、阶段、Plan/Todo、已确认事实、阻塞、子任务、Artifact、剩余预算、等待原因、完成依据须由 Harness 维护为可机读权威状态；模型看到的只是由它生成的当前视图。模型说"已完成"只能进 VERIFYING。
3. **十任务态 + 预算边界**：CREATED/RUNNING/WAITING_INPUT/WAITING_APPROVAL/WAITING_EVENT/PAUSED/VERIFYING/COMPLETED/FAILED/CANCELLED，每态定义等待原因与允许迁移——显式化让 Runtime 能释放资源、界面能说清在等什么。步数/时长/Token/工具调用/高风险动作次数全部进预算，耗尽出明确终态+未完成清单。
4. **计划三模式 + 门禁 + 委派契约**：轻量 Todo / Plan Mode（只读探索→计划→确认→解锁执行）/ Planner-Executor 按复杂度选；长任务按阶段门禁分段验收。子任务带七要素契约（目标边界/已知事实/能力权限/预算/输出证据/失败语义/验收条件），子代理不继承父权限，产物是新 Observation 须经 Schema+版本+父验收三关口。
5. **失败→恢复映射 + 完成验证**："Agent 失败"不是可执行诊断——瞬时错误有界退避、参数错误修正、环境缺失重建、权限拒绝等待或终止、无进展检测渐进处置；副作用行动重试前必须先证明"上次没发生"。完成验证五级（结构→环境→确定性→独立模型→人工）按风险选择，完成 = 一组目标相关事实，不是一句话。

## A1（原书案例 + 合成演练）
- 原书·实践案例：PolarDB-X 自动修复以"稳定复现"作为修复交付门禁，Agent 从报警自主完成分析/复现/修复/测试，仅研发参与最终审查（c-25）；PatchPilot 以"是否完成交付"而非"是否完成一次执行"衡量效果（c-24）；多 Agent 研发小队 24 道基线题盲测：10 等价/5 接近/4 部分完成/0 方向错误——完成判定对照专家代码而非模型自述（c-28）。
- 原书·契约差异示例（3.1.2 转述）：同一修复目标，契约只到"可审批变更"时不得把"尚未发布"误判为未完成；目标含发布则须进一步核验审批与真实部署状态。
- 合成演练（纸面推演，非原书案例）：客服"退款工单处理"任务——裁剪状态机为八态（每态定义等待原因与允许迁移）；预算=步数 15/时长 10min/工具调用 20 次/高风险动作 2 次，接近阈值收敛、耗尽出未完成清单；计划模式=轻量 Todo（只记可交付状态变化项）；完成判据选确定性验证级：工单系统状态=已解决 ∧ 退款流水存在 ∧ 用户确认记录，三事实缺一不可；模型自述"已处理"只进 VERIFYING，验证失败转新 Observation 继续修复；查物流子任务按七要素契约委派，失败语义=RETRY_OR_REASSIGN。状态迁移表可对输入逐事件走查。

## A2（情境应用）
场景：设计 Agent 的执行循环与任务状态机时；定义"什么算完成"的验收标准时；防死循环、防预算失控、防"自称完成"时；拆分委派子任务时；长任务断点恢复设计时。
语言信号：「Agent 说做完了怎么信」「怎么防死循环/防烧钱」「任务卡在等待怎么处理」「子任务怎么派、失败了怎么办」「agent loop / completion criteria / budget / delegation / 无进展」。
区分：context-engineering 管 Loop 每轮窗口内看见什么（Context 管线与压缩）；state-layering 管权威状态存哪、如何分层持久化（本卡只定义状态语义）；action-plane 管 Act 阶段的权限判定与审批（本卡的 Plan Mode 解锁写权限，其执行侧控制归 action-plane）；调度/定时/工作流级完成语义归第 10 章单元。

## E（执行步骤）
输入契约：任务目标与边界、成功标准（可观测的环境证据）、风险等级、预算上限（步数/时长/Token/费用/工具次数）、是否需要委派与人工环节。缺成功标准或风险等级时先向需求方确认，不得默认"模型说完成即完成"。
1. 定契约与完成判据：把成功标准改写为环境证据清单（系统状态/流水/Diff/测试报告），标注契约目标边界（到"可审批变更"还是"已发布"）。完成标准：每条判据绑定环境证据而非模型输出；无一句"模型自述"级判据。
2. 裁剪状态机：从十态中选必需态，每态定义语义、等待原因、允许迁移；预算字段与外部终止条件同时定义。完成标准：迁移表覆盖全部已选状态与事件，预算含高风险动作计数。
3. 选计划模式与门禁：按复杂度选 Todo/Plan Mode/Planner-Executor；长任务划分阶段并定义每阶段产物与门禁条件；重规划须说明触发事实并保留已完成项。完成标准：每阶段门禁可机判。
4. 设计委派契约（如有子任务）：七要素逐项写明，子代理权限显式最小化；定失败策略四型（FAIL_FAST/BEST_EFFORT/RETRY_OR_REASSIGN/ESCALATE）；产物过 Schema+版本+父验收三关口。完成标准：无"一句话委派"。
5. 定验证级别与恢复路径：按 p1-113 风险映射选验证层级（低风险结构化产物→结构验证；高影响→人工验收）；Verifier 返回结构化缺口与可修复性，失败转新 Observation；副作用行动定幂等键与"先查后重试"顺序。完成标准：完成=事实清单（evidence 引用+remaining_actions）；失败类型→恢复策略映射表齐备。
输出契约：状态迁移表 + 预算表 + 计划/门禁方案 + 委派契约模板 + 完成事实清单格式。判停：无外部环境可查证（纯文本生成类任务）时降级为结构验证+人工抽验，并明示验证强度受限。

## B（边界）
- 最大失败模式是"任务看起来完成"（ce-03）：完成判定依据是模型输出文本而非测试/文件差异/业务校验，高风险动作无审批点——交付后返工才暴露。
- 状态多写点污染（ce-30）：每个 Tool 各自直接改任务权威状态，变更无法归因无法回放——State Patch 由 Harness 统一提交。
- 模型评审结论不能当运行事实（ce-51）：评估结论与事实记录分开保存、带方法与版本，避免评审误差被下游当证据扩散。
- Prompt ≠ Harness 约束（4.2.3）：Prompt 可要求"先规划再修改"，但只有权限模式+工具白名单+持久状态+HITL 共同生效才构成真约束——计划约束不可只写在提示词里。
- Middleware 有时机禁区（4.5.1 表）：Task 创建前后禁隐式改用户目标；Action 前后禁绕过统一行动平面；State 变化前后禁多处各自维护权威状态；Verify 前后禁仅凭模型自述标记完成——每加一个扩展点核对禁区。
- 平台完成语义 ≠ 业务完成（4.6.4）：平台统一纳管不等于共享完成标准；发布状态就绪（3.5.3）只是平台事实，业务 Task 完成由企业契约定义。
- 盲目重试只增加成本和风险（4.6.1）：重试前先分类失败类型；无进展检测（相同工具相似参数反复调用/同一错误反复出现/Plan 长时间不变）比最大步数更早发现问题。
