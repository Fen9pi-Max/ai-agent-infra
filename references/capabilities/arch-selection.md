# 形态与成熟度选型（四维形态判断 + L1-L4 成熟度 + 最低充分架构）

## R（原文摘引）
> 这些形态的根本区别，不在于界面是否采用对话方式，而在于任务循环由谁掌握、执行路径在什么阶段确定，系统能够在多大程度上影响外部环境，以及任务是否需要跨会话持续运行或由多个 Agent 分工协作。（第 1 章 1.2.1）
> 企业应当结合任务价值、风险、运行规模和工程成本，为每类任务选择成本与风险可接受的最低充分架构。这是贯穿本章的决策原则。（第 1 章 1.4.1）
> 只有在当前架构无法以可接受的风险和成本交付任务，而新增能力具有明确价值时，升级才有必要。（第 1 章 1.4.1）
> Long-Horizon Agent 与 Multi-Agent 不是同一维度。前者解决任务如何跨时间持续，后者解决多个执行主体如何协作。（第 1 章 1.2.3）
> 采用哪种形态取决于任务结构，而处于哪个成熟度取决于运行与治理能力的完备程度。（第 1 章 1.4.1）
> 凡是被授予的自主性，都必须有与之匹配的边界、证据和验证手段；凡是暂时不需要的能力，可以不建设，但需要明确在什么条件下必须补齐。（第 2 章 2.1.3）

## I（解释）
1. **两个独立判断**：形态（Chat/RAG→Workflow→Copilot→Single-Agent→Long-Horizon/Multi-Agent，哪种 Agent）由任务结构决定；成熟度（L1 辅助生成→L2 受控自动化→L3 Agentic Execution→L4 规模运营）由运行与治理完备度决定。二者常被混为一谈——名称含 Agent 的产品可能只是 L1。
2. **形态四维**：任务循环由谁掌握、路径何时确定、环境影响多大、是否跨会话/多主体。Workflow 适合路径可穷举、错误代价高；Agent 适合路径难预知、环境可反馈、结果可验证。企业主流结论是 Hybrid：确定性流程固化边界，Agent 只处理不确定段落。
3. **升级双条件门槛**：当前架构确实无法以可接受风险/成本交付 + 新增能力有明确价值，缺一不升。"越智能越好"被显式否定——低风险知识助手可长期停在 L1。
4. **两个正交扩展**：Long-Horizon（时间维：跨时间保持目标/状态/责任一致）与 Multi-Agent（协作维：角色/权限/上下文隔离）独立采用，引入条件是单 Agent 受到时间跨度、上下文容量、职责冲突、权限隔离或并行效率五种具体限制。
5. **决策上下文**：Agent = Model + Harness——可靠性寄托在模型上还是工程上，是选型的第一分叉。Agentic 六特征是形态判定依据而非功能清单；五责任域/三视图/生命周期闭环为后续构建单元（U2-U7）提供共享架构语言，防各单元各自发明。

## A1（原书案例 + 合成演练）
- 原书·调研数据（2026 开发者调研报告，1906 份问卷）：46% 企业已开发/开发中，仅 18% 部署到生产——卡点不在意愿与模型，而在 Harness 工程配套（c-01）；单 Agent 40% / 多 Agent 42% / 以 HITL 为架构原则 15%——多形态在企业内长期共存、自主度是可调参数（c-02）；Coding 率先规模化因其反馈明确、边界清晰、可回滚，57% 采购编程工具与 78% 用通用框架并存（c-03）；落地集中在容错空间大、能人工兜底的场景，核心业务流程占比 <40%（c-09）。
- 合成演练（纸面推演，非原书案例）：电商客服 Agent——60% 询问可 FAQ 穷举、30% 查单/改地址、10% 退款且 >500 元须人工；数据不出私域、团队 6 人。四维逐项映射 → 形态 = Hybrid（FAQ/路由走 Workflow 固化 + 查单诊断段 Agent 持循环 + 退款执行独立高管控）；成熟度分段定位（退款段停 L2，诊断段 L3）；用双条件核验"跨 3 天工单"只需状态外置（不需要 Long-Horizon）；无并行/职责冲突证据 → 不引入 Multi-Agent。每项决策可回指四维或双条件输入。

## A2（情境应用）
场景：立项"要不要做 Agent、做成什么形态"时；有人提议"直接上 Multi-Agent/最高自主性"时；评估采购产品"是不是真 Agentic"时；决定某类任务要不要升成熟度时。
语言信号：「这个场景适合 Agent 还是 workflow」「要不要上多智能体」「我们是 L 几」「能不能全自动化、要不要留人工」「form factor / agentic vs workflow / maturity / multi-agent 值得吗」。
区分：本卡回答"要不要 Agent、什么形态、什么成熟度、架构原则长什么样"；harness-entry 回答"选好形态后由谁实现"（第 3 章四类入口）；action-plane 回答自主性授予后权限与审批怎么落；团队拓扑与多 Agent 编排细节不归本卡。

## E（执行步骤）
输入契约：任务描述（步骤/分支在设计时能否明确）、错误代价与可逆性、数据边界与合规要求、团队规模与工程投入、现有自动化现状。缺风险等级或验收要求时应先询问，不能静默按低风险处理。
1. 六特征初判：核对目标中心/运行时定路径/环境作用/跨步骤状态/确定性约束/可观测评估，判断是否进入 Agentic 形态。完成标准：六项逐条标注满足/不满足/部分。
2. 四维定形态：任务循环归属、路径可预知度、环境影响+验证手段、跨会话/协作需求，逐项映射到 Workflow / Agent / Hybrid；可穷举段落固化、不可穷举段落给循环。完成标准：每段任务有形态归属 + 一句理由。
3. 扩展核验：仅在五种限制（时间跨度/上下文容量/职责冲突/权限隔离/并行效率）有具体证据时引入 Long-Horizon 或 Multi-Agent，二者分别判断。完成标准：无证据则明确写"不引入"。
4. 成熟度定位：按任务循环/执行跨度/环境影响/生产治理四维定位 L1-L4，可按任务分段定位（不同段落不同级别）。完成标准：每段一个级别 + 该级典型局限说明。
5. 升级门槛与最低充分检查：对照双条件决定是否升级；检查每项能力是否为当前任务所必需，暂不建设的列出补齐触发条件。完成标准：升级决策含双条件证据；无"为未来预加码"项。
输出契约：形态决策表（段落×形态×理由）+ 成熟度定位表 + 不引入项及条件 + 待补能力触发条件清单。判停：任务全部步骤可设计时穷举 → 直接输出 Workflow 结论并结束，不进入 Agent 设计。

## B（边界）
- 架构决策不能留给构建阶段隐式完成（2.4.2）：形态与权限模型由实现细节倒推确定后，只能靠重构解决，补丁无效——风险来自形态/权限模型时回本卡重新设计，而非叠补丁。
- 形态判断是定性判据：原书未给量化权衡公式（复杂度成本度量），权重与阈值须按场景设定；不要伪造"客观打分"。
- 六特征是判定依据不是功能清单（1.3.2）：判定为 Agentic 不要求全量启用功能或最高自主档。
- 适用边界（原书视角）：本手册为阿里云企业白皮书视角，参考架构（三平面、五责任域、部署拓扑）默认多租户多团队的"平台必要性"假设；小团队/单场景应裁剪——是否需要平台统一治理本身是 L4 级问题。Agentic OS 六维对比（1.4.3）是差距分析视角，不要求企业自建操作系统式平台。
- 相邻不混淆：模型选型五维与路由降级回归（2.2.1）属模型层决策，不因"换更强模型"替代架构判断——降级模型协议兼容不等于能力等价（ce-01）。
