# AI 资产注册、版本与发现（结构化引用 + 不可变版本 + 发布 Pipeline + L0-L5 演进）

## R（原文摘引）
> Agent 不应通过偶然的文件路径或固定地址保存依赖，而应使用结构化引用，包含 Namespace、资源类型、资源名称和版本选择方式。（第 15 章 15.6.1）
> 提交评审后，系统固定本次候选内容和摘要，后续检查都针对同一份内容进行。任一检查要求修改时，版本回到草稿阶段；已发布版本保持不变。（第 15 章 15.5.1-15.5.2）
> 统一 Pipeline 不意味着所有资源使用同一组检查。公共流程负责状态和记录，不同资源仍需选择适合自身的评估方法。（第 15 章 15.5.3）
> 如果内容、依赖或关键运行条件发生变化，原评测结果不能继续沿用。即使资源版本号未变，摘要不一致也应停止发布。（第 15 章 15.5.4）
> 阶段之间的判断标准应以实际能力为准，而不是是否部署了某个产品。（第 15 章 15.10.5-15.10.6）

## I（解释）
1. **五类资产一套语义**：Prompt/Skill/MCP Server/Agent/AgentSpec 统一建模为"逻辑资源（稳定名称、Namespace、负责人——它是谁）+ 资源版本（固定内容、独立版本号、内容摘要——内容是什么）"两层；Agent 用结构化引用声明依赖（Namespace+资源类型+资源名称+版本选择方式），Resolver 解析为唯一版本，运行记录保存解析结果而非标签名。已发布内容不可覆盖——否则历史评测、问题追踪、运行记录引用的版本全部失去意义。
2. **发布是有序 Pipeline 不是点击上线**：草稿→提交评审（固定候选内容与摘要）→有序检查节点（格式→安全→依赖→评测，某节点拒绝后续不执行）→人工判断→发布形成不可变版本，在线状态与标签决定可发现性。三条铁律：检查过程不改候选内容；自动结果不替代人工判断；评审通过≠正式上线。
3. **评测与版本绑定**：可用于发布决策的评测记录至少关联资源类型/名称/版本/内容摘要/评测集版本/模型与运行时版本/策略与工具版本/执行时间；内容、依赖或关键运行条件变了原评测作废——版本号未变但摘要不一致应机械停止发布。
4. **MCP 与 Agent 的分离原则**：能力定义、版本、运行端点三分离（端点扩缩容不产生新版本，Tool 参数/返回结构变了必须新版本）；Agent Registry（哪些 Agent 可调用）与 AgentSpec Registry（Agent 如何组装）两层分管。
5. **发现与资格分离**：ARD 跨类型形成候选（相关性排序），治理资格独立判断（在线状态、授权、环境兼容、风险等级）——高度相关但已撤回或超授权的资源不得因得分高进入候选；发现摘要与执行内容两阶段加载，Context Compiler 按信任分级与 Token 预算装配进运行时。
6. **可追溯的三个抓手**：反向引用（从资产查受影响 Agent）、Lock Manifest（任务开始时锁定的版本组合）、有效 Prompt 指纹/Context Manifest（实际生效组合）——让"改一个 Prompt 坏三条链"和"结果为什么变了"变成可回答、可预判的问题。
7. **分阶段演进防过度设计**：L0 分散维护→L1 版本留存→L2 统一 Registry→L3 评估与可信供应链→L4 受控动态发现→L5 持续改进；判断以实际能力为准（仅建资源列表仍允许覆盖历史内容不算 L2）。落地顺序：先纳管多 Agent 共用、变更频繁的资源。

## A1（原书案例 + 合成演练）
- 原书案例（调研与实践篇转述）：①2026 调研：MCP 已关注或落地企业合计 37%，真正完成企业内私有部署仅 9%，28% 明确提出 MCP 服务管理与注册中心需求——协议本身不提供私有注册中心、统一身份鉴权、版本灰度与审计留痕，缺口正是本章要补的企业级配套。②Mamba Insight（运营分析 Data Agent，亲历）：把近一年 500+ 条数据需求逐条标注，暗知识固化为 9 个结构化 Skill 文档 + 45 组 QA 对两类资产，均遵循可版本/可审计/可灰度/可回滚，经 Skill 审核流水线管理。③生产故障诊断 Agent 端到端八步流程（15.10.2）：启动加载稳定依赖记基础 Lock Manifest → 形成能力需求 → ARD 发现长尾能力 → RAD 解析远程 Agent → 两级治理判断 → 解析版本端点 → Context Compiler 装配记 Manifest 与 Trace → 输出带证据结果。
- 合成演练（按原书规则推演）：20 个 Agent 共用 3 个 Prompt、若干内部 Skill 和 5 个 MCP Server，Prompt 改在代码里、无统一管理。按 L0-L5 判定当前处 L0（Prompt 在代码中、信息分散），给出 L0→L2 路线：先纳管多 Agent 共用、变更频繁的资源；产出结构化引用样例与 Registry 六组件职责表；定义发布 Pipeline（格式→安全→依赖→评测有序节点 + 评测版本绑定字段）；演练一次风险 Skill 版本处置。可核验输出：引用四要素齐全且运行记录保存解析结果；Pipeline 满足三铁律；"版本号未变但摘要不一致→停止发布"可机械核对；处置链四要素（内容摘要/权限记录/消费者列表/可替代版本）在场——缺任一项即无法判断需停止哪些任务。

## A2（情境应用）
场景：多个 Agent 共用 Prompt/Skill，改一处坏三条链且无法预判影响；MCP 要在企业内私有部署需要注册与版本管理；想把外部 Skill/公共 MCP 引入生产；回答不了"这次结果为什么变了"（Prompt、模型、变量、Context 谁变了）；组织要建 Agent 平台规划资产治理路线。
语言信号：「Prompt 到处复制改不动了」「Skill 怎么统一管理和授权」「MCP 注册中心怎么建」「资产怎么版本化、怎么回滚」「外部 Skill 准入要做什么检查」「怎么知道线上跑的是哪个版本」；英文 trigger：asset registry / versioning / immutable release / rollback / capability discovery / supply chain。
区分（初稿）：agent-security 承接资产准入中的安全检测规则本体（恶意命令、行为偏离声明），本卡管资产生命周期、版本与解析机制——安全是 Pipeline 里的一个节点，不是全部；observability 管运行轨迹，本卡管资产台账，两者的接口是 Lock/Context Manifest 与 Trace 的关联；上线前验证资产组合的行为归 agent-simulation（其 Manifest 版本锁定复用本卡的解析语义）。

## E（执行步骤）
输入契约：资产现状清单（五类资产的数量、共用关系、变更频率、负责人）、Agent 数量与风险水平、现有发布流程与评测能力。缺现状清单时先盘点（这正是 L0 的第一步），不能凭印象设计。
1. 定级：按 L0-L5 判当前阶段，判定以实际能力为准。完成标准：判定依据可指认（如"仅建列表仍允许覆盖历史内容"即不满足 L2）。
2. 统一引用与版本：建立逻辑资源 + 不可变版本双层模型，结构化引用四要素（Namespace/类型/名称/版本选择方式），Resolver 解析并要求运行记录保存解析结果。完成标准：任一历史运行能回答"用了哪个版本"。
3. 建发布 Pipeline：草稿→提交评审固定内容与摘要→有序检查（格式→安全→依赖→评测，拒绝即停回草稿）→人工确认→不可变发布→标签控制可发现性；维护反向引用。完成标准：三铁律落地（检查不改内容、自动不替代人工、评审通过≠上线），摘要比对规则可机械执行。
4. 评测绑定发布：评测记录按九关联字段登记；失效规则执行（内容/依赖/运行条件变化即作废）。完成标准：无"沿用旧评测放行新内容"路径。
5. 发现与装配（L3 以上引入）：外部 Skill 六阶段准入（来源核实→完整性校验→静态检查→隔离验证→人工评审→内部发布）；ARD 混合检索 + 治理资格过滤；固定依赖 + 动态发现混合模式；发现摘要与执行内容两阶段，Context Compiler 按信任分级与预算装配，生成 Context Manifest。
6. 处置与运营：风险版本按四要素处置（下线→发现侧排除→停新加载清缓存→经 Manifest 与 Trace 定位受影响任务→新版本重走 Pipeline）；按五方面运营指标（资源治理/变更评审/发现质量/运行效率/安全治理）度量。
输出契约：资产台账 + L 级判定与演进路线 + 引用规范样例 + Pipeline 流程与检查节点表 + 评测绑定字段表 + 处置演练记录。判停：单 Agent、单人使用、无共用资产时可停留 L0-L1（版本留存）而不建 Registry——过度设计本身是本卡警告的失败模式。

## B（边界）
- Prompt 在生产随时修改不留版本是最基础反例（ce-11）：Agent Release 不是可复现单元，任何评估结论只对修改那一刻成立；资产变更绕过与代码相同的发布链（ce-25）时，退化以成本上升、误选率上升等间接形式出现——资产变更是行为输入，等价于代码变更。
- 影子 Agent 资产黑箱（ce-64）：不知道有多少 Agent、谁创建、调了什么资源、有何权限，权限不可枚举即不可治理——资产发现是治理的第零步。
- 撤回反例（ce-24）：资产存在派生链（文档→切片/向量/摘要），只降低检索分数不算撤回——需禁止新读取、删原始内容、清派生数据、更新引用并保留最小审计证明。
- 托管边界反例（ce-27）：托管平台转移的是运行责任，不是知识可见性与 Skill 授权决策——多租户隔离与业务验收仍需企业自己补。
- 评测误用反例（ce-26）：资产评估只看总体成功率会掩盖分场景/分租户退化，需按场景、风险分层评估；版本号首先承担唯一标识作用，兼容性不能只凭版本号推断。
- 适用边界：小团队不必初期引入全部组件（L0-L5 的存在意义）；评测集/黄金集构建方法归调优篇，本卡只把评测作为发布门禁使用；恶意内容检测规则本体归 agent-security；通用 Context 构建技术归信息契约相关能力，本卡只保留资产进入 Context 的信任分级、预算与一致性治理面；Nacos AI Registry 等仅为参考实现，机制协议无关。
