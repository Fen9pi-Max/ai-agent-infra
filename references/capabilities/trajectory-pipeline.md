# 轨迹数据与运行时 Pipeline（三对象区分 + 检索阅读归因 + 相邻事实链 + 行粒度先行 + 周期质检）

## R（原文摘引）
> 上线后的团队需要持续回答两组问题：任务有没有做好，以及把它做好花了多少代价。（18.1）
> 完成配置后发起一条新任务验证，不要仅凭开关已开启就认为数据已到达。……第一条记录看对后，再挑一个失败任务和一个多轮任务。（19.1）
> 已知具体执行时，优先使用 TraceID 精确查找；需要查看一段连续交互时，用 SessionID 找相关记录。……筛选条件从少到多增加，结果为空时先撤掉最近增加的条件。（19.2）
> 分析时，尽量把结论落到一组相邻事实："用户要求操作步骤 → 检索返回了步骤 → 最终回答遗漏步骤"。这样的记录便于别人复核，也能直接用于后续评分。（19.3）
> SessionID 帮助查找相关交互，但不会自动证明它们都属于同一个任务。（19.6）
> 选择之前，先明确一行代表什么。退款质检可以从"一次任务一行"开始；分析用户为何反复补充信息，需要连续多轮；比较多个并行 Agent，则要分别保留各条路径。（20.1）
> 先展开一条普通任务的输入、输出和轨迹，确认质检人员能连续读懂；再找一条工具报错或没有答复的任务，看它是否保留下来。（20.3）

## I（解释）
1. **本卡是数据飞轮的组织层**：真实运行 → 轨迹组织（Trace/Trajectory）→ Pipeline 加工成质检与评估可用数据 → 沉淀进候选集，供下游评估实验消费。模块是环不是单向流水线：评估结果可写回数据集，复核既改样本也改评估器。
2. **三个组织对象别混用**：Trace（一次执行的相关调用，定位某次执行问题）、Session（一段连续交互，查用户补充与上下文，但同一会话可能有多个任务）、Trajectory（整理后的行为过程，适合阅读与加工样本）。时间接近或文字相似不能证明"完整任务已被恢复"。
3. **检索按问题选入口**：具体某次执行用 TraceID，连续交互用 SessionID，无标识用应用/工具/时间范围组合，意图模糊用语义搜索——相似度只负责选候选，不代表相同难度或错误。
4. **阅读法与结论格式**：先读输入输出定目标与结果，再看指标概览定重点，不逐字通读；沿"用户补充→Agent 行动→工具返回→后续回答"查关键步骤，核对关键动作的输入依据与结果使用；结论写成相邻事实链（A→B→C），别人能复核、下游能直接评分——单独写"回答质量不好"下游不知道查什么。
5. **三类分析各有路径**：工具失败看失败后的行动（修正后成功与原样重试不应给同样建议）；耗时/Tokens 高找"多出来的工作"（不凭总量删步骤，必要探索也消耗资源）；业务质检看回答与执行事实是否一致（"工具接收请求、任务结束、业务目标达成不是同一件事"；材料不足先记待确认，别把采集问题当 Badcase）。
6. **Pipeline 第一决策是行粒度**："一行代表什么"（一次任务/一段多轮/一条并行路径）决定分组、采样、评分方式与业务人员能否读懂；配置用真实数据预览驱动——普通任务可读、异常任务保留；处理按成本排序：先筛选、再采样、后模型处理；单次跑通用后周期任务化，衔接历史补数与周期起始时间（"任务已创建"≠"数据已写入"）。

## A1（原书案例 + 合成演练）
- 原书第 18.3 章退款超时例：补齐业务结果并建立关联→评估指出结果核实问题→人工确认预期做法→调优选择补状态查询/改 Skill/修幂等重试→实验覆盖成功/失败/不确定（18.3，转述）。第 18.4 章给出"产品客服遗漏操作步骤"的一轮七步法示例。实践篇：畅捷通五层一体化监控 + 应用-资源-租户三维拓扑，故障定位从平均 10 分钟以上压缩至 30 秒以内（c-33）。
- 合成演练（原书未提供该场景成套记录，按 19.2/19.3 规则推演）：用户投诉"改签 Agent 回答遗漏材料清单"。已知具体执行→TraceID+时间范围定位；先读输入输出，定位知识检索步骤，核对"检索已返回清单 vs 回答未使用"；输出相邻事实链"用户要求材料清单 → 检索返回含清单 → 回答仅输出费用说明"——可被他人复核并直接进评分。Pipeline 侧（按 20.1-20.5 规则）：每周质检退款任务、人力每天只能复核 100 条→行粒度=一次任务一行→预览验证普通任务可读、工具报错任务保留（被过滤则调条件）→随机采样 100 条/日 + 语义去重建题库→建周期任务输出 refund_review_daily 并衔接历史补数时间。

## A2（情境应用）
场景：新接入观测数据要验证采集链路时；用户投诉某次具体执行要排查时；某类工具任务表现差或耗时/Tokens 偏高要定位时；要把散乱运行记录变成业务能读的日常质检表时；为评估实验准备候选样本时。
语言信号：「轨迹怎么查」「Trace 里看什么」「为什么这次回答漏了步骤」「耗时高在哪」「质检表能不能自动生成」「一行代表什么」「trajectory / trace / session / pipeline / 数据集 / 留样」。
区分（初稿）：本卡产出"相邻事实链结论 + 候选样本 + 质检数据集"，到样本入候选集为止；业务确认、rubric、黄金集与实验归 golden-badcase；"改哪层（环境/Harness/模型）"的归因决策归 tuning-attribution，本卡提供其证据原料；采集接入本身（打点、上报配置）属可观测接入类能力，本卡从"数据已到达"开始。

## E（执行步骤）
输入契约：调查问题类型（某次投诉 / 一类工具差 / 耗时偏高 / 周期质检）+ 观测数据访问入口 +（Pipeline 路线）人力复核预算与输出用途；无观测数据时先走采集接入，不在无数据状态下空谈分析。
1. 首条验证（新接入必做）：亲手执行一条任务并记录 TraceID/时间/问题/回答→按时间范围定位，核对输入输出与工具调用及返回→再看一条失败任务（错误反馈是否保留）和一条多轮任务（用户补充是否可见）；列表为空按序排查入口→时间范围→筛选条件→采集状态，先区分"数据未采集"与"Agent 未正确执行"。完成标准：三类记录核对结论（对/错在哪）。
2. 检索定位：按问题选入口——具体执行 TraceID；连续交互 SessionID；工具表现差用应用+工具名+时间；变慢用同应用按耗时筛再比 Steps/Tokens；意图反复出现用语义搜索后人工确认；条件从少到多，为空先撤最近增加的条件；找到记录组后先读代表样本，概念咨询与操作流程类分开分析。完成标准：候选记录组 + 入口选择理由。
3. 阅读与归因结论：先输入输出→指标概览定重点→展开关键工具动作（检索词是否针对、返回是否含所需内容、后续回答是否使用）→多 Agent 沿委派关系查子轨迹目标与返回；怀疑记录缺失交工程回查采集，业务结果以工具反馈和业务状态为准。完成标准：结论写成相邻事实链 A→B→C，每环有记录支撑。
4. 三类分析行动法（按问题类型分支）：工具失败→展开入参、看失败后行动（追问/改参数/原样重试），修正后成功与原样重试给不同建议；耗时/Tokens 高→比较相近任务、逐次看查询与结果，输入结果几乎不变才提复用/限重试/缩返回；业务质检→对照执行事实，先判断缺项来自知识、检索还是回答组织，材料不足记"待确认"。完成标准：带依据的候选问题清单 + 每项明确下一步（补知识/修工具/改策略/调流程/先补数据）。
5. 留样入候选集：单条或多条加入数据集，首次建集保留用户输入、Agent 输出、轨迹内容，需溯源再加应用/模型/工具名/Tokens 字段；写入时核对字段映射（最终答案别接成完整轨迹），写入后检查题目、回答、过程在同一条记录；失败例与正常例都保留。完成标准：候选集新增记录字段完整、来源可溯。
6. Pipeline 建设：先定行粒度（一行=一次任务/一段多轮/一条并行路径）→按交付需要选能力组合（投影/过滤、实例构建、去重、采样聚类、LLM 标注、周期执行），保留共同基础字段按用途分输出→用真实数据预览：普通任务质检人员能连续读懂、工具报错/无答复任务被保留（被过滤则调条件），业务负责人用样本确认"收到这样的表能否开始工作"→创建单次任务（预览时间≠执行时间）→运行后到数据集抽查→复用处理定义建周期任务，衔接历史补数范围与周期起始时间，日常监控执行历史并抽查新增。完成标准：固定输出数据集（行数、失败样本保留率）+ 字段映射核对记录 + 周期任务运行记录。
输出契约：相邻事实链结论（可复核）、候选样本集、固定格式质检数据集与周期管线。

## B（边界）
- 无可复现证据的主观调参是反模式（2.4.4 反例）：运行阶段不产出结构化 Trace/状态/成本事实，"感觉最近好了"式的调优无法归因到具体变更——本卡以"先有可读轨迹"为前提，采集缺位时先补观测而非硬分析。
- 工具错误与模型错误在 Trace 上现象相似（任务未完成），本卡只负责把证据链摆出来，"定责到层"须走 tuning-attribution 的验证实验；把采集问题、工具接口问题当成 Badcase 直接改 Agent 是显式警告。
- 数据到达不能靠开关推断："任务已创建"≠"数据已写入"；相似度搜索分数不是质量分，也不代表相同难度或错误；SessionID 不自动证明同任务、时间接近不证明记录完整——任务级结论须补业务事实与关联。
- 轨迹记录的是"一次执行发生了什么"：重新实验还需要题目、运行入口、环境与评分标准，本卡输出不能直接当实验结论用。
- 逐字通读长轨迹低效且易失焦；只看最终回答不看工具往返，会把"检索已有材料却未使用"误判为"知识库没材料"（两者改进方向不同）。
- 与相邻能力分工：样本的业务确认、rubric、黄金集、Badcase 分流与实验采用归 golden-badcase；单条复盘发现规则后的资产化（SQL/Skill/Workflow）归 controlled-evolution；AgentSpace/Loopie/百炼 Pipeline 等产品界面操作为 reference，本卡只保留方法层（验证次序、行粒度先行、预览驱动、条件从少到多）。
