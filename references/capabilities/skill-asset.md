# Skill 资产化与渐进披露（打包结构 + 三层披露 + Trace 沉淀四步 + 发布链反退化）

## R（原文摘引）
> Tool 告诉 Agent"能做什么动作"，Skill 告诉 Agent"在某类任务中如何正确使用若干动作"。（第 5 章 5.5）
> 当企业积累数百个 Skill 时，全部注入每轮 Context 会迅速耗尽窗口，也会让模型选择错误能力。（第 5 章 5.5）
> 一次任务成功，不意味着它已经成为可复用能力。（第 5 章 5.5）
> Skill 的评估不应只看是否被模型选中。（第 5 章 5.5）
> 不要先跨作用域召回再在生成端"提醒模型不要泄漏"，因为内容进入模型输入时，隔离已经失败。（第 5 章 5.6）

## I（解释）
1. **资产模型三不等式**：Skill ≠ 一段 Prompt（是含确定性脚本的工程包）；≠ Tool 别名（Tool 是单个动作，Skill 是"某类任务中如何正确使用若干动作"的方法）；不自带权限（只在当前用户/任务/环境允许时才能执行）。打包 = manifest（名称/版本/所有者/适用条件/所需工具权限环境/输入输出验收契约）+ instructions + scripts + templates + examples + tests。
2. **渐进披露三层**：发现层（模型只见名称/简述/适用条件/主要风险）→ 选择层（Harness 按任务/权限/环境解析候选并加载完整 Manifest）→ 执行层（用到某步时才读详细指令/脚本/模板）。选择不只靠语义匹配：还查模型兼容性、工具依赖、环境条件、租户许可、版本状态——Skill 可被发现但不可执行（如任务处于只读探索期）是合法状态。
3. **二分边界**：稳定、重复、可编码且失败代价高的步骤（格式转换/固定校验/权限查询/测试执行）沉淀为脚本；需理解模糊目标、比较方案、解释异常的保留为模型指令。脚本不藏在说明文本里不受控运行，仍须经行动平面与环境权限契约。
4. **沉淀四步 + 生命周期**：从 Trace 提取稳定步骤→移除任务 ID/临时路径/一次性判断→为脚本补回放测试→打包发布。生命周期 Draft→Test→Review→Publish→Observe→Update/Deprecate/Rollback；评估口径是启用前后任务成功率/步骤数/人工修改量/成本/安全事件，不是"是否被选中"；Trace 定位到具体 Skill 版本，latest 指针不入生产。
5. **六层作用域 + 反退化闭环**：资产可见性按 Global/Tenant/Project/User/Session/Task 六层划定，先确定调用身份再查询允许作用域；Context Policy/Memory/Knowledge/Skill 任何变更走与代码相同的发布链（校验→影响分析→离线回放→灰度→监测→回滚），防一次资产更新静默改变线上行为。

## A1（原书案例 + 合成演练）
- 原书·实践案例：Mamba Insight 运营分析 Data Agent——把近一年 500+ 条数据需求逐条标注，暗知识固化为 9 个结构化 Skill 文档 + 45 组 QA 对资产——从重复需求沉淀可复用能力的完整路径（c-37）；调研中 MCP 关注者 37% 而私有部署仅 9%、28% 提出服务管理与注册中心需求——能力资产的企业级配套（Registry/治理）是普遍缺口（c-11）。
- 合成演练（纸面推演，非原书案例）：客服团队 20 条成功的"退货政策咨询"轨迹——沉淀四步执行：提取稳定步骤（查政策条款→比对订单 eligibility→生成带条款号引用的回复）；移除工单号与临时路径；为脚本补 3 个回放用例；打包（manifest 含所需只读工具与输入输出验收契约）。三层披露配置（发现层仅 30 字描述+适用条件+风险）；发布走 Draft→Test→Review→Publish，评估=启用前后成功率/人工修改量对比；可执行性检查：要求只读政策库+任务非只读探索期→可发现且可执行。核验：Skill 不自带权限、无 latest 指针入生产、Registry 字段齐全（所有者/作用域/版本/依赖/权限需求/支持模型/测试结果/发布日期/弃用状态/使用效果，p1-159 十字段）。

## A2（情境应用）
场景：反复教 Agent 同一套做法、准备把成功轨迹沉淀成可复用能力时；Skill 数量增多挤爆窗口、误选增多时；给 Skill 做版本/回滚/下线治理时；资产（Prompt/知识/记忆/Skill）更新引发行为退化复盘时。
语言信号：「怎么把这次成功经验沉淀下来」「Skill 怎么打包/版本管理」「几百个 Skill 怎么不让模型选错」「资产更新怎么不影响线上」「skill packaging / progressive disclosure / asset lifecycle / 蒸馏沉淀」。
区分：state-layering 管 Memory/Knowledge 等单类对象的治理细则（写入六问/冲突遗忘/分库），本卡管跨资产的作用域/污染两端/删除派生链/发布链与 Skill 单资产的构建披露全流程；context-engineering 管 Selected Skill 层怎么进窗口，本卡的发现层决定候选集；多团队 Registry 平台/发现服务归第 15 章资产治理单元；自进化的审批/实验/回滚体系归第 22 章。

## E（执行步骤）
输入契约：候选 Trace（成功任务轨迹，含版本）、使用频率与重复度证据、目标使用者（哪些 Agent/模型/租户）、所需工具与权限清单、可投入的测试/评审资源。
1. 判沉淀价值：核对重复度（同类任务≥3 次或明确复用计划）、步骤稳定性、失败代价。完成标准：三项各有证据；一次性成功不得直接发布。
2. 沉淀清洗四步：提取稳定步骤→去特定化（移除任务 ID/临时路径/一次性判断）→脚本补回放测试→打包（manifest+instructions+scripts+tests）。完成标准：manifest 字段齐备；脚本测试可独立重跑。
3. 二分切分：稳定可编码步骤进 scripts，语义判断步骤进 instructions；脚本声明经行动平面执行的约束。完成标准：每步骤有归属与理由，无"藏说明文本里的可执行逻辑"。
4. 配置三层披露与六项可执行检查：发现层元数据（名称/简述/适用条件/风险）；选择层检查模型兼容/工具依赖/环境条件/租户许可/数据范围/版本状态。完成标准：存在"可发现不可执行"的显式判定逻辑（如只读探索期）。
5. 发布与评估：Draft→Test→Review→Publish；Observe 期按启用前后成功率/步骤数/人工修改量/成本/安全事件评估，很少被采用或降低效果的调整描述、缩范围或下线；资产变更走发布链（影响分析→回放→灰度→监测→回滚）。完成标准：Trace 可定位到 Skill 版本；无 latest 入生产。
输出契约：Skill 包（manifest+instructions+scripts+tests）+ Registry 条目 + 披露配置 + 评估基线记录。判停：无成功 Trace 或无测试/评审资源时不进入打包——回任务层先积累轨迹，宁缺勿脏。

## B（边界）
- 一次成功 ≠ 能力（5.5 红线）：一次性成功被当普遍方法沉淀，是记忆污染的资产版；清洗四步不可跳。
- 三类污染两端防护（ce-23）：写入端无来源识别/验证/作用域绑定、读取端无身份过滤/指令数据分离，任何污染都会被复用机制放大到后续任务。
- 撤回不能只降检索分数（ce-24）：删除须走派生链六步（禁读→删原文→清索引/缓存/摘要/派生→更新引用该资产的 Manifest 与 Skill→留最小审计→触发受影响 Agent 重验证）；权重衰减与彻底删除在策略中区分。
- 资产变更绕过发布链（ce-25）：Prompt/知识/记忆/Skill/Context Policy 更新不经影响分析与灰度直接生效，退化以成本上升、泄漏、Skill 误选等间接形式出现且难归因。
- 总体成功率掩盖分场景退化（ce-26）：一个资产可能提升某类任务却损害另一类，评估必须按场景/租户/风险/复杂度分层。
- Skill 无额外权限：不因打包成 Skill 绕过行动平面——当前用户无写权限或任务在 Plan Mode 只读期，Skill 照样不能写（与 action-plane 的交界红线）。
- 反场景：探索性/一次性任务、方法本身不稳定（规则上月一变）时不资产化；数百 Skill 全量注入窗口本身就是要用渐进披露解决的病，不是默认状态。
- 适用边界（原书视角）：六层作用域/Registry 治理以企业多租户为背景，个人项目可裁剪为 Global/User/Task 三层，但"身份先于检索"与发布链门禁不裁剪。
