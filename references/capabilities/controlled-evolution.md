# 受控自进化（五路改进方向 + 经验库挖掘核验 + 召回接入实验 + 四类资产化 + Badcase 局部修改 + 三档成熟度四确认）

## R（原文摘引）
> 选择方向时，先检查 Agent 是缺方法、重复生成相同代码，还是被工具或运行环境阻碍。（23.1）
> 经验库适合保存"遇到什么情况，可以怎样处理"。它帮助不同任务复用方法，也让维护者能够从来源判断方法是否可靠。（23.2）
> 接入遇到问题时，可按现象定位：没有发起查询，检查 Skill 是否启用、触发说明和工具权限；查询失败，检查地址、空间、库名和凭证；……命中了经验却没有采用，检查返回内容是否进入上下文、前提是否适用。（23.3）
> 先保留一组不使用经验的运行作为 Baseline，再用相同模型、工具和任务测试候选策略。……如果某条经验让 Agent 反复扩大范围、照搬历史参数，先缩小它的使用范围或在接入侧停止采用，保留出问题的任务作为反例。（23.4）
> 面对已确认的 Badcase，先写清楚"应该在哪一步采取什么行动"。……验证任务应触发原来的问题，才有理由采用修改。（23.6）
> 每次决定采用时，负责人确认四件事：目标问题是否改善，原有任务是否退化，额外代价是否可接受，目标 Agent 是否实际使用了被验证的内容。（23.7）

## I（解释）
1. **方向由现象决定，共五路**：相似故障总要重新探索→建经验库；经常漏前置检查/测试/结果确认→补 Skill；反复编写相近查询脚本→整理 SQL 模板/Script；固定流程总要人盯→接 Workflow；重复提交、恢复后状态不明→改 Harness。入口动作是业务负责人先定义"什么算完成"，维护者从 Trace 对照成功与失败任务定位缺口。
2. **经验库的三要素与核验**：每条经验要能回答"解决什么问题、建议什么动作、什么条件下适用"；挖掘结果必须回到来源 Trace 验证——动作是否真的出现、结果是否支持建议（"查不到日志时扩大时间窗口"要区分当时是窗口太短还是根本没采集，前者复用查询方法，后者先修接入）。来源与不适用条件防止把一次现场处置变成所有任务的固定要求。
3. **召回接入按现象四分定位**：未发起查询→Skill 启用/触发说明/工具权限；查询失败→地址/空间/库名/凭证；查到为空→库中内容/查询表达/过滤范围；命中未采用→是否进入上下文、前提是否适用。分开定位避免反复调阈值却没解决接入问题；Agent 口头说"参考了历史经验"必须对应真实调用。
4. **召回是否划算由实验决定**：留一组不用经验的 Baseline，同模型/工具/任务测候选策略（新 Session + 重置任务状态防污染）；五个可调因素——召回阈值、返回数量、触发时机、放置位置与长度、使用要求（明确是历史参考、采用前检查当前条件）；验收按业务指标 + 完整任务成本（含召回开销），未参与挖掘的同类任务独立验证后才采用。
5. **稳定方法资产化四类产物**：SQL 模板（重复计算）、Script/工具（分页解析汇总）、Skill（任务方法：何时用、先确认什么口径、如何核对）、Workflow（固定步骤含异常分支）；按最大开销选先交付项，不必一次交齐；采用前换参数重跑 + 异常样本 + 新任务端到端验证。
6. **Badcase 驱动局部修改**：先写清"应该在哪一步采取什么行动"，修改逐项对应执行证据（不整份重写成通用注意事项）；用三组任务验证——目标 Badcase、原本成功的任务、不应触发该 Skill 的任务（防修复变成全局负担）；Harness 类问题改恢复语义（区分未开始/结果未知/已完成，结果未知先核对业务状态）。"受控"的含义：一切候选修改经实验验证、四确认通过才采用，异常交负责人，且始终保留恢复原配置的办法；自动化按手动→半自动→受控自动三档渐进。

## A1（原书案例 + 合成演练）
- 原书实践篇：塔斯汀万店智能运维闭环——每次诊断沉淀（上下文，人工根因，AI 准/不准评价）三元组形成历史根因库，下次诊断优先读取，并按 service+alert_type 统计准确率反哺产品改进；排障 SOP 封装为 Skill（Redis/连接池/OOM/支付超时），新人凭一键 RCA 报告即可研判；同类告警收敛率超七成（c-32，RCA 准确率数字未说明）。同章 Agentic SOC 以"受控自主四类边界（目标/质量/权限/停止）"演示自进化的治理形态（c-27）。
- 合成演练（原书未提供该场景记录，按 23.1/23.6/23.7 规则推演）：数据分析 Agent 写 SQL 前不核对字段口径，报表时区错误。现象=漏前置检查→选补 Skill。先写清"应在生成 SQL 前查询 schema 并确认口径"，生成逐项对应执行证据的局部修改（不整份重写）；三组任务验证——目标 Badcase、原成功任务、不应触发该 Skill 的任务。若同时存在"会话恢复后重复提交"，走 Harness 分支：区分未开始/结果未知/已完成，结果未知先核对业务状态。采用前四确认（问题改善/不退化/代价可接受/Agent 实际使用了被验证内容）并保留恢复原配置办法。可核验输出 = Skill diff、三组任务验证记录、采用决策记录。

## A2（情境应用）
场景：相似故障每次都从头探索、想"把踩过的坑存起来"时；要让 Agent 在任务开始或遇到相关失败时能召回历史做法时；Badcase 确认后要改 Skill/Harness 但怕改坏别处时；团队想用系统自动挖掘经验、生成候选时；考虑要不要让调优流程全自动时。
语言信号：「把经验存下来给 Agent 用」「经验库 / 历史根因库」「这次 Badcase 怎么改 Skill」「经验召回有没有效果」「能不能自动调优」「experience library / recall / skill 沉淀 / self-evolution / 自进化」。
区分（初稿）：tuning-attribution 处理模型主线（SFT/RL/蒸馏/发布），本卡处理 Agent 主线（经验库/Skill/SQL/Workflow/Harness），f4-28 五路径映射是两卡衔接——五路中无"训练"，训练触发归前者；golden-badcase 确认 Badcase 并提供实验基础设施，本卡直接消费其产出做定向改造；trajectory-pipeline 提供挖掘所需的可用轨迹。

## E（执行步骤）
输入契约：业务完成标准（业务负责人给出）+ 成功/失败任务对照轨迹 + 已确认的 Badcase（含补好的正确要求，来自 golden-badcase）；缺业务确认的 Badcase 先回 golden-badcase，不自行定"应该怎样"。
1. 选改进方向：业务定义"什么算完成"，维护者对照成功/失败轨迹定位缺口类型，按现象-方向-期望变化表选路（经验库 / Skill / SQL 模板 / Workflow / Harness，可组合）；查询工具本身缺能力则由工具维护者补。完成标准：方向决策 + 现象-缺口对照依据。
2. 建经验库并核验（选经验路时）：确认轨迹可用（用户目标、关键工具调用与结果可见）→ 选一致的来源范围（近期、同类任务，覆盖成功/失败/失败后恢复，不为凑条数纳入规则已过时的历史）→ 抽查代表经验三件事（解决什么/建议动作/适用条件）→ 回 Trace 验证动作真出现、结果支持建议。完成标准：核验记录；结果只有"仔细分析"等泛化要求时补代表性轨迹与问题信息。
3. 召回接入与实验：安装召回能力→配置库地址与凭证→启用 Skill 与工具权限→用已检查过的经验做真实查询验证（返回内容与来源；再观察完整任务在哪一步使用）→按四类现象定位接入故障。实验：留不用经验的 Baseline，同模型/工具/任务（新 Session、重置状态）调五因素，业务指标 + 完整任务成本验收，未参与挖掘的同类任务独立验证后采用。完成标准：召回配置决策 + 一次"经验影响行动"的验证记录。
4. 资产化（做法稳定后）：按最大开销选先交付项整理为 SQL 模板/Script/Skill/Workflow（附字段含义、依赖、异常处理与调用示例）；Agent 可起草，熟悉业务与工具的人审查后入库；采用前换一组参数重跑、加入空数据/重复记录/字段变化样本、再从新任务端到端检查 Agent 能找到资产并正确调用。完成标准：资产清单 + 三层验证记录。
5. Badcase 局部修改：写清"应该在哪一步采取什么行动"→ 用原 Skill + 失败轨迹 + 相邻成功任务 + 预期行为生成局部修改，逐项对应执行证据 → 三组任务验证（目标 Badcase / 原成功任务 / 不应触发任务）；Harness 类按恢复语义分支（未开始/结果未知/已完成），可控环境模拟提交前中断、提交后未保存等场景验收。完成标准：修改 diff + 三组验证记录；验证任务确实触发原来的问题。
6. 采用四确认与档位治理：确认目标问题改善、原有任务不退化、额外代价可接受、Agent 实际使用了被验证内容；记录原版本/候选差异/实验结果/采用范围，保留恢复原配置的办法。自动化按三档渐进（手动→半自动→受控自动），先自动化高频、范围清楚、结果易检查的动作；跨资产自动实验/生产发布接入自有交付系统，异常交负责人。完成标准：采用决策记录 + 恢复预案 + 当前档位说明。
输出契约：方向决策、经验库与核验记录、召回配置与实验结果、资产清单、Skill/Harness diff 与验证记录、采用决策与恢复预案。

## B（边界）
- "受控"是定义而非选项（2.4.4 反例）：让 Agent 在生产中自由修改自己——任何由模型/反馈/轨迹生成的 Prompt、Memory、Skill、Harness 补丁都是候选变更，未经可复现评估、安全检查、版本化、灰度与可回滚发布就进生产，自进化退化为不可控线上试错；线上数据无差别自动回灌同类（17.5.5 反例：需四道触发条件）。
- 记忆/经验污染（5.6 反例）：错误推测、失败轨迹、恶意输入被写入并长期当经验复用——写入必须有来源识别、核验与候选区；工具返回的文本不应被提升为行为规则。
- 经验的适用边界：缺来源与不适用条件的经验会把一次现场处置变成所有任务的固定要求；经验让 Agent 反复扩大范围、照搬历史参数时，缩小使用范围或接入侧停用并留反例——调整的是具体使用方法，不是笼统判断"经验有没有用"。
- 经验出问题的处置陷阱：只暂停挖掘不会停止旧经验继续影响任务，必须调召回或采用设置（23.7 显式警告）。
- 召回不一定划算：短任务多查一次可能净亏；召回开销要计入完整任务的耗时/Token/费用；出问题经验停用要留反例供后续校准。
- 局部修改纪律：整份重写成"通用注意事项"会丢失针对性且难以验证；验证任务不触发原来的问题就没有采用理由；只用目标 Badcase 验证不查"不应触发的任务"，修复会变成全局负担。
- 与相邻能力分工：模型训练路线（SFT/RL/蒸馏）不在本卡，训练触发判断归 tuning-attribution；Badcase 的确认、实验平台与黄金集归 golden-badcase；轨迹可用性检查依赖 trajectory-pipeline 的产出；agentloop-experience Skill 安装、API Key/白名单配置等为阿里云产品操作，判 reference。
