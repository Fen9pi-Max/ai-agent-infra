# AI 网关三语义治理（准入四步 + 预算不变量 + 重试预算 + 任务账本）

## R（原文摘引）
> 网关只保证准入、转发与记录的一致性，既不能仅凭请求成功断言任务完成，也不能替代执行系统保证状态恢复。（第 9 章 9.1.1）
> 三种语义可以部署在同一数据面，也可以由不同组件承接。统一的关键不是所有能力位于同一进程，而是身份映射一致、策略边界清晰、调用记录能够关联。（第 9 章 9.1.3）
> 错误分类应先于重试。……如果 SDK 客户端对一次逻辑调用最多尝试 3 次，网关对每次转发又最多重试 3 次，那么一次用户可见的调用最多会到达上游 9 次……重试次数、并发压力和费用会以乘积方式放大。（第 9 章 9.2.4）
> 可用额度 = 已授权额度 − 已结算消耗 − 在途预留；准入条件 = 本次最大可计费消耗 ≤ 可用额度。检查和预留必须在同一原子操作或等效一致性事务中完成。（第 9 章 9.2.6）
> 权限应取调用者原有授权、工作负载授权、任务委托范围和资源侧限制的交集，不能由模型声明的身份、工具描述或 clientInfo 扩大。（第 9 章 9.3.5）
> 审批未决的请求不得转为实际执行。……批准不意味着后续必定放行。等待期间身份可能过期、参数可能改变、预算可能被其他调用占用，因此执行前必须重新准入。（第 9 章 9.5.4）
> task_id → session_id → turn_id → model/tool call → attempt_id 这是一条分析下钻路径，不强制所有系统采用相同存储树。（第 9 章 9.4.5）

## I（解释）
1. **三语义是分析框架不是三个产品**：LLM Gateway（模型路由/限流/容灾/计量，不判业务成功）、MCP Gateway（协议代理/工具授权，发现≠授权）、Agent Gateway（入口身份/路由/亲和/并发/跨调用关联，不定义 Task/State/恢复语义）。可同数据面也可分组件；统一只看四条件：身份映射一致、策略边界清晰、调用记录可关联、同一上游调用不因穿过多组件被重复计费。
2. **职责红线**：网关只做准入、转发、记录。不凭请求成功断言任务完成、不解释业务 State、不定义 Checkpoint；请求成功率与业务任务完成率分开统计。
3. **可靠性三律**：错误分类先于重试（限流看重置时间与替代端点、服务端错误看调用语义、认证错误终止修凭证、上下文超限交应用决策不截断历史）；"尚未收到响应体"≠"上游未执行"；未经验证的兜底返回可解释失败，不以"自动降级"为名改业务契约。多层重试乘积放大（3×3=9），预算必须跨层传递：总截止时间用绝对时间、剩余额度按 call_id 原子扣减、每次尝试有独立 attempt_id。
4. **预算四档声明承诺**：速率限制/token 时间窗/余额配额/严格预算机制不同——"先查后扣"保证不了硬上限（余额 100 时两个 max-80 并发请求可耗 160）；严格档要求检查与预留同一原子操作，预留覆盖输入+受约束最大输出+其他计费项，多层额度同时验证，token 配额与金额预算分开，结果未知不因租约到期退款。
5. **MCP 准入与权限**：认证—协议校验—授权—转发四步各自独立，逐请求元数据不能替代身份与权限判断；有效权限取四方交集；tools/call 必须再次鉴权；REST 转 MCP 要参数级策略（限主机出站防 SSRF、支付限金额/收款方/审批/幂等键）；网关要成为不可绕过执行点须满足五前提（凭证不下发、出口受控、服务发现收敛、直连禁止、旁路审计）。
6. **审批是持久业务状态**：未决不执行、挂起不占连接、批准后执行前重新准入（身份/委托/参数摘要/预算）、超时不自动降级为只读、结果未知交业务对账。
7. **账本与变更闭环**：归因链路 task_id→session_id→turn_id→call→attempt_id，task_id 权威在业务应用，客户端关联头绑定认证主体防伪造；候选变更走六阶段（观测→建议→构建验证→治理授权→灰度→反馈），Evaluation 无发布权；回滚不止恢复配置，还要处理已执行副作用、未结算额度与运行中任务。

## A1（原书案例 + 合成演练）
- 原书调研案例（转述）：2026 Agent 开发者调研（1906 份问卷）——多模型路由与自动降级被 63% 企业列为最需要的网关能力，为比例最高单项（c-05）——网关需求侧证据。信永中和：AI 网关统一模型接入、多模型主备切换、按部门/Agent/模型 Token 统计支撑成本治理、统一认证权限、敏感信息识别与内容安全检测、全程调用审计留痕，一周联调上线（c-35）——三语义落地的平台路径，效率数字未说明。两例均为报告转述。
- 合成演练（纸面推演，数值可复算）：平台含 3 个模型供应商、30 个 MCP 工具（含支付类）、成本按项目归集。推演并核验：SDK 3 次×网关 3 次=上游最多 9 次→总截止时间取绝对时间、剩余额度按 call_id 原子扣减；授权 1000、已结算 200、在途 300→可用 500，最大消耗 450 准入、550 拒绝；余额 100 时两个 max-80 并发请求经"先查后扣"最终耗 160→支付类工具走严格预算档；MCP 准入四步（认证→协议校验→授权→转发）；有效权限=调用者∩工作负载∩委托∩资源侧；支付工具参数级策略（金额阈值+收款方白名单+审批+幂等键）；审批挂起结束连接、批准后重新准入；账本 task_id→session_id→turn_id→call→attempt_id，task_id 权威在业务应用。产出三语义职责矩阵+重试预算表+预算档位+审批状态机+账本 schema，均可独立核验。

## A2（情境应用）
场景：多模型/多供应商要统一入口、路由与降级时；重试风暴或预算超支（含 DoW 攻击）要设防时；MCP 工具要统一鉴权与参数级管控时；高危操作审批要与流量准入结合时；Token 成本算不到项目/部门头上时；路由或提示词变更想安全灰度时。
语言信号：「重试把上游打爆了」「预算怎么硬上限」「工具能不能调谁说了算」「审批通过了就一定放行吗」「成本归集到项目」「gateway / retry storm / quota / MCP authorization / cost attribution」。
区分：async-completion 管完成语义五层——本卡只记账不判完成；state-storage 管状态权威与 Checkpoint 结构，本卡不解释业务 State；multi-agent-org 管团队权限模型，本卡管单点流量的准入/授权/计费治理语义；agent-comm 管传输与交互语义选型，本卡不管通道。

## E（执行步骤）
输入契约：流量清单（模型供应商、MCP 工具及风险等级、Agent 入口）、身份体系现状、预算主体层级（组织/团队/项目）、审批流程现状、现有网关/运维设施。缺"工具风险等级"或"财务归属维度"时先补齐，不做静默默认放行。
1. 画三语义职责矩阵并核对统一四条件：每项能力标注落在哪个语义、由哪个组件承接；四条件逐项打勾。完成标准：矩阵无悬空能力，四条件结论成文。
2. 定重试与超时策略：错误分类表（限流/服务端/认证/上下文超限/无响应体）→ 各类重试许可 → 预算跨层传递（绝对截止时间+call_id 原子扣减+attempt 独立标识）→ 五类超时分层（连接/首字节/TTFT/流式空闲/总截止）。完成标准：分类表+每逻辑调用的最大上游尝试次数上限可复算。
3. 定预算档位：按风险声明各主体用哪一档；严格档落实原子预留不变量（公式+预留覆盖范围+多层验证+token/金额分离+结果未知保守等待）。完成标准：档位声明表+严格档实现要点，最大消耗估算方法注明依据。
4. 定 MCP 准入与授权：四步流程、权限交集规则、tools/call 再鉴权、参数级策略（按工具类别给约束）、不可绕过五前提核查（不满足则如实声明"只是集中入口"）。完成标准：准入流程图+策略清单+五前提结论。
5. 定审批状态机：待审批/批准（重新准入后转发）/拒绝/超时或撤销/结果未知五分支，记录绑定工具版本与参数摘要，回调认证防重放。完成标准：状态机+每分支动作与审计字段。
6. 建任务账本：归因链路、标识权威分工、客户端关联头绑定认证主体、缺关联记待归因、区分原始 usage/估算/价格版本。完成标准：账本 schema + 防伪规则。
7. 定变更闭环：六阶段链路+每步准入条件、自动化只在预批准范围幅度内、回滚清单含副作用/未结算额度/运行中任务。完成标准：闭环流程+回滚检查表。
输出契约：职责矩阵、重试预算表、预算档位声明、准入与授权策略、审批状态机、账本 schema、变更闭环。判停：无身份体系可依托时先建主体映射，网关策略不能建在匿名流量上。

## B（边界）
- 三语义是分析框架，不是成熟度阶梯，不要求依次建设三个独立产品（9.1.3/9.1.5）；建设进度按独立验收目标衡量（凭证不再分散、用量可归属、拒绝可追溯），不以插件数量衡量。
- 未经验证的兜底路径必须返回可解释失败，不得以"自动降级"为名改变业务契约（9.2.4）；切换 provider 前先验证工具/结构化输出/数据地域兼容。
- 网关非天然不可绕过：Agent 仍持直连凭证与网络出口时，网关只是集中入口（9.3.5 五前提）；框架/网关/资源服务器各留检查构成纵深防御，任何一层不得宣称整链绝对安全。
- 反例（第 14 章，ce-58/67）：拒绝钱包攻击——单请求限流对任务级累计消耗不可见，需任务级预算与异常行为阻断；Agent 聚合全部下游权限成"超级应用"，单点沦陷等于全域沦陷，出站凭证须按服务逐次收敛。
- 指标红线：TTFT≠HTTP 首字节、缺 usage 不记零、客户端取消不证明上游停止、只用 HTTP 200 判成功、只记放行不记结果、一条 Trace 当完整 Task——五类误区（9.6.3）；审计材料≠业务 Evidence，Outcome 由成功标准与 Verifier 判定。
- 审批超时不得自动降级为只读执行——那会改变请求含义（9.5.4）。
- 平台必要性假设（适用边界）：第 9 章面向企业级多供应商/多租户平台。单团队小规模可从 SDK 内超时+简单预算起步，网关分阶段建设（先凭证托管+模型入口），不必一步到位。
- 阿里云产品视角：HiRoute 为书中计划化委派的模式示例名、非产品操作；实践篇网关案例锚定阿里云产品栈——吸收机制（档位、不变量、准入四步），具体产品能力自行验证；OTel gen_ai.* 处于演进态，采用须固定版本。
