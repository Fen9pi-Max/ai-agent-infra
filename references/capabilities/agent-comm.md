# Agent 分布式通信四面选型（四面 × 四档 + 契约六要素 + 续传点）

## R（原文摘引）
> 四个通信面分别是人机面、协作面、能力面和内构面。协议只提供其中部分契约，具体的持久化、路由、授权和恢复仍需由实现补齐。（第 12 章 12.2.1）
> 以下四档用于区分接口呈现和解耦程度，不是成熟度等级。一个系统可以同时使用多档语义。（第 12 章 12.2.2）
> 需要分别检查两个条件：是否有独立于连接的任务句柄，以及是否有事件续传位置。……流结束与业务任务结束是不同边界。（第 12 章 12.2.3）
> 无论落在哪一档，一份可用于生产的 Agent 通信契约都需要回答六个问题。这六项既是设计检查表，也是判断某个协议"缺什么"的量规。（第 12 章 12.2.5）
> 命名通道……续传点 (通道, 序号) 构成可恢复位置……结果保留……未确认重投。（第 12 章 12.4.3）
> 任务在服务端独立存在，前端连接只是当前的一个观察视图；连接断开只影响可见性，不影响任务推进；重连后通过续传点补齐遗漏事件。（第 12 章 12.8）
> 协议放弃承担状态，不意味着状态消失，而意味着状态责任转移到应用层的显式句柄，并由应用选择持久化后端。（第 12 章 12.5.3）

## I（解释）
1. **先重检四假设再沿用老办法**：调用耗时是否有界（长任务不能靠延长同一 HTTP 请求承载）、会话是否依赖当前连接（连接只是当前传输路径）、等待期间占用哪些资源（连接/内存/保留环境/存储分别测量）、端点会不会变（扩缩容/接管/沙箱重建改变物理地址，契约要把业务标识与物理端点分开并定义重新寻址）。
2. **四面 × 四档是选型地图**：按通信双方身份分四面——人机面（增量可见与随时打断要求最高而前端连接最不可靠）、能力面（Agent↔工具，毫秒级查询与分钟级任务同协议）、协作面（Agent↔Agent，任务天然长跑而点对点信任组合增长）、内构面（服务端组件间，海量会话的通道元数据成本与多租户隔离）。按解耦程度分四档——S1 请求-响应、S2 请求域流式、S3 任务句柄、S4 持久通道。一个系统可同时用多档；选型=逐段链路定位面与档，回答"状态寄存何处、以什么方式失效"。
3. **判别两条件防直觉误判**：token 流与 SSE 只说明结果怎么到达，不说明任务是否独立于连接。检查一：有无独立于连接的任务句柄（能否稍后查询）；检查二：有无事件续传位置（能否补齐保留范围内事件）。有句柄不一定能重播事件，有事件序号不保证业务状态可恢复。
4. **契约六要素是量尺**：标识（会话/任务/轮次/消息从属；任务标识绑死消息线程会限制后台执行）、顺序（通常限任务或会话内）、投递保证（至少一次+去重键等，同系统不同通道可不同强度）、续传点（断连后从哪继续，与任务查询分开声明）、生命周期（通道创建/过期/销毁前核对活跃任务）、背压（过载怎么减速）。缺哪项，就是该协议"缺什么"的答案。
5. **状态承载三位置决定恢复方式**：连接与进程内存（断连即失，靠查询或重试）、外部状态存储（按任务标识取可信状态按恢复契约继续）、持久消息通道（保留期内补读去重）。三者可关联不可互相替代；只有完整事件溯源契约下通道日志才是权威状态源；消息重播不恢复进程、不撤销外部操作。协议无状态（如 MCP 移除会话）= 状态责任转移到应用显式句柄+自选后端。
6. **协议选择的根因与陷阱**：MCP 垂直（Agent→工具）无状态核心利于实例间分配，A2A 水平（Agent↔Agent）有状态任务需要可查询生命周期——方向差异源于通信形态，不是路线优劣。A2A 流式属 S2（进度可见）、推送通知属 S3 增强（只是"去拉取"的触发器，结果可寻址性由任务查询保证）。协议 Task/Message/Artifact 是互操作语义，须与业务同名对象经适配层显式映射，不能直接当业务权威。
7. **规模化与结构**：通道键=治理单元（按什么标识命名，就按什么粒度隔离/限流/观测/回收）；海量会话用轻量逻辑通道挂少量父主题+空闲回收，排除三种直觉方案；手脑分离把决策循环（会话=追加事件日志+无状态 Harness）与工具执行（沙箱=普通工具）拆进程，以 MQ 保序投递相连；人机面"连接不是任务边界"——任务在服务端独立存在，执行期引导走流式、阻塞式审批走持久化待办。

## A1（原书案例 + 合成演练）
- 原书机制案例（转述）：手脑分离四层落地引自 Qoder 案例——脑（Agent Runtime 决策推进）/路（MQ 保序投递承担等待与背压）/手（Sandbox Worker 完成即释放）/底（Session State 持久化事实），动机含 harness 老化与资源需求差异（12.7.2，机制已抽象为通用四层模型，案例名保留为出处语境）。
- 原书实践篇案例（转述）：GOAI 大赛"总工之眼"（建筑工程多专业智能会审）——跨专业分歧不做平均处理：各专业 Agent 的不一致意见连同依据保留，提交真人总工程师复核、裁决并留痕，基于 AgentTeams 形成可追溯运行记录（第 29 章 29.3.3，c-15）——人机面"阻塞式审批走持久化机制"与协作面"消息留痕、裁决作为任务状态"的真实运行；注意该案例的重心在裁决机制而非通道选型，通道细节未说明。
- 合成演练（纸面推演）：系统含多端前端会话、Agent 调 12 个 MCP 工具、经 A2A 委派子任务给另一 Agent、会话量十万级。推演产出：人机面按"连接只是观察视图"定结构（任务服务端独立存在，重连按续传点补齐）；能力面按"协议无状态≠应用无状态"定状态责任（MCP 无会话后任务状态在应用侧句柄+自选后端）；协作面按判别两条件定语义（推送通知只是"去拉取"触发器，结果可寻址性由任务查询保证），协议 Task 与业务 Task 建映射；内构面十万级会话排除三种直觉方案（每会话一主题/广播/每 Session 消费组）→轻量逻辑通道挂少量父主题+空闲回收；每段链路填契约六要素表，缺项即该协议"缺什么"。选型结论可逐面逐档核验。

## A2（情境应用）
场景：前端断线重连后要补齐 Agent 输出时；纠结某段链路用请求-响应、SSE 流、任务句柄还是消息队列时；Agent 调工具/委派给其他 Agent 选协议（MCP/A2A/REST）时；会话量大到主题/消费组爆炸时；把决策循环与工具执行拆进程时；为某个协议做"缺什么"评估时。
语言信号：「SSE 断了任务还在吗」「流结束就是任务完成吗」「Agent 之间用什么协议通信」「十万会话消息通道怎么设计」「MCP 和 A2A 怎么选」「streaming / task handle / resume point / message bus / MCP vs A2A」。
区分：multi-agent-org 管团队秩序（分工/委派/聚合），本卡管协作双方的传输与交互语义；async-completion 管任务模型与完成语义，本卡的 S3 任务句柄/续传点是其通信侧判据；ai-gateway 管准入/授权/计费治理语义，本卡不管策略执行；runtime-sandbox 管执行环境，本卡手脑分离中的"手"引用其沙箱结论。

## E（执行步骤）
输入契约：通信段清单（双方身份、预估时长、断连容忍度、结果获取方式）、会话量级、现有协议/中间件约束、恢复要求。缺"断连后业务预期"（取消执行还是可查结果）时先向业务确认，不从传输形式推断。
1. 重检四假设：逐段确认耗时有界性、会话-连接关系、等待资源、端点稳定性。完成标准：四假设各有结论，不成立项列出。
2. 逐段定位面×档：按双方身份定面，按判别两条件（任务句柄？续传位置？）定档；同步三条件核查（时限内可完成/是否需独立伸缩削峰/失败结果可否确认）。完成标准：面×档选型地图，每段注明判别依据。
3. 填契约六要素表：每段链路逐项填标识/顺序/投递保证/续传点/生命周期/背压。完成标准：六列无空项；缺项即记录为该协议缺口与补齐责任方。
4. 定状态承载与恢复：每段状态落在内存/外部存储/持久通道哪一位置，断连后走查询、重放还是重试；协议无状态时明确应用侧句柄与后端。完成标准：状态位置表+恢复条件说明。
5. 需要持久通道时核对四最小语义并算异步代价：命名通道、续传点(通道,序号)、结果保留、未确认重投；对照五类代价（每跳延迟/幂等要求/保留策略/故障传播/可观测缺口）逐项给动作。完成标准：四语义核验结论+代价对策清单。
6. 海量会话治理：定通道键粒度（会话/用户×模型/任务），评估轻量通道方案（父主题复用、双向索引、空闲回收），排除三种直觉方案要留排除理由。完成标准：通道键决策+容量估算。
7. 人机面与手脑分离定结构：人机面按"连接不是任务边界"设计（服务端任务+快照与增量事件+续传点；执行期引导走流式、阻塞审批走持久待办）；需要拆进程时按脑/路/手/底四层分配职责并显式定义工具调用标识、接收确认、取消与未知状态处理。完成标准：结构图+分离时的消息契约。
输出契约：面×档选型地图、契约六要素表、状态位置与恢复表、通道治理方案、人机面/手脑分离结构。判停：无法描述断连后的业务预期时，先回 async-completion 明确任务模型，再做通信选型。

## B（边界）
- **概念模型声明（重要）**：原书第 12 章自述四面×四档"是本章分析分类而非行业标准分层"，S1-S4"不是成熟度等级"；MCP/A2A 规范本身在演进（书中引用 MCP 2026-07-28 版本行为）。本卡输出的是选型量尺与检查表，不是可照抄的行业标准实现——任何"按此分层即合规"的宣称都超出原书。
- 反例（凭传输形式推断业务语义，本章核心反模式）：流结束≠任务结束、429 或连接失败≠工作区丢失、收到推送≠结果已送达、协议任务完成通知≠业务 Outcome——断连是否取消执行、能否查结果由服务契约明确，不从传输形式推断。
- 反例（12.7.3，海量会话三种直觉方案失效）：每会话一个标准主题（元数据先压垮控制面）、广播过滤（单节点成容量上限）、每 Session 独立消费组（等于重建路由）；并列反模式：会话与常驻进程一对一绑死（"宠物"式进程）。
- 协议对象≠业务对象（11.6.2）：A2A 的 Task/Message/Artifact 与业务同名对象生命周期和权威来源不同，须适配层映射；Agent Card 声明不能仅凭之建立可信身份。
- 异步不是免费的（12.4.4）：每跳延迟、幂等要求、保留策略、故障传播、可观测缺口五类代价——只在实际需要的链路加机制（同步三条件的递进原则）。
- 人机面前端副本不是权威状态：事件格式、运行中断与消息续传是不同能力，精确补读需额外约定事件标识与保留窗口。
- 平台必要性假设（适用边界）：轻量通道、手脑分离面向高并发服务端场景；单进程原型用函数调用+简单回调即可，不引入消息总线。
- 阿里云产品视角：Qoder 案例与 MCP/A2A 版本细节为书中转述语境；机制已抽象为通用模型，具体协议版本行为与产品能力须按当前规范自行核验，不因书中描述假定稳定。
