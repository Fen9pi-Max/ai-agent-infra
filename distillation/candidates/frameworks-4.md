- id: f4-01
  title: 调优归因次序：先环境→再 Harness→后模型
  type: framework
  source_chapter: 调优篇导读（另见 17.1.1）
  source_quote: |
    "两条主线不是先后依赖，也没有高下之分，进入哪一条由归因决定：先排除能够独立复现的执行环境故障，再检查 Harness 是否提供了充分信息与可靠控制，最后才判断是否属于模型能力缺口。"
  summary: |
    面对 Agent 效果问题时的固定归因次序：第一步排除可独立复现的执行环境故障（工具/服务/资源）；
    第二步检查 Harness 是否给了模型充分信息与可靠控制（上下文/工具协议/状态/重试停止）；
    第三步才把跨任务反复出现的同类决策错误归因为模型能力。
    把问题落到正确的对象上，是避免"用模型训练弥补系统工程问题"或"用系统补丁掩盖能力短板"的前提。
  tags: [attribution, decision, tuning, mental-model]
  inputs: [失败现象, 运行轨迹]
  outputs: [优化对象结论（环境/Harness/模型）]
  steps:
    - 排除可独立复现的执行环境故障
    - 检查 Harness 信息供给与运行控制是否充分
    - 确认错误在信息、接口、反馈均充分时仍跨任务稳定出现，才归因模型

- id: f4-02
  title: 失败归因三层验证表（执行环境/Harness/模型）
  type: framework
  source_chapter: 17.1.1（表 17.1-1）
  source_quote: |
    "执行环境：绕过模型直接调用相应工具或服务；若故障仍能复现，则归因于执行环境。Harness：固定模型和执行环境，修正上下文、工具协议或运行控制；若问题明显减少，则归因于 Harness。"
  summary: |
    每层归因配一个可操作的验证方法：执行环境层"绕过模型直调工具看故障是否复现"；
    Harness 层"固定模型与环境，只修正上下文/工具协议/运行控制，看问题是否明显减少"；
    模型层"固定 Harness 与环境重复测试或替换模型，错误跨任务变体稳定出现或随模型显著改善才归因模型"。
    失败现象本身不能直接决定归因（如工具选错可能是能力不足也可能是描述含混），必须现象+判定条件+验证结合。
  tags: [attribution, troubleshooting, verification, table]
  inputs: [失败现象, 轨迹与调用记录]
  outputs: [归因结论与优先优化对象]
  steps:
    - 假设执行环境故障：绕过模型直调工具验证复现
    - 假设 Harness 问题：固定模型与环境修正上下文/协议/运行控制
    - 假设模型问题：固定 Harness 与环境做重复测试或换模型对照

  title: 模型—Harness 边界四组对照实验
  type: framework
  source_chapter: 17.1.1
  source_quote: |
    "对于模型与 Harness 边界不清的问题，可以在执行环境稳定的前提下组织四组对照：原模型与原 Harness、原模型与候选 Harness、候选模型与原 Harness、候选模型与候选 Harness。"
  summary: |
    当问题无法明确归因模型还是 Harness 时，在执行环境稳定前提下组织 2×2 对照：
    原模型+原 Harness、原模型+候选 Harness、候选模型+原 Harness、候选模型+候选 Harness，
    在一致任务集和预算下比较模型改动、Harness 改动及二者交互的收益。
    若候选模型需要专门 Prompt 或协议适配，应把适配纳入对应配置记录，避免把组合变化全部归因于模型。
  tags: [attribution, experiment, ablation, decision]
  inputs: [候选模型, 候选 Harness, 一致任务集与预算]
  outputs: [模型改动/Harness 改动/交互收益的分离结论]
  steps:
    - 固定执行环境
    - 构建 2×2 四组配置（原/候选模型 × 原/候选 Harness）
    - 同任务集同预算比较，拆分主效应与交互效应

- id: f4-04
  title: 模型决策能力四分类
  type: framework
  source_chapter: 17.1.2
  source_quote: |
    "在“接收观察—作出决策—获得反馈—调整决策”的循环中，可将模型问题归纳为四类"
  summary: |
    把笼统的"Agent 效果不好"拆为四类模型决策能力缺口：
    ①任务理解与约束识别（自然语言→可执行目标、完成标准、前提与边界，必要时提出澄清）；
    ②工具使用与反馈理解（选工具、生成合法参数、判断返回是否足以支持下一步）；
    ③多步决策与状态利用（理解已完成/待解决/可用信息，按反馈调整顺序，含与用户协作确认）；
    ④失败恢复与合理终止（报错后修正/补信息/换路径/求助；满足条件后正确终止）。
    这些是模型的决策表现；工具执行、状态持久化、权限校验仍归 Harness 与环境。完成此拆解才能构造训练数据、选学习信号、独立验收。
  tags: [capability-model, decomposition, tuning]
  inputs: [失败案例或能力缺口描述]
  outputs: [可构造训练数据、可选择学习信号的模型优化目标]
  steps:
    - 沿"接收观察—决策—反馈—调整"循环定位失败环节
    - 归入四类决策能力之一
    - 转化为具体决策点的优化目标

- id: f4-05
  title: 模型优化目标设定：质量/可靠性/成本三维 + 单位成功任务成本 + 安全护栏
  type: framework
  source_chapter: 17.1.3
  source_quote: |
    "可采用“单位成功任务成本”，即统计期内全部任务的执行成本除以成功完成的任务数量，失败任务消耗的资源也计入分子。比较时应固定任务构成并同时报告成功率，避免因放弃困难任务而形成表面上的成本下降。"
  summary: |
    把"更强/更省"转化为可验证目标：优化动因分效果驱动与效率驱动，但都从质量（任务按要求完成、关键动作正确、约束遵守）、
    可靠性（多次运行、覆盖输入变化/长交互/工具异常/用户补充，关键场景不回退）、
    成本（单位成功任务成本=全部任务执行成本÷成功任务数，失败消耗也计入；含端到端时延及高分位）三维共同评估。
    训练前明确任务、基线、门槛、预算、安全约束与回归范围；训练后同口径复测。
    安全护栏分层：模型识别约束，Harness 做调用侧校验/放行/重试上限/停止条件，环境做资源侧强制校验。
  tags: [metrics, goal-setting, cost, safety-rail]
  inputs: [优化动因（效果/效率）, 业务要求]
  outputs: [可验证的质量/可靠性/成本指标与安全护栏]
  steps:
    - 区分效果驱动与效率驱动动因
    - 从质量、可靠性、成本三维度设定指标（含单位成功任务成本）
    - 训练前固定对照基线、门槛与回归范围，训练后同口径复测
  missing_conditions: []

- id: f4-06
  title: 模型优化方法选择判据：SFT / Agentic RL / 模型蒸馏
  type: framework
  source_chapter: 17.1.4（图 17.1-3；17.2.6 衔接）
  source_quote: |
    "有明确示范时选择 SFT。当工具使用、任务推进或失败恢复已有较明确的有效示范，而模型执行不够稳定时，可以通过监督微调提高这些行为在相应条件下出现的概率。"
  summary: |
    确认模型能力缺口后按学习信号与优化目的选方法：
    ①有明确可示范的正确行为、模型执行不稳 → SFT（提高目标行为在相似条件下的生成概率）；
    ②路径优劣需实际执行判断、环境能给可验证反馈、成本可承担 → Agentic RL；
    ③教师模型已具备能力、目标是迁移/压缩/部署（规模、时延、部署条件）→ 模型蒸馏（学生可能进入教师未覆盖状态，需检验偏差累积与失败恢复）。
    三者不互斥：蒸馏常通过教师数据上的 SFT 实现，SFT 后可继续 RL；组合与排序由基座能力、信号质量、目标 Harness 与成本预算决定。
  tags: [decision, method-selection, sft, rl, distillation]
  inputs: [归因后的能力缺口, 示范可得性, 环境反馈可靠性, 部署目标与预算]
  outputs: [优化方法选择及排序决策]
  steps:
    - 判断正确行为能否被可靠示范
    - 判断路径优劣是否只能靠环境交互评价
    - 判断是否存在可迁移能力的教师模型与部署约束

- id: f4-07
  title: SFT 适用边界与监督目标拆解
  type: framework
  source_chapter: 17.2.1
  source_quote: |
    "如果路径优劣只能通过环境交互才能判断，或者同一状态下缺少可信的目标动作，就不应直接将不确定结果作为监督标签，而应先完善验证条件，或考虑 Agentic RL 等依赖环境反馈的方法。"
  summary: |
    进入 SFT 的双前提：问题已归因于模型 + 目标行为能被可靠示范（专家/规则系统/更强模型可给出稳定可核验的正确行为）。
    监督目标必须从具体能力缺口出发而非"提升 Agent 能力"：如工具调用失败拆为调用时机/工具选择/参数语义/反馈理解错误，
    多轮失败定位为约束遗失/状态利用不足/终止判断错误。
    典型目标行为：信息充分时直接回答、需要外部信息时选工具、关键条件缺失时澄清、依据接口生成参数、结合结果更新计划、错误/权限不足/结果不完整时修正、求助或停止。
  tags: [sft, applicability, decomposition]
  inputs: [已归因模型的能力缺口]
  outputs: [落到具体决策点的监督目标清单]
  steps:
    - 确认正确行为可稳定示范
    - 把缺口拆到具体决策点（时机/选择/参数/反馈理解/终止）
    - 为每类决策点确定需要补充的样本与验证测试

- id: f4-08
  title: 轨迹构造可监督样本的可见性约束
  type: framework
  source_chapter: 17.2.2
  source_quote: |
    "每个目标行为只能依赖该决策时刻已经可见的信息。某次工具调用尚未返回时，目标动作不能使用其结果；用户在后续轮次补充的条件，也不能提前进入早期决策的输入。"
  summary: |
    样本构造本质：保持决策因果关系前提下，把完整轨迹转成若干"可见上下文—目标行为"样本。
    硬约束是可见性——目标动作不得使用决策时刻之后才有的信息，否则离线训练信息条件优于真实运行，上线无法复现。
    完整交互可作连续上下文，也可按决策点拆历史前缀样本；须保留任务约束、工具说明、历史动作与环境反馈。
    若必要状态在进入模型前已被截断/遗漏/错误组织，应先修 Harness 而不是靠 SFT 补偿。
    覆盖应含正常执行、多轮推进、异常恢复三类，且工具使用要含直接回答/发起调用/请求澄清多种选择，避免"遇任务就调工具"。
  tags: [sft, data-construction, causality]
  inputs: [完整轨迹（系统指令/用户请求/工具定义/模型动作/环境反馈/修正）]
  outputs: ["“可见上下文—目标行为”样本集"]
  steps:
    - 定位轨迹中经验证值得复用的模型行为
    - 检查每个目标行为只依赖决策时刻可见信息
    - 覆盖正常/多轮/异常三类场景并保留依赖信息
  missing_conditions: []

- id: f4-09
  title: SFT 监督内容筛选与角色级/质量级掩码
  type: framework
  source_chapter: 17.2.3（表 17.2-1）
  source_quote: |
    "可以将错误动作保留在历史上下文中，使模型理解当前为何需要修正，但屏蔽该错误动作对应的训练损失，只监督经过验证的后续行为。"
  summary: |
    任务成功不代表每一步值得模仿；样本质量须逐步审查而非由最终结果决定。
    按交互内容分类处理：系统指令/用户请求/工具定义→仅作输入上下文；工具结果与环境观察→保留输入、不算生成损失；
    经验证的调用/澄清/修正/最终答复→计算监督损失；用于解释恢复场景的错误模型步骤→保留上下文但屏蔽损失；未核验步骤→补核验或移出训练集。
    角色级掩码排除非模型内容，质量级掩码处理"模型生成但错误"的步骤，二者解决不同问题。
    实施时应抽查实际参与损失计算的内容。
  tags: [sft, data-quality, masking]
  inputs: [轨迹样本, 逐步验证结果]
  outputs: [带损失掩码的训练样本]
  steps:
    - 对关键行为逐步审查，不凭最终结果定性
    - 按内容类别决定监督处理（输入/保留/算损失/屏蔽损失）
    - 抽查实际参与损失计算的内容

- id: f4-10
  title: SFT 样本配比与能力回退防护
  type: framework
  source_chapter: 17.2.4
  source_quote: |
    "样本配比应同时反映生产任务分布和已经确认的能力缺口。高频任务用于建立稳定的基本行为，长链路任务用于训练跨步骤的信息利用，低频但影响较大的异常用于补足恢复能力。"
  summary: |
    配比原则：高频任务建基本行为、长链路任务训跨步骤信息利用、低频高影响异常补恢复能力；
    同时保留原本可直接完成的简单任务样本，防止训练后普遍增加工具调用或交互轮次。
    不机械等量混合，按开发集失败类型调整覆盖；保留通用指令遵循样本，检查专业任务改善是否伴随其他能力回退。
    工程约束：训练与推理用兼容的对话模板、工具调用格式与结束标记；检查长样本截断位置（保目标动作不丢依赖）；
    全量微调 vs LoRA 按基座、任务复杂度、预算与独立评测定，均不能替代数据质量控制。

  inputs: [生产任务分布, 开发集失败类型分析]
  outputs: [训练样本配比方案与训练配置]
  steps:
    - 按生产分布+确认缺口设计三类覆盖
    - 保留简单任务与通用样本防回退
    - 校验模板兼容性与截断位置后训练

- id: f4-11
  title: SFT 执行评测验收（防"续写式"评测）
  type: framework
  source_chapter: 17.2.5
  source_quote: |
    "SFT 的验收应让候选模型在固定的 Harness、工具接口和执行预算下自主运行，由环境返回实际反馈，再观察早期决策如何影响后续执行。若每一步都提供标准历史，只检查模型能否续写下一条标准响应，就无法暴露错误累积和恢复失败。"
  summary: |
    训练损失下降≠能完成任务。验收必须让候选模型在固定 Harness、工具接口、执行预算下自主运行并接收环境真实反馈。
    按质量（任务完成/约束满足/答复有执行结果支持）、可靠性（不同输入/长交互/异常下重复表现）、
    成本（调用次数/token/时延/单位成功任务成本）、安全（权限边界/危险动作/停止条件）四维报告。
    测试集按任务族/模板/数据来源分组防泄漏；比较版本时保持 Harness/任务/预算一致，组合变更单独记录；
    有采样随机性时重复运行报告波动。交付物：候选模型或适配器、训练与推理配置、数据版本、按缺口与准入指标组织的评测报告。
  tags: [sft, evaluation, acceptance]
  inputs: [候选模型, 固定 Harness 与预算, 分组测试集]
  outputs: [四维评测报告与发布判断]
  steps:
    - 固定 Harness、工具接口与执行预算
    - 让模型自主运行完整任务接收真实反馈
    - 按质量/可靠性/成本/安全四维报告并对照缺口
  missing_conditions: []

- id: f4-12
  title: Agentic RL 准入判断六维度
  type: framework
  source_chapter: 17.3.1（表 17.3-1）
  source_quote: |
    "进入 Agentic RL 前，需要分别回答两个问题：这个任务是否值得使用强化学习，以及当前系统是否具备训练条件。前者由模型能力缺口和任务反馈结构决定，后者由环境、验证器、安全边界和训练成本决定。"
  summary: |
    六维度准入：①问题归因——失败确来自模型动作选择/反馈利用/恢复策略，否则先修上下文、工具协议、权限或环境；
    ②示范可得性——有效路径不唯一、难以为每个决策点提供稳定标签，若可稳定示范优先 SFT；
    ③结果可验证性——结果或关键中间状态可被规则/测试/可靠评审稳定判断，否则先建验证器或标尺集；
    ④环境能力——可重复执行、状态可重置、探索可隔离、过程可追踪，否则先建 Sandbox/模拟器/回放环境；
    ⑤基础策略——模型已有基本指令遵循与工具调用能力、能产生一定比例有效轨迹，否则先提示/SFT/换基座；
    ⑥投入产出——预期改善能覆盖 Rollout 与环境维护成本。
    "结果可验证"比"过程可完整标注"更重要：RL 无法从不可靠反馈推断真实目标（验证器只查"是否生成退款记录"会让模型学会快速创建不合规退款）。
  tags: [rl, admission, decision, table]

  type: framework
  source_chapter: 17.4.4
  source_quote: |
    "可将失败轨迹拆解为四类缺口：知识缺口表现为目标或约束理解错误；决策缺口表现为工具选择或步骤顺序错误；执行缺口表现为参数、格式、权限或调用协议不合法；恢复缺口表现为面对空结果、超时、冲突证据或工具报错时继续重复原动作。"

  title: 轨迹阅读法：先目标与结果，再关键步骤，结论落到相邻事实链
  type: framework
  source_chapter: 19.3
  source_quote: |
    "分析时，尽量把结论落到一组相邻事实：“用户要求操作步骤 → 检索返回了步骤 → 最终回答遗漏步骤”。这样的记录便于别人复核，也能直接用于后续评分。"
  summary: |
    读轨迹的顺序：①先看输入输出了解任务目标与最终答案；②再看步骤数、工具调用、Tokens、耗时概览确定重点环节，不逐字通读；
    ③沿"用户补充→Agent 行动→工具返回→后续回答"顺序查执行步骤，长记录用步骤搜索定位工具名/关键内容/错误提示，展开入参与执行结果；

    怀疑记录缺失时由工程人员结合身份回查采集；业务结果以实际工具反馈和业务状态为准。

    - 核对关键动作的输入依据与结果使用

  type: framework
  source_chapter: 19.4
  source_quote: |

  summary: |
    三类问题的分析路径：
    ①工具失败——展开入参确认缺什么，再看失败后的行动（追问/改参数/重新调用）：确实收到错误仍告知成功→改错误处理与回复策略；返回没表达清楚失败→同时查工具接口；多次原样重试同一错误→调重试或停止条件（修正后成功说明能恢复，与原样重试不应给同样建议）；业务是否真产生结果要核对业务系统。

  title: 仿真与边缘生产验证互补闭环
  type: framework
  source_chapter: 24.7
  source_quote: |
    "仿真回答的是”如果发生 X，Agent 会怎样“；边缘生产验证回答的是”全球真实用户实际发生了什么，Agent 表现如何“。"
  summary: |
    仿真（上线前，合成场景/模拟用户，覆盖边界与长尾，模拟网络参数，红队攻击样本，回答"能否应对假设场景"）与
    边缘生产验证（上线后，全球真实请求，主流场景与真实分布，实际网络状况，真实攻击流量，回答"真实环境表现如何"）互补，
    构成版本发布前后完整验证闭环。
    边缘观测四类：请求分布（地域占比/高峰时段/路径偏好）、网络状况（端到端延迟/丢包/中断/长连接稳定性）、

    边缘灰度发布：站点级版本管理（开发/灰度/生产三环境，版本克隆生成、按请求规则导流验证、可切换回滚），

    联合准入：发布基线同时含 Region 内指标（回答正确率/任务完成率）与边缘指标（全球延迟分布/缓存命中率/安全拦截率）。

    - 上线后边缘观测真实分布与网络

- id: f4-70
  title: 边缘优化三阶段演进与企业成熟度模型
  type: framework
  source_chapter: 24.8（另见 24.9 决策建议）
  source_quote: |
    "三个阶段的关系与”选择最低充分架构“原则一致——边缘优化同样不追求最高阶段，而是根据业务的全球化程度选择成本与收益最优的阶段。大多数企业长期停留在阶段一或阶段二即可获得显著收益"
  summary: |
    三阶段渐进演进：
    阶段一（边缘基础设施增强）——业务代码不变，网络层加边缘加速与安全（Anycast、智能路由、DDoS、WAF/Bot、静态缓存、SSL 卸载）；
    实施四步：ESA 接入与 DNS 切换→全球基线延迟测量→重点区域效果验证→全球生效；适用：已有稳定 Region 部署、想改善全球延迟与安全但不动架构；
    阶段二（Agent 能力部署到边缘）——语义缓存、模型路由、Token 计量、内容转换、轻量推理在边缘执行；适用：Token 成本或内容处理延迟成瓶颈；
    阶段三（Agent 原生边缘部署）——边缘优先拓扑、中心兜底；两级运行时（EdgeFunction 近用户做鉴权/路由/改写/缓存/过滤；RegionFunction 近源做上下文/编排/推理/记忆/沙箱），
    "逻辑单例、物理可替换"+状态外置（配套权威源、版本钉扎、激活协议、并发写控制、断网降级、回滚规则）；ESA AI 加速网关（缓存/传输/内容/计量/过滤/调度）；
    关键指标：边缘处理比例（按任务风险与 SLO 设目标，正确性优先而非单一最大化）、冷启动、路由决策延迟、会话保持率、故障转移时间；
    适用信号：每区域独立部署运维不可控、全球 TTFT 网络占比超 30%、Token 成本线性上升无缓存手段。
    成熟度 L1-L4：L1 无边缘优化直连 Region；L2 接入边缘加速与安全独立看板（未进评估闭环，无法量化 ROI）；
    L3 边缘指标纳入 Release 准入（评估闭环）；L4 边缘数据驱动自进化（全自动闭环）。
    成熟度不是越高越好（L1 单区域、L2 全球化初期、L3 生产严格门禁、L4 大规模全球化）；
    判断信号：全球用户抱怨延迟但 Region 指标正常→需阶段一；Token 成本线性上升无缓存→需阶段二；每区域独立部署不可控→需阶段三；单区域运行→暂不需要。
  tags: [edge, maturity-model, staged-evolution, architecture]
  inputs: [全球化程度, 延迟/成本结构, 运维负担信号]
  outputs: [所处阶段与成熟度判断, 阶段选择决策与对应评估指标]
  steps:

    - 按阶段实施对应能力（接入增强→能力下移→边缘原生）
    - 用各阶段评估指标验证并对照成熟度模型定位

- id: f4-71
  title: 边缘优化不适用场景判断
  type: framework
  source_chapter: 24.9
  source_quote: |
    "流量规模小或缓存命中率低时，边缘层的额外成本可能超过收益，此时阶段一甚至”不优化“才是正确选择。"
  summary: |
    六类需审慎评估的场景：①单区域业务（用户与 Region 物理距离近，延迟收益有限投入不成比例）；
    ②严格数据驻留（不允许跨区域缓存复制或数据不出特定司法辖区，需按区域合规配置甚至放弃边缘缓存）；
    ③高正确性风险回答（个性化强、权限敏感、时效性高的内容不应进语义缓存，防错误答案误命中）；
    ④边缘算力受限（复杂推理、长任务、大上下文仍需回源，边缘只做预处理粗筛）；
    ⑤区域能力差异（各区域边缘能力、可用模型、合规要求不同，全球统一策略需按区域适配，无法一刀切）；
    ⑥成本反转（流量小或命中率低时边缘额外成本可能超过收益，"不优化"也是正确选择）。
    决策依据：基于全球化程度、数据驻留要求、请求分布与成本结构选阶段，并设与业务 SLO 匹配的指标目标；
    书中所有性能数字为示例假设，正式实施前必须由企业基线与压测校准。
  tags: [edge, applicability, boundary, decision]
  inputs: [业务区域分布, 数据驻留要求, 流量规模与缓存命中预期]
  outputs: [是否采用边缘优化及安全边界的决策]
  steps:
    - 逐项核对六类限制场景
    - 命中任一类时降级或放弃对应边缘能力
    - 用企业基线与压测校准后再决策
