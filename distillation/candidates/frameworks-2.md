  type: framework
  source_chapter: 第 7 章 7.5.2

    "持续运行可以立即执行后续动作，但始终占用计算资源；保留内存的浅层暂停可以减少活跃计算，但仍需保留相应内存。"
  summary: |

# ============ 第 8 章 状态存储分层 ============

- id: f2-15
  title: Agent 状态四类分层地图
  type: framework
  source_chapter: 第 8 章 8.1.2
  source_quote: |
    "从数据形态看，Agent 的状态不是单一对象，而是一组生命周期、访问方式和一致性要求各不相同的数据集合。"
  summary: |
    状态外置后按形态分四类：运行时状态（事件日志/检查点/任务进度/租约/状态指针，保障可恢复可迁移可协调）、
    工作区与产物（文件/代码/快照/版本，需共享引用回滚）、记忆与知识（摘要/偏好/经验/文档/向量索引/图谱）、
    业务语义与治理状态（本体/规则/租户/权限/审计）。
    关键不是所有状态落入同一种存储，而是每类状态获得匹配物理承载，同时在上层拥有统一身份、元数据、版本、权限与生命周期。
  tags: [state-management, storage, layered-model]

- id: f2-16
  title: 先定义状态正确性边界，再选存储引擎
  type: framework
  source_chapter: 第 8 章 8.1.3
  source_quote: |
    "正确的起点不是先选择某一种引擎，而是先定义不同状态对象的正确性边界，再为其匹配相应的存储能力，并通过统一契约把它们组织为一个整体。"
  summary: |
    不同对象有一致性差异：运行时状态需要写入顺序、原子更新、幂等与可恢复历史；
    工作区产物关注版本/快照/引用/回滚；记忆知识强调可检索性、时效性、来源可信与权限过滤；
    本体治理需维护对象身份、关系完整与审计证据。
    误配的后果：任务事实当可检索文本会丢顺序与原子性，成果当无版本附件难回滚，记忆与权限混同会让过期/越权内容持续影响决策。
  tags: [state-management, consistency, design-process]

  title: Event Log：只追加事件日志的顺序性与一致性边界
  type: framework

  type: framework

- id: f2-43
  title: AI Gateway 三种可组合治理语义
  type: framework
  source_chapter: 第 9 章 9.1.3
  source_quote: |
    "三种语义可以部署在同一数据面，也可以由不同组件承接。统一的关键不是所有能力位于同一进程，而是身份映射一致、策略边界清晰、调用记录能够关联。"
  summary: |
    按治理对象分三种可组合语义：LLM Gateway（模型路由/限流/容灾/计量，不判断业务成功）、
    MCP Gateway（协议代理/工具授权，不把可发现等同于已授权）、Agent Gateway（入口身份/路由/亲和/并发/跨调用关联，不定义 Task/State/恢复语义）。
    是分析框架而非成熟度阶梯。完整调用链示例：Agent 入口→模型路由→工具鉴权→审批后重新准入→结果回传任务账本。
    网关只保证准入、转发与记录一致性，不能仅凭请求成功断言任务完成。
  tags: [gateway, governance, layered-model]

- id: f2-44
  title: 网关能力分阶段建设路径
  type: framework
  source_chapter: 第 9 章 9.1.5
  source_quote: |
    "企业可以先统一凭证托管和模型入口，再建立用量归因与工具授权，最后逐步引入路由实验和评估回归。每一步都应有独立的验收目标。"
  summary: |
    渐进顺序：凭证托管+模型入口 → 用量归因+工具授权 → 路由实验+评估回归。
    每步有独立验收目标（凭证不再分散到客户端、用量可归属项目、拒绝可追溯），不以插件数量衡量进度。
    部署折中：在既有网关扩展可复用证书身份运维体系，但长连接与内容缓冲可能影响其他业务；
    独立部署利于容量发布隔离但增加负担；常见折中是共享身份与策略管理、按流量类型隔离数据面。
    网关自身按关键基础设施设计，逐项定义依赖故障行为。
  inputs: [企业现有网关/身份/运维体系, AI 流量特征]
  outputs: [分阶段的网关能力与独立验收结论]
  steps: [统一凭证托管与模型入口, 建立用量归因与工具授权, 逐步引入路由实验与评估回归, 每步设置独立验收目标]
  missing_conditions: [各阶段时间节奏未给，按企业现状决定]
  tags: [gateway, rollout, progressive-delivery]

- id: f2-45
  title: 模型选择与推理端点选择分离
  type: framework
  source_chapter: 第 9 章 9.2.3
  source_quote: |
    "模型选择与端点选择应分开。……不能把 API 稳定性、扩展实现成熟度和算法效果合并为一个结论。"
  summary: |
    路由分两层决策：模型层（静态映射与权重灰度、成本感知路由需能力门槛+质量下限+价格口径、
    语义路由需评估过的分类器与回退路径）与端点层（同一模型的实例选择，可依据队列、在途请求、缓存信号）。

    API 稳定性、扩展实现成熟度、算法效果应分别绑定版本讨论；缓存与路由需共同评估总成本而非单次 token 数。
  tags: [llm-gateway, routing, selection]

- id: f2-46
  title: 错误分类先于重试 + 跨层尝试预算传递
  type: framework
  source_chapter: 第 9 章 9.2.4
  source_quote: |
    "错误分类应先于重试。……一次用户可见的调用最多会到达上游 9 次……重试次数、并发压力和费用会以乘积方式放大。"
  summary: |
    重试许可判断：限流响应结合重置时间/配额/替代端点处理；服务端错误只在调用语义允许时重试；
    认证错误终止修凭证；上下文超限不应靠截断历史"解决"（改变任务输入），由应用决定压缩/换模型/明确失败。
    "尚未收到响应体"≠"上游未执行"（可能已计费已副作用）；流式响应已提交后不能透明重放。
    多层恢复会乘积放大（3×3=9 次），尝试预算必须跨层传递：总截止时间为绝对时间，剩余额度按 call_id 原子扣减，
    每次尝试用稳定 call_id/attempt_id 关联；重试、摘除与模型切换分开记录以便归因。
  inputs: [上游错误分类, 调用幂等性, 各层重试配置]
  outputs: [带预算约束的重试决策, 可还原为一次逻辑调用的 attempt 关联记录]
  steps: [先对错误分类（限流/服务端/认证/上下文超限）, 判断调用语义是否允许重试, 层间传递绝对截止时间与剩余尝试额度, 按 call_id 原子扣减预算, 每次 attempt 独立标识并关联, 未经验证的兜底路径返回可解释失败]
  missing_conditions: [各层预算的具体数值未给]
  tags: [llm-gateway, retry, budget, error-handling]

- id: f2-47
  title: 超时分层测量：连接 / 首字节 / TTFT / 流式空闲 / 总截止
  type: framework
  source_chapter: 第 9 章 9.2.5
  source_quote: |
    "连接超时用于约束建连，首字节超时用于识别上游长时间无响应，TTFT 描述有效生成开始前的等待，流式空闲超时约束连续事件间隔，总截止时间控制整个调用的资源占用。"
  summary: |
    五种时限同时存在但互不替代：持续发心跳的流可以不触发空闲超时却始终没有有效内容。
    TTFT 的统计必须明确起止点，不能等同于 HTTP 首字节（首 SSE 事件可能只是心跳）。
    SSE 解析需跨字节切片重组事件并设单事件长度/累计缓冲/解析时间上限；
    缺少 usage 不能记为零消耗，客户端取消不能证明上游停止生成——保留估算或未结算状态待对账。
  tags: [llm-gateway, timeout, streaming, measurement]

- id: f2-48
  title: 预算语义四档与严格预算原子预留不变量
  type: framework
  source_chapter: 第 9 章 9.2.6
  source_quote: |
    "可用额度 = 已授权额度 − 已结算消耗 − 在途预留；准入条件 = 本次最大可计费消耗 ≤ 可用额度"
  summary: |
    四档机制承诺不同：请求速率限制（准入速度，不管 token 成本）、token 时间窗（用量增长，有在途并发超限窗口）、
    余额型配额（近实时额度，非严格并发预算）、严格预算（可证明最大消耗+原子预留+结算退款）。
    "请求前检查、响应后扣减"无法保证硬上限（余额 100 时两个最大消耗 80 的并发请求可耗 160）。
    严格预算要求检查与预留同一原子操作，预留覆盖输入+受约束最大输出+其他计费项，重试单独占额度；
    结果未知不因租约到期无条件退款；多层额度（组织/团队/项目/任务）同时验证，token 配额与金额预算分开。
  inputs: [主体授权额度, 单次调用最大可计费消耗估算]
  outputs: [准入决定与预留记录, 幂等结算与退款]
  steps: [声明预算档位与承诺强度, 估算本次最大可计费消耗, 原子地检查并预留额度, 调用结束后按实际消耗幂等结算并释放多余预留, 结果未知时保守等待对账]
  missing_conditions: [最大消耗估算的可靠方法依接口计费项而定]
  tags: [budget, quota, llm-gateway, consistency]

- id: f2-49
  title: MCP 准入四步：认证—协议校验—授权—转发
  type: framework
  source_chapter: 第 9 章 9.3.3
  source_quote: |
    "MCP 请求的准入可以按“认证—协议校验—授权—转发”四步理解……协议说明不是调用者身份证明。"
  summary: |
    认证回答"谁在调用"（独立于协议的凭据做主体映射）；协议校验按版本检查头部镜像、方法与报文约束；
    授权按主体、工具与参数决定放行；转发按声明策略重新构造上游请求。
    逐请求元数据只服务于协议校验与转发两步，不能替代身份与权限判断。
    头部可辅助分类路由但执行前必须验证与正文一致，避免头部鉴权与正文执行面对不同对象；
    server/discover 的能力通告不证明依赖健康、已授权或必然成功。
  inputs: [MCP 请求（含逐请求元数据与镜像头）, 主体凭据, 工具与参数授权策略]
  outputs: [放行转发的上游请求或带原因的拒绝, 审计记录]
  steps: [认证：凭据映射稳定策略主体, 协议校验：按版本核对镜像头与方法报文, 授权：按主体/工具/参数判定, 转发：按策略重构上游请求并默认不透传下游凭证]
  missing_conditions: [Legacy/Modern 双代际的桥接方向与能力子集需按实现显式声明]
  tags: [mcp-gateway, authentication, authorization, procedure]

- id: f2-50
  title: 工具权限交集原则与网关不可绕过条件
  type: framework
  source_chapter: 第 9 章 9.3.5
  source_quote: |
    "权限应取调用者原有授权、工作负载授权、任务委托范围和资源侧限制的交集，不能由模型声明的身份、工具描述或 clientInfo 扩大。"
  summary: |

  title: 审批约束转发的状态化处理

- id: f2-59
  title: Task / Session / State 等六对象权威关系模型
  type: framework
  source_chapter: 第 10 章 10.1.1
  source_quote: |
    "Task 是异步执行的最小业务单元，具有独立、持久的标识和自己的业务 State。Task 可以跨越等待、恢复、人工审批等多个阶段持续存在，也可以跨多个 Session 续跑。"
  summary: |
    对象权威分工：Task（业务应用/任务模型定义，跨 Session 跨等待跨恢复）、业务 State（业务应用，与 Task 同寿）、
    Session Context（Harness/Runtime，按会话持续）、Checkpoint（工作流引擎/Runtime，按恢复契约）、
    Runtime State（Runtime，一次执行租约内：心跳/租约/Worker/当前步骤）、外部副作用（业务系统，与外部系统同寿）。
    跨 Session 续跑需 Runtime 显式装载授权的 Task State 并关联当前 Session，而非默认共享上下文；
    Task 隔离取决于租户/运行身份/凭证/环境/资源边界，Session 只是一段执行视图。
  tags: [task-model, responsibility-boundary, state-management]

- id: f2-60
  title: 完成语义五层模型：执行状态—运维状态—候选证据—Evidence—Outcome
  type: framework
  source_chapter: 第 10 章 10.1.2
  source_quote: |
    "执行状态……它回答”这次执行有没有跑完“，不回答”业务目标是否达成“。"
  summary: |
    五类信息分层回答不同问题：执行状态（Runtime 的 succeeded/failed 等运行信号）、
    节点运维状态（Worker 在线/租约有效/依赖降级等基础设施健康，影响调度不等于 Task 结论）、
    候选证据（日志/Trace/快照/Artifact/LLM 原始响应等原始材料）、
    Evidence（被业务成功标准明确引用的候选证据，需核验来源完整性与验收关系）、
    Outcome（业务应用或获授权 Verifier 依 Evidence 与成功标准做的最终判定）。
    LLM-as-a-Judge 只是 Evaluation 实现不是 Outcome 权威；"强制标记成功"只改执行状态并留审计，不能跨层判定 Outcome。
  tags: [outcome, completion-semantics, layered-model, evidence]

- id: f2-61
  title: 恢复与幂等的责任划分
  type: framework
  source_chapter: 第 10 章 10.1.3
  source_quote: |
    "Checkpoint 保存的是按恢复契约保存的状态……它不等同于外部副作用幂等：若外部写入已提交而 Checkpoint 尚未落盘，重跑仍会产生重复副作用。"
  summary: |
    调度器管统一触发/并发控制/故障转移，但重复投递仍可能发生，执行端按业务操作标识核对结果；
    Checkpoint 用于复用计算结果避免重算，不等于副作用幂等（外部写入已提交而 Checkpoint 未落盘时重跑仍重复）；
    幂等机制按交付语义与外部能力组合选择（任务唯一键/幂等键/去重账本/outbox-inbox/租约与 fencing token/对账补偿），无通用必选项；
    新实例需重新取得执行权，不能恢复一份旧心跳就继续提交；信号（Watch/回调/轮询）缺失后以权威 Task State 重新对账。
  tags: [idempotency, recovery, checkpoint, responsibility-boundary]

- id: f2-62
  title: 异步任务三组件架构：队列 + 调度器 + 状态机
  type: framework
  source_chapter: 第 10 章 10.2.3
  source_quote: |
    "任务队列承担排序与缓冲，调度器负责将 Task 投递给合适的 Worker 并维护租约，任务执行状态机维护生命周期与转换合法性。"
  summary: |
    任务队列：优先级排序、同优先级 FIFO、积压降级（拒绝新任务返回结构化错误/低优先级限速/告警扩容），队列深度是核心观测指标。
    调度器：负载均衡与 Worker 选择（轮询/按槽位/加权/亲和路由）+ 背压。
    状态机：维护生命周期与合法转换。
    Task 定义至少含名称、内容、优先级、Agent/池、关联 Session、成功标准（引用 Evidence 与 Verifier）、
    重试策略、超时、计划调度时间与业务时间。状态存储以数据库为权威源、内存缓存加速。
  inputs: [客户端提交的 Task（含属性表字段）, Worker 池与租约]
  outputs: [可靠接收确认与 Task ID, 执行结果与状态通知]
  steps: [任务入队按优先级与 FIFO 排序, 调度器选 Worker 并投递维护租约, 状态机推进生命周期, 完成后经 Webhook/推送/轮询通知客户端]
  missing_conditions: [通知方式三选一或组合，按客户端能力决定]
  tags: [async-task, architecture, scheduling, procedure]

- id: f2-63
  title: 任务执行状态机（九状态转换表）
  type: framework
  source_chapter: 第 10 章 10.2.3.3
  source_quote: |
    "任务执行状态机维护生命周期与合法转换。"
  summary: |
    状态集合：waiting（初始化等依赖）→ queued（等资源）→ running（执行中）→ succeeded/failed/killed；
    hold 等待审批/输入/外部条件；skipped 用户跳过；mark_succeeded 用户手动标记成功（终态）。
    合法转换约束失败/终止任务只能由用户手动重跑回 queued；hold 满足后回 waiting 或转 skipped。
    该表描述执行调度状态，业务 Outcome 另按验收规则维护，两者分离。
  tags: [state-machine, async-task, lifecycle]

- id: f2-64
  title: 背压组合机制
  type: framework
  source_chapter: 第 10 章 10.2.3.2
  source_quote: |
    "背压的本质是让消费速率自适应执行速率，避免过载崩溃。"
  summary: |
    Worker 全忙时调度器不应继续取任务。生产常用组合：并发配额（每 Worker 最大并发）、
    队列水位线（超阈值暂停拉取）、消费速率自适应（按完成速率动态调整拉取批量）、
    租约超时（防 Worker 失联任务卡死）、动态容量（按心跳实时调整可用槽位）。
    "空闲/繁忙 Worker 注册表"只是单任务单 Worker 假设下的简单实现，不是通用定义。
  tags: [backpressure, scheduling, load-management]

- id: f2-65
  title: 任务状态监听三方案组合：轮询 / 回调 / 共享存储+Watch
  type: framework
  source_chapter: 第 10 章 10.2.4
  source_quote: |
    "三种方案不互斥。生产实践通常组合使用：回调为主、轮询/租约兜底、共享存储做权威持久化。"
  summary: |
    轮询（控制权集中，但单次失败不能推断异常——判定异常应基于租约/心跳）；回调（实时但依赖诚实回报，
    事件须带 Task ID/事件序号/Worker 标识/租约 token 供幂等消费丢弃迟到事件）；共享存储+变更通知
    （断连事件丢失，重连以当前状态为准重新对账；etcd Watch 需处理 compaction）。
    三者都是变化信号不是唯一事实源，信号缺失或中断必须以权威 Task State 重新对账。
  inputs: [Worker 执行状态变化, 租约与心跳信号]
  outputs: [状态机更新, 通知与重试触发, 与权威存储对账后的一致状态]
  steps: [正常路径 Worker 主动回调, 回调丢失时经查询或租约异常核对, 所有状态变更同步落权威存储, 调度器与 Worker 重启后从存储恢复]
  missing_conditions: [轮询频率与租约时长按业务定]
  tags: [state-sync, polling, callback, watch, procedure]

- id: f2-66
  title: HITL 场景下内置 vs 外置调度选择
  type: framework
  source_chapter: 第 10 章 10.2.5
  source_quote: |
    "外置调度由专用系统管理执行分配和唤醒，Agent 完成当前步骤后保存恢复所需状态与引用，再按环境能力释放 Worker。"
  summary: |
    人工介入使 Task 进入 hold，等待从分钟到数天，直接影响资源利用率。
    内置调度接入门槛低自包含，是否常驻取决于等待与状态恢复能力而非部署位置；
    外置调度等待期可释放执行资源，但需对接调度 API、暴露恢复接口，且调度/状态存储/审批通道仍占资源。
    审批回传必须明确：事件载荷含 Task ID/审批版本号/授权主体/决策结论，接收方是 Runtime 或调度器，
    需验证未过期、未重复、与当前状态兼容；工作流引擎人工节点可承载暂停恢复但不自动拥有业务审批授权。
  tags: [hitl, scheduling, selection]

  type: framework

- id: f2-71
  title: 节点就绪条件三种边：普通依赖 / AND Join / OR Join
  type: framework
  source_chapter: 第 10 章 10.4.3
  source_quote: |
    "OR Join 的关键是显式取消未选分支，否则它们会继续消耗资源、产生副作用，与下游已基于“先到结果”做出的决策冲突。"
  summary: |
    普通依赖边：上游 succeeded 或 skipped 即就绪，上游失败按错误处理策略；
    AND Join：所有入边上游到达终态且满足策略（全部成功/至少 N 个成功）；
    OR Join：任一入边满足即就绪，未选分支由引擎显式取消，迟到结果进审计日志不改变下游已就绪状态。
    默认调度规则与显式汇聚规则需明确衔接，否则"所有前依赖完成"与"任一完成即继续"会在同一张图里矛盾。

- id: f2-72
  title: 工作流引擎三类工程能力：持久恢复 / 幂等局部重跑 / 可视化运维
  type: framework
  source_chapter: 第 10 章 10.4.4
  source_quote: |
    "每个节点完成后，引擎将输入、输出、执行状态持久化为步骤级 Checkpoint。后续节点的输入从 Checkpoint 读取，而非重新计算。"
  summary: |
    一、状态持久化与断点恢复：步骤级 Checkpoint 使执行不依赖单个工作进程，崩溃后从最后成功 Checkpoint 继续；
    二、幂等与局部重跑：区分"计算结果复用"（Checkpoint 存在且版本匹配则跳过重算）与"外部副作用幂等"
    （写入已提交而 Checkpoint 未落盘时重跑仍重复）——先保存意图再执行后保存结果，故障窗口按后端能力用事务/Outbox/幂等键/对账处理，
    已发生操作只能确认或补偿不能由检查点撤销；
    三、可视化运维：DAG 上标注实时状态/耗时/重试，支持重跑/跳过/强制标记成功/暂停/终止，
    采集按最小必要+脱敏+RBAC+期限，凭证禁止入库。
  inputs: [节点执行结果, 外部副作用提交记录]
  outputs: [步骤级 Checkpoint 链, 可恢复可审计的执行视图]
  steps: [节点完成后持久化输入输出与状态, 恢复时校验 Checkpoint 版本并复用, 核对失败步骤的外部副作用, 人工介入操作走状态机并留审计]
  missing_conditions: [自愈策略的重试参数按节点配置]
  tags: [workflow, checkpoint, idempotency, ops, procedure]

- id: f2-74
  title: 编排层与执行系统的职责边界（协调与自主平衡）
  type: framework
  source_chapter: 第 11 章 11.1.3
  source_quote: |

- id: f2-75

  title: 个人工作区 Agent 的接入边界

- id: f2-77

  type: framework

- id: f2-78
  title: 团队组织拓扑三模式：主管—执行 / 对等协作 / 分层编排
  type: framework
  source_chapter: 第 11 章 11.3.2-11.3.4
  source_quote: |
    "主管—执行、对等协作和分层编排，是对决策、委派和汇报关系的不同安排。它们不是从低级到高级的演进阶段，而应根据实际工作特点选择。"
  summary: |
    主管—执行：主管统筹目标/分工/依赖/汇总，执行者在明确目标约束下自主完成；风险是决策瓶颈与主管重复验证，目标交付物负责人依赖清楚时即应放行执行者。
    对等协作：按专业职责直接协商相互复核，沟通路径短，但必须预先约定分歧解决、共同决定事项、产物整合者与最终交付责任。

- id: f2-79
  title: 专业能力与组织角色分离
  type: framework
  source_chapter: 第 11 章 11.3.1
  source_quote: |

    角色须说明可自主决定什么、需交付什么、何时寻求协调；人也可承担需求澄清/专业判断/关键决策角色而非仅兜底。

- id: f2-80
  title: 协作机制四阶段：任务定义→计划制定→调度执行→结果聚合
  type: framework
  source_chapter: 第 11 章 11.4
  source_quote: |
    "这个过程依次经过任务定义、计划制定、调度执行和结果聚合。"
  summary: |
    任务定义：Task 记录目标/范围/输入/交付物/验收条件/负责人/约束，Subtask 承载可独立分派的局部交付，

  missing_conditions: [拆分粒度标准为定性判断（独立交付/不同责任/明确依赖）]

- id: f2-81

  type: framework

- id: f2-82
  title: 结果聚合三层判定与"已完成≠终态"
  type: framework
  source_chapter: 第 11 章 11.4.4
  source_quote: |
    "执行者提交结果，表示候选成果已经产生；Leader 或指定审核成员接受子任务结果，表示它具备继续用于下游工作的条件；根 Task 达到完成条件……三者相关，但不能互相替代。"
  summary: |
    三层递进：提交（候选成果产生）→接受（具备下游使用条件，Leader 可在授权范围内接受普通子任务，但内部接受≠最终业务验收）→
    根 Task 完成（当前有效版本成果共同覆盖总体目标）。
    "已完成"表示执行阶段结束、产物具备交付条件，不是生命周期终态：人工验收者取得产物、按约定规则确认接受后才归档完结；
    未通过验收沿用原 Task 与结果关系继续修订而非另建任务。最终交付说明有效产物如何覆盖目标、结果一致性、剩余限制与停止条件是否触发。

  type: framework
  source_chapter: 第 12 章 12.1.1

- id: f2-92
  title: 状态承载三位置与恢复条件
  type: framework
  source_chapter: 第 12 章 12.1.2
  source_quote: |
    "本章沿着状态由谁保存、断连后如何继续这条主线比较通信机制。需要区分三类内容：业务任务状态、执行检查点，以及消息日志与消费位置。"
  summary: |
    三类承载位置：连接与进程内存（当前响应/临时调用状态，断连即失，恢复靠查询持久任务或可重试调用）、

- id: f2-93
  title: 四个通信面模型（人机/能力/协作/内构）
  type: framework
  source_chapter: 第 12 章 12.2.1
  source_quote: |
    "四个通信面分别是人机面、协作面、能力面和内构面。协议只提供其中部分契约，具体的持久化、路由、授权和恢复仍需由实现补齐。"
  summary: |

- id: f2-94
  title: 四档交互语义谱系（S1-S4）
  type: framework
  source_chapter: 第 12 章 12.2.2
  source_quote: |
    "以下四档用于区分接口呈现和解耦程度，不是成熟度等级。一个系统可以同时使用多档语义"
  summary: |
    S1 请求—响应（响应期内耦合，状态在临时调用状态，解决短调用不自带长任务查询）；
    S2 请求域流式（当前流依赖连接，增量可见，单凭流不保证断连补齐）；

    时间/空间耦合度决定失效模式；两轴（通信面×语义档）交叉构成选型地图，回答某段通信该用什么语义、状态寄存何处、以什么方式失效。

- id: f2-95
  title: 请求域流式与任务异步的判别两条件
  type: framework
  source_chapter: 第 12 章 12.2.3
  source_quote: |
    "需要分别检查两个条件：是否有独立于连接的任务句柄，以及是否有事件续传位置。……流结束与业务任务结束是不同边界"
  summary: |
    token 流与 SSE 只说明结果如何逐步到达，不说明任务是否独立于连接存在——一个流可以是当前调用输出也可以订阅持久后台任务。

    有任务句柄不一定有完整事件重播，有事件序号不保证业务状态可恢复；断连是否取消执行、能否查结果由服务契约明确，不能从传输形式推断。

- id: f2-96
  title: 通信契约六要素（设计检查表）
  type: framework
  source_chapter: 第 12 章 12.2.5
  source_quote: |
    "无论落在哪一档，一份可用于生产的 Agent 通信契约都需要回答六个问题。这六项既是设计检查表，也是判断某个协议”缺什么“的量规。"

- id: f2-97
  title: 同步通信三项选择依据
  type: framework
  source_chapter: 第 12 章 12.3.3
  source_quote: |
    "选择请求—响应时，应检查执行时长、扩展需求和失败处理三项条件。"
  summary: |

  outputs: [该链路的通信语义选择]

  missing_conditions: [具体时限阈值需各方在接入时约定]

  title: 持久通道四条最小语义
  type: framework
  source_chapter: 第 12 章 12.4.3
  source_quote: |

  summary: |

- id: f2-105
  title: 手脑分离：决策循环与工具执行的进程解耦
  type: framework
  source_chapter: 第 12 章 12.7.2
  source_quote: |
    "会话是追加式事件日志……Harness 是调用模型、路由工具调用的那个循环；沙箱是跑代码、改文件的执行环境。……任务不属于某台机器，机器只负责当前这一棒。"
  summary: |
    把决策循环（脑）与工具执行（手）拆到不同进程，以会话通道相连。三个抽象解耦：会话=追加式事件日志（完整保留，压缩裁剪是不可逆决策），

- id: f2-106
  title: 海量会话通道的失效点与轻量通道
  type: framework
  source_chapter: 第 12 章 12.7.3
  source_quote: |
    "若用常规消息队列为每个会话建一个标准主题，通道本身的元数据会先于业务压垮控制面。"
  summary: |
    会话数到万级十万级时三种直觉方案失效：每会话一个标准主题（元数据/路由同步/创建回收成本）、
    广播消息（全量重复投递过滤，单节点成容量上限）、每 Session 独立消费组（消费组爆炸+外部协调等于重建路由）。
    并列反模式：会话与常驻工作进程一对一绑死（"宠物"式进程，占资源、断线丢上下文、迁移难）。
    解法是轻量通道/逻辑通道复用：运行时按业务标识声明挂到少量父主题，服务端内存仅字符串键，共享父主题存储+轻量索引；
    配套机制：首次发送自动创建、双向索引、就绪集合公平排空、空闲自动回收、单通道挂起、通配符/显式两种订阅。
    验收关注持久性、保序、隔离、恢复与规模成本，不限定具体产品机制。
  tags: [messaging, scalability, channel, failure-mode]

- id: f2-107
  title: 人机面结构：连接不是任务边界
  type: framework
