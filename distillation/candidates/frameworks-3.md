- id: f3-01
  title: 治理四支柱模型（可见／有边界／资产可管理／行为可验证）
  type: framework
  source_chapter: 治理篇导读（第 13-16 章总纲）
  source_quote: |
    "治理不是给运行额外附加约束的环节，而是让一个已经在运行的系统变得可信：可观测、有边界、资产可管理、行为可验证。"
  summary: |
    把"让自主运行的 Agent 系统可信"分解为四个可分别建设的支柱：运行可见（可观测性）、行为有边界（安全）、
    依赖资产可管理（注册/版本/发现）、上线前行为可验证（仿真）。四支柱中只有可观测性构成硬依赖
    （没有统一口径的 Trace 与指标，安全事件无法定位、变更影响无法度量、验证缺少比较基准），
    其余可按当前关注点选择顺序；治理沉淀的观测指标、审计证据、资产记录与验证结论同时是调优的可信事实输入。
  tags: [governance, mental-model, observability, security, asset-management, simulation]

- id: f3-02
  title: AI 可观测性"看什么 × 看哪里"规划框架
  type: framework
  source_chapter: 第 13 章 13.1.3
  source_quote: |
    "AI 可观测性需要明确两个基本问题：一是'看什么'，即从哪些维度判断 Agent 的运行状态；二是'看哪里'，即需要覆盖哪些观测对象。"
  summary: |
    设计观测体系先回答两个正交问题。"看什么"＝四个观测维度：运行表现（任务是否完成/输出是否符合预期）、
    稳定性与性能（错误/超时/重试/异常循环/延迟）、成本与效率（Token/调用成本/资源效率）、行为审计（关键操作可追溯）。
    "看哪里"＝三层观测对象：任务与交互层（请求/轮次/会话/任务）、Agent 执行层（Agent/工作流/模型/检索/工具调用）、
    AI 基础设施层（AI 网关/推理引擎/沙箱/Pod/GPU）。维度与对象通过指标、日志、Trace、事件建立关联，
    使问题能从任务结果逐步定位到具体执行步骤或基础设施状态。
  tags: [observability, planning, matrix]

- id: f3-03
  title: 四层观测数据采集架构
  type: framework
  source_chapter: 第 13 章 13.2.1
  source_quote: |
    "统一采集架构并不要求所有对象采用相同的接入方式，而是允许多种采集入口并存，在汇聚过程中统一传输协议、执行语义和关联标识。"
  summary: |
    面对异构 Agent 技术栈的统一采集架构分四层：被观测对象层（应用/Coding Agent/网关/推理/工具/沙箱/容器/GPU）、
    采集接入层（埋点、SDK 插桩、探针、Hook、Daemon、服务端遥测、日志解析、K8s 接收器、节点 Agent、eBPF，可组合）、
    统一处理层（采集网关做协议适配/语义规范化/采样/过滤/脱敏/路由，统一字段含义并保留来源与实际值/估算值）、
    存储与分析层（各类数据进各自存储，通过共同标识联合查询而非强行同模型）。
    组合采集时按原生调用 ID、时间边界和数据来源去重，避免同一次操作重复建 Span 或重复累计 Token。
  inputs: [多来源遥测数据（应用埋点/探针/Hook/Daemon/eBPF/服务端指标）]
  outputs: [统一语义、可关联的 Trace/Metrics/日志/事件存储]
  steps:
    - 按对象能力选择一种或多种采集入口（应用最懂语义，服务端有请求处理状态，运行时采集证明实际行为）
    - 多入口组合采集，按原生调用 ID、时间边界、数据来源去重
    - 经统一采集网关（OTLP 等）完成协议适配、语义规范化、属性补充、采样、过滤、脱敏
    - 按数据类型路由到各自存储，通过共同标识建立联合查询
  missing_conditions: [各层具体产品选型由部署环境决定，书中以阿里云/LoongSuite 为例]
  tags: [observability, architecture, data-collection, multi-source]

  title: 遥测数据分工框架（Trace 定位路径 / Metrics 发现趋势 / 日志事件保存细节）
  type: framework
  source_chapter: 第 13 章 13.2.1（13.5.1 呼应）
  source_quote: |
    "Trace 记录一次请求或 Agent 活跃执行中的因果关系，将应用入口、Agent 编排、模型调用、检索、工具调用、AI 网关、推理服务和沙箱执行串联起来。"
  summary: |
    三类遥测数据互补分工：Trace 记录因果关系、还原执行路径（还应继续关联沙箱内子进程/文件/网络等有诊断价值的行为，
    避免停留在"命令执行成功"）；Metrics 观察请求量/错误率/耗时/Token/成本/资源利用率等聚合趋势，
    指标标签用低基数可控维度（模型、工具类型、环境、结果），不用 Session ID/Trace ID 等高基数字段；
    日志与事件保存消息摘要、错误栈、策略判定、进程退出等细节，数量大粒度细的行为不逐一建 Span，
    而是通过 Trace ID/Span ID/tool-call ID/实例与进程标识在 Trace 视图下钻。

- id: f3-05
  title: 高代码应用观测接入三方式选型（手动埋点 / 进程级插桩 / K8s 自动注入）
  type: framework
  source_chapter: 第 13 章 13.2.2
  source_quote: |
    "实际选型不应只追求'零代码'。对于框架支持良好、以技术性能监控为主的应用，可先采用对应语言的自动插桩探针"
  summary: |
    三种接入方式按"语义最强、改造较多 → 接入统一、改造较少"排列：LoongSuite GenAI Utils 手动埋点
    （语义最强，可记录目标/阶段/业务结果，需改代码并正确处理上下文/异常/异步/流式）、进程级探针自动插桩
    （零代码改动覆盖受支持组件，但只能识别"调用了什么"无法推断"为什么调用/属于哪个业务阶段"）、
    K8s 集群级 Operator 自动注入（批量交付探针与配置，解决交付治理而非语义）。
    生产实践常用"探针采集通用依赖 + GenAI Utils 补充业务语义"的混合方式；
    核心判据：需要还原决策过程、区分执行阶段或按业务结果分析 → 必须手动埋点补业务语义。
    手动与自动组合时避免重复建模：探针已生成的 Span 不再创建语义相同的 LLM/Tool Span。
  inputs: [应用可改造程度, 框架/SDK 支持情况, 观测目标（技术监控 vs 业务语义）]
  outputs: [选定的接入方式组合, 唯一有效的 TracerProvider 与导出链路]
  steps:
    - 判断应用是否可修改代码/启动方式/工作负载配置
    - 以技术性能监控为主且框架受支持 → 自动插桩
    - 需还原决策过程/区分阶段/按业务结果分析 → SDK/GenAI 语义库手动埋点
    - K8s 规模化环境 → Operator 统一交付探针，再在关键边界补业务语义
    - 保证进程内只有一套有效 TracerProvider；对 Prompt/响应/参数设置按需采集、截断、脱敏、采样与访问控制
  missing_conditions: [探针版本与依赖兼容性需逐启动方式（Uvicorn/Gunicorn 等）验证]
  tags: [observability, instrumentation, selection, tracing]

- id: f3-06
  title: Agent 任务 Span 层级建模法（ENTRY→AGENT/WORKFLOW→STEP→LLM/RETRIEVAL/TOOL）
  type: framework
  source_chapter: 第 13 章 13.2.2
  source_quote: |
    "以一次 Agent 任务为例，建议形成'ENTRY → AGENT/WORKFLOW → STEP → LLM/RETRIEVAL/TOOL'的基本层级。"
  summary: |
    用统一层级把用户请求、Agent 规划、模型推理、检索和工具执行还原为有父子关系的任务轨迹：
    入口 Span 记录会话/用户/任务上下文；Agent 或工作流 Span 表示一次编排；Step 表示计划/执行/反思阶段；
    叶子 Span 表示模型、检索或工具调用。每个 Span 按需记录模型与供应商、Token、工具名、参数摘要、结果摘要、
    重试、超时、完成原因等属性。跨步骤字段（业务主键、租户、渠道、实验分组）在入口写入 Baggage 随上下文传播，
    只属于单个操作的字段写在对应 Span 上，避免高基数或敏感数据无差别复制到整条链路。
    Web 应用在 WSGI/ASGI 中间件建 Entry；框架回调接入时以 run_id/parent_run_id 保存关系而非线程号；
    流式调用记录首 Token 时间并在流结束后写完整用量。
  inputs: [Agent 任务执行过程, 会话/用户/任务标识]
  outputs: [具有父子关系的任务轨迹（Trace/Spans），含 Token/耗时/状态属性]
  steps:
    - 在业务入口建立 ENTRY Span，写入 session_id/user_id 到 Baggage 并传播
    - 为每次 Agent 编排建立 AGENT/WORKFLOW Span
    - 为计划/执行/反思阶段建立 STEP Span
    - 为模型/检索/工具调用建立叶子 Span，退出上下文前写回结果类字段
    - 重复出现的业务函数封装为装饰器；生成器/流式/后台任务将上下文保持到流结束、取消或失败
  missing_conditions: [框架无稳定生命周期回调时需等待插件支持或基于 BaseInstrumentor 自行扩展]
  tags: [observability, span-hierarchy, instrumentation, tracing]

- id: f3-07
  title: Coding/通用 Agent 遥测事件→Trace 重建法（多来源融合）
  type: framework
  source_chapter: 第 13 章 13.2.3
  source_quote: |
    "多来源融合应按字段确定权威来源，优先使用原生请求、响应和工具调用 ID 配对。时间接近只能作为受约束的辅助证据。"
  summary: |
    对无法修改内部实现的 CLI/IDE/桌面 Agent，用"Agent 侧适配器 + 独立 Daemon"协同采集：
    适配器从原生回调（模型请求响应、工具开始结束）、生命周期 Hook（用户输入、轮次结束通知）、
    本地 transcript/日志/数据库（消息、原生调用 ID、Token、持久化时间）获取原生执行证据；
    Daemon 负责增量读取（文件偏移/游标/快照）、跨来源补充、语义归一化和上报。
    各来源先归一化为遥测事件再构建 Trace；按字段确定权威来源，优先用原生请求响应与工具调用 ID 配对，
    Hook 与 transcript 观察到同一操作时合并去重，缺失/估算信息明确标识不用零值补齐。
    关键判定规则：模型生成的 tool-call 只是调用意图，实际执行由匹配的执行回调或结果记录确认；
    轮次结束依据运行级终止证据而非单次模型结束；Token 优先用服务端实际用量、同响应多来源只累计一次；
    业务 Task 与原生 Session 区分并保留映射，关联缺失时明确标识不从时间邻近自行推断。
  inputs: [原生回调, 生命周期 Hook, 本地 transcript/日志/数据库]
  outputs: [可关联的执行记录（Trace），含调用配对、时间边界、去重后的 Token 用量]
  steps:
    - 按 Agent 暴露的能力选择采集入口，三类来源可组合
    - Hook 只记录活动或唤醒标记，限制执行时间与数据规模；Daemon 增量读取并确认记录完整
    - 归一化为遥测事件（用户输入/llm.request/llm.response/tool.call/tool.result 等），保留原生关联标识
    - 按稳定标识配对请求与响应、调用与结果，构建 Trace；排除兼容副本避免重复建模
    - 持久化采集游标与去重状态，游标只推进到完整且已处理的记录边界
    - 对照原始记录、遥测事件与最终 Trace 做验收（多轮/并行/取消/错误/子 Agent/重启恢复）
  missing_conditions: [Hook 通知只表示有活动，不能据此认定调用已结束；常规 Input 保存游标不等于后端已收到（端到端不丢不重需另行设计）]
  tags: [observability, coding-agent, telemetry, trace-reconstruction]

- id: f3-08
  title: eBPF 无侵入运行时观测链路
  type: framework
  source_chapter: 第 13 章 13.2.4
  source_quote: |
    "Agent 的模型调用与工具执行等关键行为均经由稳定的内核接口，为统一观测提供了基础。"
  summary: |
    当 SDK 与扩展能力差异大、应用层埋点适配成本高时，利用内核稳定接口无侵入采集：
    模型调用＝一次网络请求+响应（可从流式增量到达时刻得出 TTFT/TPOT/端到端耗时）；
    工具调用＝进程、文件、网络三类事件（进程树与命令行、文件读写反映对代码配置的改动、网络事件覆盖外部访问）。
    事件统一携带进程标识与内核时间戳，可按进程关系与时序拼接，把模型输出的工具调用意图与随后真实发生的系统行为对应，
    还原完整 Agent 行为轨迹。固定处理链路：内核态探针事件 → 事件解析（字节流还原为 HTTP/1.1、HTTP/2 结构化报文，
    进程/文件/网络事件还原为结构化记录）→ 事件关联（按连接配对请求响应、按父子关系串进程树）→
    输出进程事件树 + 以会话为单位的 Agent 轨迹。
  inputs: [内核态探针事件（网络/进程/文件）]
  outputs: [进程事件树（每次工具执行的命令与产物）, Agent 轨迹（按时序的模型调用与工具执行）]
  steps:
    - 在模型调用与工具执行必经的内核接口部署 eBPF 探针
    - 批量送入用户态做事件解析，还原结构化报文与记录
    - 按连接配对请求响应、按父子关系串联进程树
    - 输出进程事件树与 Agent 轨迹两份数据，与模型工具调用意图对应
  missing_conditions: [加密流量与部分用户态协议可见性有限；缺用户目标与业务授权上下文，需与应用埋点互证]
  tags: [observability, ebpf, runtime, non-intrusive]

- id: f3-09
  title: Session-Trace-Span 三层观测模型与 Trace 切分边界
  type: framework
  source_chapter: 第 13 章 13.3.1
  source_quote: |
    "如果执行通过持久化队列、回调或长时间等待跨越了清晰的运行边界，应在恢复时创建新 Trace，并通过相同的 Session 标识、前序关系或 Trace Link 保留上下文和因果联系。"
  summary: |
    用三个逻辑层级组织 Agent 观测：Session 是跨多次交互的关联范围（可跨多条 Trace 和较长时间间隔），
    不宜把整个长会话记为一条永不结束的 Trace；Trace 记录一次外部输入触发的活跃执行，
    当 Agent 返回结果、转入跨请求等待、或因错误中断停止时结束；Span 是有明确开始/结束/结果的可观测操作，
    通过父子与时间关系构成调用树（嵌套＝调用关系，同父时间重叠＝并行）。
    切分规则：内部重试/模型回退不结束当前 Trace 但每次实际调用分别记录；流式输出属同一 Trace
    （覆盖到流消费完成或被中断）；AskUser/HITL 若同进程内未释放控制权则沿用当前 Trace，
    若已持久化状态或进入长等待则结束并在外部输入重新激活时创建新 Trace，用 Session 标识+前序关系关联。
    Span 划分优先覆盖对结果、延迟、成本有实际影响的操作，过粗无法定位、过细引入噪声与开销。
  tags: [observability, trace, session, boundary, hitl]

- id: f3-10
  title: Agent 执行语义统一框架（ENTRY/AGENT/WORKFLOW/STEP/LLM/RETRIEVAL/MEMORY/TOOL/GUARDRAIL/COMPACTION/HITL/INTERRUPT）
  type: framework
  source_chapter: 第 13 章 13.3.2
  source_quote: |
    "如果缺少统一语义，同一类行为会以不同名称进入观测平台，难以进行跨应用查询和聚合分析。"
  summary: |
    用十二种执行语义统一描述链路中实际发生的操作及其观测边界：ENTRY（一次外部请求的完整处理，一个 Session 可含多次 ENTRY）、
    AGENT（一次实际 Agent 调用，子 Agent 也是独立调用并关联发起方）、WORKFLOW（多节点编排过程）、
    STEP（ReAct 一次推理-行动迭代，只在能可靠识别轮次时记录）、LLM（一次真实发往模型的请求，重试/回退分别记录）、
    RETRIEVAL（召回外部信息，LLM 自主发起的检索位于对应 TOOL 下）、MEMORY（明确的记忆读写管理，不把读已组装上下文当 MEMORY）、
    TOOL（一次实际发生的工具执行，不表示模型调用意图；审批等待与实际执行区分）、GUARDRAIL（围绕明确对象的规则校验，
    记录被校验对象/阶段/判定/处置并紧邻被保护操作）、COMPACTION（上下文摘要裁剪卸载，记录触发原因与前后规模）、
    HITL（人工参与交互，区分等待/恢复/拒绝/终止）、INTERRUPT（正常完成前被停止，保留发起方与原因）。
    Trace 父子结构应反映真实调用关系而非人为拼接成固定树形；语义设计优先记录系统能直接观察和验证的事实，
    不把无法稳定获得的模型内部思维过程作为必要字段。
  tags: [observability, semantics, taxonomy, trace, cross-framework]

- id: f3-11
  title: 稳定性问题"聚合指标→Trace 下钻"排障路径
  type: framework
  source_chapter: 第 13 章 13.3.3
  source_quote: |
    "此类问题通常需要先通过聚合指标发现趋势或异常，再下钻到对应请求的 Trace，查看具体错误位置和步骤耗时。"
  summary: |
    稳定性问题不一定表现为单次请求失败，也可能体现为错误率、超时率或延迟长尾的持续升高。
    排障路径：先用聚合指标发现趋势或异常（请求量、各操作类型错误率、超时率、错误类型占比及首次失败位置分布、
    端到端延迟与步骤延迟的 P50/P95/P99、模型 TTFT/TPOT），再下钻到对应请求的 Trace 查看具体错误位置和步骤耗时。

- id: f3-18
  title: 推理耗时分解联合解读法（E2E ≈ 队列等待+Prefill+Decode+开销）
  type: framework
  source_chapter: 第 13 章 13.5.2
  source_quote: |
    "一次请求的端到端耗时可以近似拆为'队列等待 + Prefill + Decode + 框架及网络开销'。"
  summary: |
    推理指标之间应联合解读而不是逐项设阈值。分解式：端到端耗时 ≈ 队列等待 + Prefill + Decode + 框架及网络开销。
    判断规则：E2E 与 TTFT 同时上升而 TPOT 基本稳定 → 优先检查 Waiting 请求数、Queue Time、Prompt 长度和 Prefill；
    TTFT 正常而 TPOT 上升 → 检查 Decode 是否受同批 Prefill 干扰、并发是否过高、GPU 计算或显存带宽是否饱和；
    吞吐下降且 KV Cache 命中率同步降低 → 检查请求前缀是否变化、缓存容量是否不足、流量是否被分配到冷实例。
    下钻维度：模型整体 TTFT 上升而只有一个 Pod 异常 → 路由倾斜或单实例容量不足；所有 Pod 同时恶化 →
    流量超整体容量、请求长度分布变化或配置调整。TTFT 反映排队与 Prefill，TPOT 接近 Decode 生成速度，两者不可只用总耗时代替。

- id: f3-19
  title: 并发分析（时间块+执行快照）方法
  type: framework
  source_chapter: 第 13 章 13.5.2
  source_quote: |
    "并发分析以时间为横轴，将每个请求的 Wait、Prefill 和 Decode 阶段绘制为时间块。沿某一时刻画一条竖线，穿过的所有请求就是当时引擎内的执行快照"
  summary: |
    Continuous Batching 使请求之间产生运行时相互影响（某请求 TPOT 变高可能因同批插入大 Prefill；长时间 Wait
    可能因并发突增占满槽位），单条 Trace 展示该请求的经历却不一定包含变慢的全部原因。
    并发分析以时间为横轴把每个请求的 Wait/Prefill/Decode 绘为时间块：横向看单个请求的阶段耗时，
    纵向看它与同批请求的重叠；沿某一时刻画竖线，穿过的所有请求即当时引擎执行快照。
    使用时从异常 Trace 的时间点跳转或选择相同时间窗口，查看该请求进入引擎前后的并发度、阶段交叠和其他请求的 Token 长度。
    典型场景：大 Prefill 阻塞同批 Decode（TPOT 同步升高）、并发突增排队（Waiting/Queue Time/TTFT 同升而 TPOT 未必恶化）。
    Prefill/Decode 分离部署时可分面板展示并用虚线关联同一请求，判断排队发生在 Prefill 侧、跨阶段传输还是 Decode 侧。
  inputs: [异常 Trace 的时间点, 引擎调度事件流]
  outputs: [同批请求相互影响的现场还原, 瓶颈类型判断（大 Prefill/排队/占槽/P-D 不匹配）]
  steps:
    - 先按高耗时或高 TTFT 筛出异常请求并记录时间窗口
    - 切到相同时间窗口的并发视图
    - 沿时间竖线取执行快照，观察异常请求与同批请求的阶段重叠
    - 结合其他请求 Token 长度与并发度判断干扰来源
    - 结合 TPOT 分位数、吞吐与 GPU 利用率验证是否为稳定瓶颈后再调整
  missing_conditions: [是否调整不能只依据一次慢请求，需验证为稳定瓶颈]
  tags: [troubleshooting, concurrency-analysis, inference-engine, continuous-batching]

- id: f3-34
  title: Prompt 发布、灰度与回滚机制
  type: framework
  source_chapter: 第 15 章 15.1.4
  source_quote: |
    "新版本通常先在测试环境完成离线评测，再进入限定 Agent、租户或流量范围的小规模验证。确认质量、延迟和成本符合预期后，才将稳定标签移动到新版本。"
  summary: |
    Prompt 发布采用"版本+标签"双轨：历史版本内容始终保持不变，变化的是标签（stable/canary 等）与版本之间的指向关系，

  inputs: [通过评审的 Prompt 候选版本, 灰度范围划分, 回滚目标]
  outputs: [稳定标签指向的新版本或回滚记录]
  steps:
    - 测试环境完成离线评测
    - 进入限定 Agent/租户/流量的灰度验证
    - 确认质量、延迟、成本符合预期
    - 移动 stable 标签到新版本
    - 出现质量或安全问题时标签回指最近已验证版本并记录

  type: framework

  type: framework

  type: framework

- id: f3-71
  title: Simulation 数据契约对象链（Spec→Manifest→Run→Task→Session→Event + Run Result）
  type: framework
  source_chapter: 第 16 章 16.3
  source_quote: |

- id: f3-82
  title: 用户与环境联合建模五维约束
  type: framework
  source_chapter: 第 16 章 16.5.1
  source_quote: |
    "用户嘴里的订单、工具参数里的订单号、数据库里的订单记录，必须是同一张单子——任何一处脱节，场景测的就是假问题。"
  summary: |
    用户模拟与环境模拟必须联合建模，确保同一业务对象在两侧有一致含义。联合约束覆盖五个维度：实体与事实绑定
    （订单只有一个事实版本）、信息可见性（用户认知与环境状态允许不同，但两侧内部各自一致）、动作入口与状态归属

    （任务完成判定随场景演化更新）。沿业务流程时间线可提炼四类典型变体（用户行为条件与环境条件独立变化、联合验证重点

    长时间等待（可按等待时长离开+查询持续未完成——验证等待计时、离开事件与在途操作衔接）、提交前撤回
    （已同意提交后撤回+撤回与提交有明确事件顺序——验证获知撤回后是否调整）、受理后响应丢失（未看到回执继续追问+
    申请已受理响应未到达——验证是否核实状态、避免重复申请）。

  type: framework
  source_chapter: 第 16 章 16.5.2
  source_quote: |
    "一个可执行的场景规格需要回答一串递进的问题：这个场景是谁、测什么、环境怎么设、用户与环境怎么关联、别的参与者是谁、事件怎么演化、运行怎么约束、怎么评价、从哪来的。"
  summary: |
    场景规格（允许多条合理执行路径的声明式规格，非脚本也非随机生成）用十个字段组沿问题链展开：
    identity（场景 ID、版本、标签、负责人——身份与变更治理）、sut（被测边界、Agent 版本、模型与 Prompt 引用——固定实验对象）、

    events.triggers 是未来计划，命中后才生成 Event。场景（实验设计方案）与资产（独立版本化的标准化材料）分离：
    改用户耐心参数是新场景版本，改模拟器披露规则逻辑是新资产版本。

- id: f3-86
  title: Simulation/Evaluation 职责划分与三道证据可用性检查
  type: framework
  source_chapter: 第 16 章 16.6.1
  source_quote: |
    "运行完成、任务成功、允许发布，是三个互相独立的结论，不能相互推导"
  summary: |
    Run Result 交付的是证据材料不是质量结论："退款申请数=1"是观测，"Agent 是否正确处理了退款"是判断。
    三个独立结论不能互相推导：运行完成是执行生命周期的事实；任务成功属于 Outcome，由业务应用或获授权 Verifier 依据
    成功标准判定；发布授权属于治理门禁。职责表：用户目标（Simulation 驱动用户继续/澄清/停止 vs Evaluation 判断业务
    目标是否实际完成）、环境故障（施加条件并记录生效与恢复 vs 判断应对与业务后果）、业务状态（按契约维护并采集 vs
    对照目标和政策检查）、运行时限（达到条件时结束 vs 判断是否满足时效）、仿真契约（报告角色漂移和执行错误 vs
    限定可评分范围与结论可信度）。有效性检查是 Simulation 最后一项输出：核实场景配置正确、用户行为遵守认知和披露规则、
    故障生效并命中、必需证据可访问。评估器一侧的证据可用性检查是三道而非一道：记录完整性（材料在不在）、
    运行有效性（条件成立没有）、证据充分性（够不够支撑这个评价项）；证据不足的项目输出"不可判定"——
    不可判定是诚实的结论，好过用不充分的证据硬评。

- id: f3-87
  title: 证据包七种用途
  type: framework
  source_chapter: 第 16 章 16.6.2
  source_quote: |
    "一次 Run 的产物不止判一次'通过/不通过'。Run Result 作为结构化证据，在治理体系中至少有七种用途"
  summary: |
    同一份 Run Result 证据包在治理体系的七种用途（前四种用证据回答问题，后三种用证据反哺体系）：
    ①质量评估与重评分（轨迹和状态交给断言/Judge/人工；边界：新增评价只能用原始证据足以支撑的信息）；
    ②缺陷定位与归因（关联用户反应→Agent 动作→工具执行→状态变化；复杂因果可能需对照运行）；
    ③版本回归与门禁（基线与候选在相同条件下配对比较；保留回归与发布依据）；
    ④复现与回放（用 Manifest 重建条件或用 Trace 交互式回放；按三种复现层次区分用途）；
    ⑤场景提取与覆盖补充（从异常路径和未命中事件提取候选场景；必须重新验证）；
    ⑥模拟器质量治理（聚合用户事实违规和环境状态不一致；避免把模拟器问题误归因于 Agent）；
    ⑦性能与成本分析（按参与方和阶段汇总耗时、Token 和费用；区分业务执行与仿真平台开销）。
    门禁边界：Testing Gate 汇总验证结果、组织回归证据，但不是发布决定者——获授权的治理节点拿证据做发布决策，
    例外路径有审批与留痕。

- id: f3-88
  title: 零违规统计置信上界推理（3/n 规则）
  type: framework
  source_chapter: 第 16 章 16.6.2
  source_quote: |
    "n 次独立运行零违规，违规率的单侧 95% 置信上界是 1 − 0.05^(1/n)，大样本下近似 3/n"
  summary: |
    读零违规回归结果的统计边界：n 次独立运行零违规，违规率的单侧 95% 置信上界是 1 − 0.05^(1/n)，
    大样本下近似 3/n——300 次零违规意味着"违规率大概率不超过 1%"，而不是零。

    最常见误读：把置信上界读成"真实违规率有 95% 的概率低于该值"（混淆了频率学派置信区间与后验概率）。

- id: f3-89
  title: 仿真假设过期信号与事件驱动校准
  type: framework
  source_chapter: 第 16 章 16.6.3
  source_quote: |
    "仿真成功率上升而生产人工接管持续增加，就是假设过期的信号。"
  summary: |
    Simulation 的结论建立在会过期的假设上：仿真用户不是真实用户（用户模型是假设，仿真成功率上升不能替代真实业务指标）、
    场景来自已知失败模式（覆盖不了训练分布之外的未知风险）、工具契约/用户行为分布/故障频次随业务漂移。
    过期信号：仿真成功率上升而生产人工接管持续增加。校准机制由事件驱动：接口变更、故障复盘、用户结构变化时触发，
    不按固定周期例行执行——固定周期会在两次校准之间放过漂移，事件驱动把成本花在漂移真正发生的地方。
    Simulation 与其他治理手段互补而非替代：生产可观测提供真实运行数据，安全框架提供威胁模型和防护规则，
    资产发现与管理提供 Agent 资产台账和版本治理。
